# Source-preserving availability storage

[ADR 0072](adr/0072-source-preserving-availability-storage.md) implements the storage prerequisites selected in [ADR 0071](adr/0071-create-only-availability-import.md). This extends native storage, validation, protocol lifecycle and calculation. Authenticated create-only import now uses this representation under [ADR 0073](adr/0073-authenticated-create-only-availability-import.md) and [the import guide](availability-import.md). Authenticated export now follows ADR 0074; source replacement/reconciliation and publication remain pending.

## Native identity and source UID

Definition API IDs remain server-generated UUIDs. Active definition protocolUid is now an exact decoded TEXT string, up to the existing 4096-code-point UID profile. It is not trimmed, case folded, Unicode normalized or parsed as a UUID. Ordinary native creation still generates its stable UID; API clients cannot choose or rename it.

Each opening keeps uid as its native UUID for occurrence actions, previews, edit lists and protocol checkpoints. A separate protocolUid string holds source identity. New native openings receive server-managed values; existing values are retained when omitted from ordinary edits, and attempts to change them reject. Cloning a new native opening must omit both uid and protocolUid; copied read-only source contacts cannot be authored through that operation. A native UID string can happen to equal its UUID spelling; the two identities still have different roles. Source conversion allocates new UUIDs while preserving arbitrary source UIDs.

Active data now contains actual calendarId and a 64-character SHA-256 UTF-8 uidDigest. A non-unique (calendarId, uidDigest) candidate index replaces the global unique UUID index. Exact string equality under the existing durable scope transaction decides conflicts; matching digests alone never merge objects. Native creation uses this check. ADR 0073 import uses the same locked check for source UIDs and adds its own two-host race evidence. Ordinary native creation still exposes no UID-setting field. Row loading validates the actual parent/digest relationship and fails unavailable on corrupted state.

Deletion removes the active data, lookup values, content and protocol state. Existing native identity markers stay content-free. Active UID conflicts are destination-calendar scoped; another calendar may hold the same source UID with a different native identity.

## Groups, comments and CONTACT

New optional categoryGroups values contain ordered groups, each with ordered TEXT values and optional LANGUAGE. Preserve duplicate values, source groups, Unicode spelling and language annotations. Counts apply before normalization: 64 total category values per component, 256 code points per value, and existing metadata budgets.

The earlier native categories plus textParameters.categoryLanguage representation remains a supported single-group alternative. A component cannot combine nonempty categoryGroups with meaningful legacy categories/language. This explicit alternative avoids competing authoritative copies while allowing existing native rows and clients to retain their single-group form. Imported proposals use categoryGroups. Omitted groups are retained by native replacements; [] explicitly clears them. Exact authorized category queries include every grouped value without language folding or hidden-rule membership disclosure. A legacy single-group payload cannot silently flatten existing grouped data.

Existing COMMENT lists and position-aligned textParameters.comments already represent the full selected repeated COMMENT profile, so they remain in place. Validation freezes both and requires exact annotation alignment. CONTACT uses a separate typed contacts list: TEXT value, optional LANGUAGE and ALTREP, at most 32 values of 4096 code points each. No alternative URI is retrieved.

CONTACT is read-only through native editing. Supplying CONTACT or an opening protocol UID for equality checking requires raw readAvailability authority before the comparison and again in the final write checks. Missing read access yields the same denial for correct and incorrect guesses. Write-only callers can omit these read-only fields and retain them; receipt disclosure still depends on write decisions, not the extra read decision. Omission retains current contacts; an identical echo is permitted; changing or clearing them rejects. Ordinary native creation cannot author contacts. Deleting an opening/definition removes its own content normally. Authorized raw views and frozen host snapshots include retained contacts; free/busy/subject summaries do not. Native edits do not gain address ownership, directory lookup, scheduling or publication authority from any metadata.

The example metadata editor edits the first grouped category property and clearly displays/preserves additional groups and imported contacts. It keeps all comment annotations. The timing editor retains groups, contacts, opening protocol UID and periods; existing unsupported-shape guards continue preventing it from flattening duration forms, multiple openings or rules it cannot edit. This is not a general source-file editor.

## PERIOD timing and bounded calculation

Availability openings now have an optional periods list of typed timing values. Every entry has an explicit UTC or exact named-zone start plus a positive explicit end or nominal duration. Preserve units and end-versus-duration form; fractions, floating/DATE values, mixed profiles, conflicting periods and invalid original anchors reject through the existing core. Start inclusions, exclusions and periods share the 256-raw-date cap.

The public event recurrence/content DTOs are unchanged. Internal event timing helpers accept optional periods for availability only, allowing original-identity single/future edits, previews and free/busy composition to use the same validated core semantics. EXDATE precedence, RFC gap/fold behavior, ISO/WKST rules and the whole-second [1970–2099 profile](adr/0041-whole-second-1970-2100-profile.md) remain unchanged.

Stored opening masters may number up to 128 per definition, matching a possible wire file shape. Query limits remain independent: native free/busy/subject search still allows 64 aggregate contributing source openings and existing 5000-output caps. Larger stored data can therefore return unknown/failure; it never establishes free time from an incomplete calculation. Availability expansion now shares 200000 recurrence candidate work across opening series and, through the existing search budget, across evaluated definitions/contributors. Failed work is not replenished. Existing event query limits and pure wire parse/query budgets remain active.

## Source and native protocol lifecycle

Definition protocol sequence, created and lastModified are nullable to preserve source omission; stamp remains required. Opening stamp remains required while created/lastModified can be absent and independent. These are protocol values, not database audit evidence: source dates need not equal import time, one another or their parent's timestamps. Whole-second UTC and the existing ordinary date profile still apply. Native views expose absent dates rather than inventing them; API revision remains authoritative for concurrency.

Existing local creation still starts at sequence 0 with known database-clock dates. Identical normalized saves preserve imported sequence/date omissions. Actual native changes advance effective sequence (omitted means 0) once; maximum sequence rejects changes atomically. Affected stamps use max(whole-second database clock, previous component stamp, previous LAST-MODIFIED), retaining nondecreasing values even for future-dated sources. CREATED remains absent when unknown. Newly created local openings/components use their known database-clock creation time, independently of a future-dated parent checkpoint; they do not inherit fabricated future creation dates. Database updatedAt still reflects local audit time separately.

Opening protocol checkpoints now retain typed override component states keyed by original recurrence identity and single/future kind. They preserve independent source dates and supplied/omitted legal metadata. Timing-only component values must inherit the master; mismatches, duplicate/orphan states and unsupported private-property multiplicity reject. Explicit supplied properties follow later native master metadata changes, while omitted properties remain omitted. Timing changes refresh affected component state, and clearing an edit removes its component state. Skipping an occurrence retains its prior timing/state for restoration; a skip is not a fabricated AVAILABLE cancellation component.

Native changes to previously tracked timing edits preserve unknown creation: their first component baseline uses the existing opening checkpoint as an explicitly approximate version baseline. No historical creation time is manufactured. Unchanged siblings retain their own state. Component state is bounded by the existing 128 native timing-edit cap, with a separate 65536-code-point source-component metadata ceiling. Wire defaults remain 64 overrides per series and 65536 metadata code points across an entire parsed file.

## Pure storage conversion and authorization

The server-internal availabilityStorageProposal helper converts a successfully validated pure IcalendarAvailabilityDefinition into frozen native content, opening UUIDs, retained timing edits and source protocol state. It preserves optional bounds/duration, basic and grouped metadata, contacts, periods, original identities and component omissions. It does not write records, select a destination, authorize imports, approve an organizer, reconcile UIDs or grant current registry approval.

Authenticated import under ADR 0073 independently checks the actual destination and revision, separate import/create permissions, all current extension registrations and dedicated organizer approval, then commits the whole file atomically under the declared host-policy guarantee. Existing native content writes continue their preliminary/final host and organizer checks with the full validated proposed content/protocol state. External fresh-check policy still has its documented after-check revocation race.

## Migration and dependency evidence

Pinned CLI generation produced module migration 20261022150826628-availability-import-storage and example migration 20261022151001963-availability-import-storage. The CLI's proposed destructive table recreation was replaced only in migration.sql with the necessary in-place transformation: drop the former random UID default, cast existing UUID UIDs to text, backfill actual calendar/digest, replace the UID index/add the parent constraint, and add each existing opening's initial protocol UID spelling without changing its native UUID. Existing identity/revisions, metadata/comment alignment, protocol state, edits and audit times are retained. Missing persisted opening identities fail the migration rather than being silently invented.

New nested JSON fields are optional, so old category/comment/protocol representations remain decodable. Generation sources, clients and metadata are CLI-generated; migration metadata and definition.sql were not hand-edited. The generated final schema defines the same fields/indexes/constraints as the transformed upgrade. Populated upgrade fixtures check retained content/identity plus text type, absent old default and replacement index semantics; fresh database integration checks exercise the resulting schema. crypto 3.0.7 is now a pinned direct server dependency for digest calculation, reusing the existing workspace resolution; the example adds a test-only direct dependency on the wire package.

[Validation evidence](scaffold-validation.md) records actual focused and broader commands/results. Tests cover no-loss mapping, source dates/sequence, groups/CONTACT, periods and native edits, injected candidate-index digest collisions, long Unicode UIDs, independent destination copies, policy/stale rollback, deletion and populated upgrades. Two-host generated-client smoke checks exercise new groups, opening UID and PERIOD projections. These are storage/native tests, not authenticated import or external-client interoperability evidence.


## Proposed replacement baseline

[ADR 0075](adr/0075-availability-update-reconciliation-contract.md) proposes server-owned comparison baselines for explicit replacements. Current storage has no such baseline; source versions and database audit times alone do not establish one. Older/native-created rows must not be silently adopted. Proposed snapshot retention, canonicalization and deletion scrubbing require review before models change. No schema or migration is introduced by that documentation batch.
