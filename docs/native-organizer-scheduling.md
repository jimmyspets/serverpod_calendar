# Explicit native organizer scheduling

Status: scoped outbound REQUEST/CANCEL implementation through a transport-independent port and synthetic example adapter. Accepted ADRs 0122–0124 cover explicit native publication, whole-series cancellation/reopening and recurring masters. Accepted [ADR 0126](adr/0126-independent-occurrence-publication-versions.md) adds complete occurrence REQUEST bundles, independent outgoing versions and full-message host approval; accepted [ADR 0127](adr/0127-retained-occurrence-reset-projections.md) adds retained-original follow-series reset projections. Accepted [ADR 0128](adr/0128-explicit-single-occurrence-cancellation.md) adds historical single-occurrence CANCEL with preserved drafts and terminal-prior-delivery gating. See [validation](scaffold-validation.md) for actual results. Individual restoration, range cancellation, concurrent partial coordination, broader lifecycle/participant workflows, inbound reconciliation and RFC 6047 mail remain separate.

## Publishing and local edits

Create an ordinary native event first. The generated `calendarEvent.saveAndNotify` API accepts its UUID and expected revision, final event content, recipient calendar-address proposals and a UUID command key. It saves the validated event and all recipient intents in one transaction, or saves nothing. Ordinary event edits never queue invitations. The host supplies the verified organizer and approved routes; no client-supplied organizer identity or system flag is accepted.

The workflow supports single events and recurring masters with DATE, UTC and named-zone native timing with a fixed organizer and 1–64 fixed recipients. Every REQUEST publication is a complete supported snapshot for that same set; instance CANCEL is a separate partial action. Imported and unknown-origin events require a future explicit adoption flow. Changing recipients/organizer, range cancellation, replies, delegation and other durable methods reject and remain first-release work. Supported occurrence REQUEST/reset and single-CANCEL profiles are described below. No invitation grants access, assigns a task or reserves a resource.

The canonical event retains the approved organizer/attendee metadata; ordinary source-read permissions protect it. The event's protocol UID is stable and separate from feed publication identity and transport IDs. Native omitted/empty summaries produce an empty scheduling SUMMARY, never the example's “Untitled event” display label. Existing text LANGUAGE/ALTREP annotations survive ordinary text changes. Rich data unsupported by the scheduling profile rejects before committing; it is not silently dropped.

Actual component changes advance the native component version. Publishing an already-saved local edit reuses its existing newer component version when it is ahead of the last publication. Each changed outgoing component must have a greater SEQUENCE than its own previous publication, with the documented cancellation/reopening floors; overflow rejects atomically. Database-clock component times are whole-second and nondecreasing. Queue creation, delivery eligibility and seven-day expiry use raw database time separately, so a future native audit/protocol floor after clock correction cannot postpone work or extend its grace. Retries never change payload, source identity, SEQUENCE or DTSTAMP.

An exact retained command retry rechecks current authorization and returns its recorded receipt. A conflicting reuse of the command key rejects. Identical normalized current and last-published content is a true no-op with no revision, protocol, scope-generation or intent changes. A new publication advances the API revision even when the component was already saved locally, so stale commands cannot queue another publication. Command receipts have bounded retention; after cleanup, stale expected revisions still reject, but indefinite command-key deduplication is not promised. Save and notify is not an implicit manual resend of a failed publication.

## Host authorization and installation

Install an optional `CalendarSchedulingRuntime` on `CalendarModule.install`. It contains a `CalendarSchedulingHost`, `CalendarSchedulingTransport` and bounded `CalendarSchedulingOptions`. A host can omit it while using ordinary calendar/import/export/feed APIs. Scheduling publication then fails unavailable; no permissive default sender or transport exists.

For REQUEST, the ordinary policy independently enforces `publishScheduling`, `updateEvent`, full event detail disclosure and `readEventSource`, plus lifecycle permission when applicable. Explicit whole-series cancellation instead requires `cancelScheduling`, `changeEventStatus`, full ordinary detail and source-read authority; text-edit or REQUEST-publication permission is not required to cancel. `readScheduling` independently controls the bounded status response. Policies receive actual calendar/event state, validated final content/protocol state and an immutable `CalendarSchedulingIntent` containing the exact outgoing bytes, organizer, roster and publication generation and explicit REQUEST/CANCEL method. A command key or stored authority reference is never a grant.

`CalendarSchedulingPolicyContext.currentEvent` is actual current native state, `proposedEvent` is final native state, `publicationEvent` is the canonical publication checkpoint, and `outgoingMessage` is the complete typed message being published or retried. For background dispatch, proposed native state equals current state because dispatch changes no event content. A cancellation or retained retry can disclose a different outgoing snapshot, so hosts must approve that snapshot and its exact intent bytes independently.

The dedicated host adapter resolves approved organizer/routes and explicitly authorizes disclosure of the exact payload and full attendee roster to every recipient. It checks again before commit. The transaction uses the existing scope lock and declared coordinated or external fresh-check guarantee; configuration and runtime checks reject a required-guarantee downgrade. A fresh external check still has an after-check revocation race. Hosts claiming coordination must implement real commit/revocation coordination through the provided transaction, not just return an enum.

Background work receives `CalendarSchedulingPolicyContext` with no fabricated login. The host must freshly enforce current sender, route, publication and full detail/source-disclosure authority for the exact queued snapshot, not just check that an event exists. Route references cannot silently redirect to another calendar address. Declared guarantees and the external after-check race apply here too. No network submission occurs under the scope lock.

The reusable module exposes `CalendarModule.runSchedulingMaintenance(session)` as a trusted server entry point. Schedule bounded wake-ups on each host or run dedicated workers. The example's recurring maintenance call runs it every 15 seconds alongside existing maintenance. Correctness uses shared database leases, transaction locks and fencing, not process-local locks, caches, sticky routing or one designated host.

## Durable records and limits

Four server-only tables separate organizer binding, immutable publication, recipient delivery and delivery attempts. The publication stores a normalized snapshot and immutable ICS bytes; each recipient has a stable delivery key, route, lease/fence, attempts and outcome. Attempts distinguish acceptance, failure, uncertainty and work never submitted. Source bodies and routing/authority references are absent from ordinary responses, exports, feeds and diagnostics. The generated `schedulingStatus` API exposes origin, latest-publication identity/time, local-change indication and at most 64 authorized recipient outcomes, without raw bytes, routes or totals. Its `method` is the latest published REQUEST/CANCEL action, independent of `hasLocalChanges`; saved drafts can still differ after cancellation. The cancellation request and status-method DTO additions require generation but no new table/column or migration.

New native creates record `native` origin; create-only import records `imported`; generated migrations mark existing rows `unknown`. A null import baseline or UUID-shaped source UID proves no origin. Development storage is not automatically reset. Existing events with unknown origin can still use their ordinary APIs but cannot enter this initial organizer workflow.

Defaults are 512 KiB ICS, 64 recipients, 16 nonterminal and 256 retained publications per meeting, 10,000 nonterminal recipient deliveries per scope, 100 maintenance candidates, eight attempts, a 120-second lease, a 30-second transport timeout, exponential retry from 30 seconds capped at one hour, seven-day expiry and 30-day terminal-history retention. Options enforce finite bounds; recipient and payload ceilings cannot exceed this profile. Capacity checks are transactional and fail the whole publication, without eviction or partial recipient sets.

Cleanup removes superseded completed publications, recipient rows, attempts and receipts after retention. The latest published snapshot remains while its binding is active to compare against local edits and preserve exact retry meaning. It may retain an old title/body removed by a later local edit; it remains private. Cleanup excludes active checkpoints before limiting candidate work, so old active checkpoints cannot starve eligible cleanup.

An organizer binding blocks event deletion, conversion between recurring/non-recurring modes and source replacement/adoption. Local pattern edits within recurring mode remain allowed under native validation. There is no binding deletion/restore API yet. Ordinary local cancellation sends no CANCEL and suppresses queued REQUEST delivery. The explicit cancellation action below queues a notification. A later binding-deletion workflow must still specify minimal correlation retention and content scrubbing before it can replace the deletion restrictions.

## Submission and example behavior

Every dispatch/retry checks parent state, current publication generation, recipient authority, route binding, immutable payload validity and expiry. A cancelled native parent blocks REQUEST submission. A published CANCEL remains eligible after an ordinary local reopen; only a new explicit publication supersedes it. Newer publications supersede older work not yet submitted. Authority denial blocks delivery; unavailable checks remain retryable until expiry and send nothing. Completion uses only the current lease/fence. A dead holder's unfinished attempt becomes uncertain when another worker takes over.

`CalendarSchedulingTransport.submit` receives the stable delivery key, immutable payload and approved source/recipient routing. Its result distinguishes accepted, transient failure, permanent failure and uncertain. Adapter exceptions/timeouts are uncertain; arbitrary exception text is not stored. Receipts must be bounded opaque text. Acceptance is not receipt, display, attendee response or resource acceptance. An already submitted message cannot be recalled after a generation/authority change. Crash after external acceptance but before commit may cause duplicate delivery; the host should support idempotency using the stable key, but exactly-once transport is not promised.

The example approves only synthetic `example.invalid` addresses and derives a synthetic organizer from the active demo identity. Its transport records fixtures under ignored `.local/scheduling-mail/` and sends no email. No SMTP/MIME provider, credential, device token, FCM/APNs or real recipient is added. Production hosts replace the policy and transport; RFC 6047 MIME and trusted inbound mail remain separate reviewed work.

The Flutter event editor opens **Meeting invitations** for saved full-detail events. That screen edits text, proposes initial recipients, explicitly saves and queues publication, shows whether current saved content differs from the publication, and lists delivery outcomes. Timing follows the saved event; ordinary timing edits stay local until publication. An uncertain response retains the exact command for retry. Reload explicitly discards unsaved text and refreshes authoritative state. The screen also provides **Cancel and notify** and **Reopen and notify**. Cancellation changes saved lifecycle status while retaining saved native draft fields; it does not save unsaved form edits, and reload explicitly discards those form edits. Recipient changes remain outside the screen.

## Explicit cancellation and reopening

Under accepted [ADR 0123](adr/0123-explicit-native-organizer-cancellation.md), `calendarEvent.cancelAndNotify` accepts event UUID, expected API revision and a command UUID for an existing binding. It atomically sets native STATUS to CANCELLED and queues whole-event CANCEL for the same fixed recipients. The outgoing component comes from the last published snapshot, preserving its text/timing and UID; no unsent local content is disclosed. Saved native title, description, location and timing remain intact. The outgoing and native protocol versions advance past both prior versions with nondecreasing whole-second timestamps; overflow/capacity/authorization failures roll back all changes.

A repeat cancellation is a true authorized no-op when latest publication is CANCEL and native status is still cancelled, even if saved draft fields differ. It never implicitly resends failed delivery or publishes those draft edits. Retained exact retries return the original receipt after fresh checks, including after a newer reopening, without recancelling that newer state. Command keys cannot be reused across REQUEST/CANCEL or different input. No-op/retry checks retain independent cancellation and lifecycle authority.

An ordinary local reopen sends nothing and leaves the published CANCEL eligible. Explicit **Reopen and notify** supplies final ordinary content with active status to `saveAndNotify`, requires REQUEST publication/edit and lifecycle authority, and atomically queues a newer REQUEST. New publication generations supersede old unsubmitted work, while already submitted messages cannot be recalled. Cancellation, reopening and uncertain retries share the approved leases, stable delivery keys, capacity, retention and fencing; no additional tables or retention expansion are added.

The focused suite covers DATE/UTC/named zones, distinct native/outgoing authorization, draft privacy, permissions, rollback, retained/no-op behavior, future-clock version floors, overflow/capacity, old cancellation retries after reopening and final dispatch denial. Independent worker probes now cover both methods with actual process loss before/after synthetic acceptance; generated-client and Flutter journeys include explicit cancellation/reopening. See [validation](scaffold-validation.md) for actual commands and results. Broader phased local validation passed for this increment; final source also passed 50 focused scheduling cases and full workspace analysis.


## Recurring masters

Accepted [ADR 0124](adr/0124-recurring-organizer-masters.md) extends the same APIs and durable storage to RRULE, start-valued RDATE/EXDATE and timed PERIOD additions. A recurring event must already be saved in that mode before its first publication. Each REQUEST contains one master with its source pattern, not expanded occurrences. Existing COUNT/UNTIL, earlier inclusions, exact DATE/UTC/zone profile, nominal durations, ISO presentation and rule-specific WKST behavior remain unchanged. Wire syntax/zone/candidate/payload limits still apply.

Mode derives from actual rule/inclusion/exclusion/PERIOD properties. Empty native wrappers do not establish a recurring mode. Bound mode conversion rejects atomically through ordinary edits and publication; supported changes within recurring mode remain ordinary local drafts until explicitly published. Existing native orphan checks still preserve occurrence edits. PERIOD-only source comparison accounts for the decoder's empty recurrence wrapper without changing native content, stored source baselines or protocol versions.

Ordinary native single/future timing, content and cancellation exceptions remain editable. Any stored occurrence-component state makes a new REQUEST unavailable in this master-only increment, including reopening. The module never clears, pins or flattens those exceptions to make publication succeed. The example shows that boundary and disables a new REQUEST while saved exceptions exist. A retained exact command retry still reauthorizes and returns its original receipt without removing newer native edits.

Whole-series Cancel and notify remains available with saved exceptions. It preserves current native pattern, text, timings and complete override/protocol state, while publishing only the last master with CANCELLED status and a newer version. Both ordinary policy and the dedicated adapter receive full final native overrides; outgoingEvent remains the distinct single master. Status reports local changes when native exceptions exist, even if master fields match the publication. A local reopen sends nothing and leaves the published cancellation eligible; a new REQUEST must still satisfy the master-only boundary.

No schema, migration, public DTO or retention change is added. The existing leases, stable delivery keys, command/version checks, fixed roster and current authority checks apply to recurring masters too. Independent-process probes and generated-client/Flutter journeys now use recurring REQUEST/CANCEL masters. Focused tests cover pattern round trips, DST, PERIOD-only output, mode/orphan rejection, exception preservation and fail-closed private checkpoint decoding. The complete local root check passed, including all 506 database cases and real worker/two-host/Flutter/Web journeys; see [validation](scaffold-validation.md). Occurrence-component/instance/range scheduling, participant changes, inbound reconciliation and real mail remain required separately.


[ADR 0125](adr/0125-scheduling-occurrence-field-projection.md) approves scheduling-only projection for required inherited occurrence fields. The pure `projectIcalendarRequestFields` helper now materializes missing summary and master participant properties in a validated candidate, preserving source annotations, explicit empty values, timing, identities and versions. A later master edit affects a new projection without mutating an earlier result. Source addresses remain untrusted until independently approved by a host. The helper performs no version allocation, storage or delivery, and rejects unsupported cancellation/alarm data without stripping it. Current durable REQUEST publication still rejects stored occurrence components. Remote exception reset, occurrence versions and bundle/storage mechanics remain unapproved; ordinary canonical export stays unchanged.

The complete [ADR 0126](adr/0126-independent-occurrence-publication-versions.md) batch was subsequently approved. Its implemented scope and remaining boundaries follow below, superseding the preceding master-only restriction for supported occurrence REQUEST bundles.

## Complete occurrence REQUEST bundles

The maintainer subsequently approved the complete ADR 0126 batch. Save and notify now emits one master and up to 64 representable occurrence components in a single immutable REQUEST. Supported singles and timing-only future anchors retain exact original DATE/UTC/named-zone identity, text parameters, end/duration and recurrence meaning. Required inherited fields are projected only into outgoing components; native source versions and inheritance remain unchanged. Ordinary edits remain local. This supersedes the earlier master-only REQUEST restriction only for the supported profile.

Each outgoing occurrence has its own SEQUENCE/DTSTAMP in a private publication ledger. New/changed projected fields allocate a version at least as new as the canonical source and later than that original's previous publication; unchanged occurrences retain their exact outgoing version, even when native source version fields alone changed. A changed inherited summary advances affected inheriting occurrences; an unrelated master edit does not advance a pinned own summary. An occurrence-only publication preserves the master's scheduling version. API revisions and publication generations remain separate. True no-ops and retained command retries reauthorize without allocating versions or rewriting bytes.

Removing/retargeting a published original, replacing its single/range identity, orphaning it through a pattern change, single cancellations, future cancellation, ambiguous same-original single/future pairs and follow-series exceptions without faithful explicit timing reject the entire publication. Never invent timing or clear local edits. A local edit may remain valid while unavailable for publication until a separately designed remote reset/instance-CANCEL workflow exists. The UI permits review/submission and explains rejection; it retains saved data and offers explicit reload/retry.

The existing snapshot/projection string columns now carry bounded version-2 data, separately limited to 512 KiB alongside the existing payload cap. They retain the complete canonical publication-time snapshot, distinct outgoing source snapshot and self-contained independent version ledger. Legacy unversioned master-only snapshots remain readable without invented occurrence history. Unknown/corrupt/oversized data fail unavailable; stored payload, complete projections/versions and canonical wire representability are revalidated before use. No new table, migration, generated DTO or retention expansion is added. Latest checkpoints stay private under the existing binding/cleanup policy.

Whole-series cancellation still emits only the last published master, preserves live private drafts/overrides and advances beyond every published component and current native sequence floor. Its checkpoint retains the prior REQUEST ledger, so cleanup cannot discard reopening history. Explicit reopening retains published originals and advances every emitted component beyond the cancellation floor. Local reopen sends nothing. Cancellation status continues to report private draft differences relative to outgoing content.

The unpublished host contract intentionally changes from `authorize` to `authorizeMessage`. `CalendarSchedulingPolicyContext` supplies current/final native state, `publicationEvent` (complete canonical checkpoint), `outgoingMessage` (typed complete message), exact `intent.payload` and `payloadDigest`. Both dedicated command phases receive built candidates; ordinary preliminary authorization occurs before projection/checkpoint validation. Background checks receive retained bytes, never regenerated drafts. Hosts must authorize every component for every recipient; old master-only adapters do not compile unchanged. The example approves only its private synthetic scope/addresses. Workers retain current origin/containment/mode/authority/route/expiry/generation checks, database leases/fencing and stable keys. Provider acceptance remains separate from display/response, and uncertain retry can duplicate submission.

See [validation](scaffold-validation.md) for the actual focused, full-batch and interactive results. Instance reset/CANCEL, broader recipient/lifecycle flows, inbound reconciliation, RFC 6047 mail and external scheduling-client evidence remain first-release work.

## Retained occurrence resets

The maintainer approved the complete [ADR 0127](adr/0127-retained-occurrence-reset-projections.md) batch. Clearing a published occurrence's own timing/text can now return it to following the native series, while Save and notify explicitly publishes its current effective values under the same original identity. Later explicit publications re-project that retained original when inherited series/range values change. Ordinary local clear/inherit actions still send nothing; no native timing/content override is manufactured or pinned. Ordinary authenticated file export retains its canonical representability rules. This restores published values and does not claim to delete the recipient's exception record.

Both single and future anchors retain their exact DATE/UTC/named-zone original and single/RANGE kind. A cleared future anchor uses the current applicable original-relative shift and span form, including a surviving earlier range. Explicit end/default/nominal duration meaning stays intact; unencodable later-fold explicit ends reject rather than resolve to a different instant. Selected effective SUMMARY/DESCRIPTION/LOCATION, status/transparency and approved roster appear in outgoing reset components. Absent effective optional text becomes empty outgoing TEXT to replace old own text; canonical absent/empty values and source annotations stay separate. Applicable current annotations are retained; cleared own annotations are not resurrected.

The ledger retains every emitted original. Version-3 snapshot/comparison strings add bounded typed `projectionOriginals` markers for full-value reset materialization. The marker subset activates when published timing or own text is cleared, persists for later re-projection and also covers explicit reopening. It is separate from the full retained identity set; unchanged ordinary first publications keep their no-op behavior. Readers reconstruct the immutable message from the outgoing canonical snapshot and markers, checking bounds, UID/parent, profile/kind/membership and body correspondence. Legacy/v2 snapshots remain readable without fabricated reset markers. Snapshot/projection/payload limits, retention and independent component versions remain unchanged; no schema/model/endpoint/migration or development reset is needed.

At most 64 distinct native/retained occurrence identities can be emitted. Resetting an original does not free its publication slot while the binding is active. Repeated creation/reset of different originals can therefore exhaust this profile and fail explicitly; the module never evicts a published identity. Excluding/removing original membership, changing its kind/profile, native individual cancellations, and first publication of new unrepresentable content-only exceptions remain unsupported and reject atomically. Cancellation/reopening/cleanup keep the self-contained marker/version ledger and current floors. Instance CANCEL, binding cleanup/remote deletion and broader historical synchronization remain separate.

Complete host approval still distinguishes canonical current/final/publication state from outgoing projected fields and immutable bytes/digest. Native override absence stays visible to the host even when the outgoing message has explicit reset components. The example uses existing clear/inherit actions followed by explicit publication; two-host, worker and Flutter tests exercise reset behavior. See validation for actual commands/results; synthetic transport establishes no external-client or real-mail interoperability.

## Historical single-occurrence cancellation

The maintainer approved the complete [ADR 0128](adr/0128-explicit-single-occurrence-cancellation.md) batch on 2026-10-27. `calendarEvent.cancelOccurrenceAndNotify` accepts an event UUID, expected API revision, command UUID and point-only original timing. It proves membership against the retained published REQUEST, including RRULE/RDATE/PERIOD/EXDATE. DATE/UTC/named-zone identity and exact zone spelling are retained. Range anchors reject; a later original governed by an earlier range is supported.

The minimal detached CANCEL contains UID, RECURRENCE-ID without RANGE, independent newer SEQUENCE, whole-second UTC DTSTAMP, approved organizer/fixed attendees and STATUS:CANCELLED. A named original includes the pinned VTIMEZONE. No SUMMARY/DESCRIPTION/LOCATION, DTSTART/end/duration, recurrence or alarm is disclosed. Newer local drafts are not a source of outgoing fields. Exact current profile/membership permits the usual native single-cancellation flag while preserving replacement timing/content. A removed/excluded/profile-changed original leaves native content/overrides/protocol versions intact. Work/coverage failures reject instead of implying absence. Each new accepted command advances API revision/audit/scope generation; native protocol state advances only for an actual native change.

The binding's existing global generation fence requires every earlier delivery to be terminal before queueing a new partial cancellation. Otherwise the command fails `dependencyConflict` atomically. Exact command retries and synchronized no-ops reauthorize without queueing or changing revisions; an old retained retry never recancels restored local state. If retention pruned an earlier receipt, the latest self-contained checkpoint proves a no-op and supplies its unchanged receipt; the requested cancellation is still authorized independently. A new command after explicit local restore reapplies the flag with a newer outgoing version. Whole-series cancellation may supersede pending instance work, uses a floor above all retained components/cancellations and preserves the ledger.

REQUESTs retain validated v3 checkpoints. Version-4 cancellation envelopes embed the complete validated REQUEST basis, canonical current snapshot and bounded typed cancellation/version ledger; whole-series CANCEL also retains its own validated master-message checkpoint. Nested v4 bases reject. Cleanup can delete superseded rows without losing the active basis/history or growing a recursive chain. Legacy/v2/v3 readers remain supported; no earlier cancellation history is fabricated. Snapshot/comparison/payload caps remain 512 KiB each, and active/reset/cancelled originals share 64 slots with no eviction. No table, column, migration, dependency or development reset is added.

`CalendarSchedulingView.publicationKind` distinguishes request/seriesCancel/occurrenceCancel, with optional `originalStart` and `hasOccurrenceCancellations`. Local-change comparison uses the published basis plus known native cancellation flags, never the private draft snapshot as proof of publication. Independent `cancelOccurrenceScheduling`, scheduling-read/full event/source and lifecycle permissions apply even without native mutation. Trusted intent/context adds kind/target, `publishedRequest` and `exactNativeMatch`; dispatch recomputes current membership while authorizing immutable historical bytes. Both command phases and workers retain complete host approval, fixed route checks, leases/fences, expiry and stable retry keys.

The example provides explicit original profile/date/time/zone controls and explains pending delivery conflicts. It preserves exact uncertain commands until retry/reload. Individual restore is unavailable: ordinary native restore is local, and new Save/Reopen and notify rejects while published individual cancellations remain. Whole-series Cancel remains available. Range cancellation, parallel partial-message coordination, broader lifecycle/inbound reconciliation, mail and external-client evidence remain separate. See [validation](scaffold-validation.md) for commands and results.

## Proposed individual restoration

The maintainer confirmed restoring the last published occurrence values while preserving newer unpublished drafts. [ADR 0129](adr/0129-explicit-occurrence-restoration.md) proposes a separate explicit action and authority, one detached versioned REQUEST, exact native flag removal only, terminal-prior-delivery gating and a self-contained v5 ledger in existing columns. Restored originals would retain full-value publication markers and independent versions, allowing a complete Save and notify only after no individual cancellations remain and all proposed current memberships/profiles validate. The master version would come from its ledger entry rather than the latest partial row. The first proposed scope rejects a cancelled native/published master instead of silently reopening it. These mechanics require review; current runtime still blocks new REQUEST/reopen while individual cancellations remain. No model source, generated code, migration or restoration endpoint is added by this proposal.
