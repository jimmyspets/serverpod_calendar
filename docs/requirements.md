## User journey and scope

Target Serverpod 4.x and later; pin compatible Dart, Flutter, and Serverpod SDK versions during scaffolding and verify supported versions.

The primary product is a reusable Serverpod module; host Flutter clients provide most GUI through generated Dart client APIs. Core calendar/task/scheduling/availability behavior is independent of external subscription-client limitations. External feeds expose a declared subset rather than the full module model. A host application supplies authentication, users, groups, membership and authorization. A developer integrates the module, associates calendars with external users, groups, rooms, venues or equipment, creates timed, all-day, zoned, and recurring events, and manages read-only subscription URLs. A subscriber adds a URL to Apple Calendar on iOS, Google Calendar, or Microsoft Outlook. A URL may publish one calendar or combine several. Changes appear on a later client refresh; revoking one URL stops future server access through that URL without disabling other URLs.

The first release includes authenticated calendar/event/task CRUD, durable storage, bounded queries and availability search across lists of people/resources, supported iCalendar import/export, feed management, external subject integration, and free/busy queries showing available or booked intervals for users and resources. The first release also includes availability-rule management/calculation (RFC 7953), iTIP event/free-busy scheduling (RFC 5546) and inbound/outbound email using the restricted iMIP-compatible profile under [ADR 0015](adr/0015-restricted-imip-profile.md), with component hint support and S/MIME signatures/encryption deferred. Complete RFC 6047 conformance is not selected; host-verified scheduling authority is still required, otherwise ingress rejects/quarantines without mutation or automatic reply. Calendar/feed descriptions use a defined RFC 7986 metadata profile. Include alarm definitions, durable due-occurrence execution and a connected-client notification example using Serverpod server events/streaming. Provider-specific iOS/Android delivery remains outside repository implementation scope. Proposed ownership keeps calendar timing/state in this module, generic delivery/device/provider concerns in a reusable notification service, and platform presentation in Flutter. Review exact RFC 9074 action/privacy semantics and advanced features separately; see ADR 0009. Host adapters supply verified calendar addresses, email ingress/delivery and scheduling authorization. Native task management and a defined standalone VTODO interchange profile are first-release scope. All VTODO iTIP methods and inbound/outbound iMIP task scheduling mail are deferred under [ADR 0011](adr/0011-defer-vtodo-scheduling.md); reject/quarantine unsupported scheduling without mutation or automatic replies and reject outbound task scheduling before queueing. Native task assignments and task alarms/notifications remain in scope. CalDAV, general upstream synchronization, proximity/advanced notification actions and a standalone reusable UI package remain separate scope; host Flutter GUI integration is required. The module does not store user/group profiles, credentials, or membership lists.

Only the Gregorian calendar system is supported across native services and supported interchange. Accept CALSCALE:GREGORIAN or omitted CALSCALE (Gregorian default); reject other systems and non-Gregorian recurrence extensions explicitly before mutation, without automatic conversion. Host extensions cannot bypass this restriction. Time zones and supported language/display metadata remain separate; see [ADR 0013](adr/0013-gregorian-only.md).

The example host/Flutter app is also the automated integration-test application, using the actual module, generated client and migrations. The module must support more than one concurrently active Serverpod instance against shared logical storage. [ADR 0018](adr/0018-automated-example-and-multiple-instances.md) records required evidence and proposed coordination boundaries; implementation remains pending.

## Confirmed RFC 5545 metadata choices

During the property review, the maintainer selected URI-only ATTACH links to host-managed files, searchable free-form event/task CATEGORIES with host validation, and CLASS labels with host-controlled disclosure/masking. The next batch confirmed editable plain-text COMMENT notes on events/tasks, editable event GEO coordinates with host/Flutter maps/address lookup, and descriptive event RESOURCES labels independent of host-managed resource links or bookings. A third batch confirmed TZNAME display-label preservation/export, TZURL URI metadata with no automatic retrieval, and import-preserved CONTACT text only, without native contact creation/editing. Batch 4 confirmed native/interchange basic RELATED-TO parent/child/sibling relationships, editable event/task URL links without retrieval, and capped automatic REPEAT alarms with configurable count/interval limits. Richer relationships and alarm identity/acknowledgement/snooze are selected in RFCs 9253/9074; numeric, lifecycle and expiry constraints remain implementation decisions. Batch 5 confirmed an explicit supported-property allowlist for IANA extensions, host-configured allowlist/validation for X-properties, and ALTREP URI metadata with ordinary text retained and host-owned retrieval/rendering. These policies do not approve unknown extension semantics. Batch 6 confirmed native/interchange CN participant/organizer display names, standard CUTYPE participant types with host-validated mappings, and host-authorized meeting participation delegation through DELEGATED-FROM/DELEGATED-TO. Names/types never establish identity or reserve resources; delegation never transfers ownership or grants calendar access. SENT-BY was subsequently confirmed in batch 8; iTIP task methods remain separate. Batch 7 confirmed DIR directory-reference URI preservation/export without lookup or identity import, validated native/interchange FMTTYPE media-type metadata on file links without content fetching/inspection, and native/interchange LANGUAGE tags in supported text/name contexts. Translation and multilingual presentation stay with host/Flutter; RFC property cardinality still applies. Batch 8 confirmed native/interchange MEMBER metadata with host validation, RANGE=THISANDFUTURE edits preserving occurrence identity and recalculating bookings/alarms, and native actions/scheduling interchange for host-verified SENT-BY authority. Imported claims never prove membership or authority, expand invitees or grant access. Arbitrary recurrence-pattern changes require separate series-edit rules. Batch 9 confirmed bounded hourly/minutely event recurrence and BYHOUR/BYMINUTE support under RFC combination rules, while deferring FREQ=SECONDLY and BYSECOND. Ordinary timestamps retain seconds; occurrence rules do not guarantee exact job/push timing. Numeric budgets and task recurrence semantics remain separate, and limits must never silently produce incomplete availability as free. Batch 10 confirmed bounded native/interchange BYYEARDAY, BYWEEKNO and BYMONTH support, respecting RFC combinations, leap years and week/year boundaries. Fiscal/school-week calendars are outside this choice; numeric limits and task recurrence semantics remain separate. Batch 11 confirmed bounded native/interchange BYSETPOS and all WKST week-start values, defaulting to Monday when omitted. Holiday/business-day calculation and Flutter week layout remain separate. All explicitly Undecided RFC 5545 matrix rows have now been reviewed; the maintainer subsequently promoted all Proposed RFC matrix rows to Yes — planned in the RFC tables; detailed policies still require implementation review. Embedded binary attachments are excluded. Labels never override host calendar permissions or automatically publish data; attachment content/storage/access stay with the host. Exact defaults, limits, field projections and unasked parameters remain open. See [ADR 0010](adr/0010-rfc5545-property-decisions.md) and the [property matrix](rfc/rfc-5545.md).

## Shared RFC 7953 profile

Apply the selected RFC 5545 metadata, host disclosure/validation, no-fetch URI, import-only CONTACT, allowlist, bounded recurrence and atomic/no-loss principles to legal RFC 7953 contexts under [ADR 0012](adr/0012-calendar-availability-policy.md). Availability starts/ends use UTC or zoned DATE-TIME; date-only/floating forms and event/task-only properties or nested alarms are not enabled. Keep PRIORITY/BUSYTYPE semantics specific to availability. The maintainer subsequently selected a per-calendar no-applicable-rule setting defaulting to unbooked time free, separate calendar results and authenticated-only raw rule APIs/import/export under [ADR 0012](adr/0012-calendar-availability-policy.md). An unavailable fallback is the proposed alternative setting; no setting overrides applicable rules/bookings or makes unknown coverage free. Raw definitions are excluded from bearer feeds. Optional person/resource summaries use host-selected contributing calendars and combine their blocking bookings without merging calendar results. Admin-only associations do not imply contribution, and summary access does not imply calendar-detail access. Summary free time requires every contributor to be free after independently applying its rules, fallback and bookings with complete coverage; no cross-calendar union or priority override. Common-free search intersects resulting subject availability; native rule management/interchange and calculated free/busy/search stay required.

## RFC 9253 relationship metadata review

The next batch selected native/interchange LINK UID and URI targets with explicit scope, independent target authorization and correct source/publication UID mapping; XML-REFERENCE is deferred and rejected explicitly. URI metadata is not fetched and must not leak private identifiers or subscription credentials. The following batch confirmed host-approved LINKREL allowlists, editable LINK labels/target language/declared media types and authorized cross-calendar links. Source/target authorization and disclosure remain independent; no access inheritance, private target/credential leakage or cascade deletion. Relations are metadata unless explicitly implemented. The next batch confirmed legal RELATED-TO UID/URI extensions with UID hierarchy targets retained, authorized REFID/CONCEPT group references and validated FIRST/NEXT ordering with bounded traversal. No workflow, recurrence-master inference, rescheduling or cascade deletion is added. LINK UID targets stay within one declared collection; cross-collection links use authorized URI targets. The final RFC 9253 batch confirmed all four temporal dependency relations, bounded signed GAP intervals and DEPENDS-ON as native/interchange metadata with authorization/validation. They do not automatically move dates, block task transitions, propagate status, reserve time, calculate working days/holidays or execute workflows. All RFC 9253 Undecided rows are resolved; XML references remain deferred and detailed graph/reference/limit policies and implementation remain pending.

## Subscription HTTP review

The maintainer selected an ETag-only initial HTTP feed contract, deferring Last-Modified/If-Modified-Since/If-Unmodified-Since and byte-range/partial responses. Subscription URLs serve fixed text/calendar output rather than negotiated JSON/XML. Preserve normal GET/HEAD/If-None-Match/304 and current publication authority checks; ICS LAST-MODIFIED metadata remains independent. See [ADR 0016](adr/0016-subscription-http-profile.md). The next batch selected If-Match handling in the feed adapter (strong comparison, RFC precedence and 412 on failure after authority checks), optional host-declared intended-audience Content-Language and deferred subscription redirects. Native revisions/per-property LANGUAGE remain distinct; no language negotiation, login redirect or replacement-credential exposure. The final batch selected explicit privacy-safe 400/405/429/503/500 errors, retaining opaque credential 404 and If-Match 412. Every error/denial uses Cache-Control: no-store with no negative-response caching. Successful responses use Cache-Control: private, no-cache, max-age=0, must-revalidate; omit proxy-revalidate and Expires initially. Failures never appear as empty successful feeds or 304; cache policy does not erase downloaded data or control polling. All listed RFC feature rows now have selected statuses; detailed constraints and implementation remain pending.
