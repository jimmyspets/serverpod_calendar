## User journey and scope

Target Serverpod 4.x and later; pin compatible Dart, Flutter, and Serverpod SDK versions during scaffolding and verify supported versions.

The primary product is a reusable Serverpod module; host Flutter clients provide most GUI through generated Dart client APIs. Core calendar/task/scheduling/availability behavior is independent of external subscription-client limitations. External feeds expose a declared subset rather than the full module model. A host application supplies authentication, users, groups, membership and authorization. A developer integrates the module, associates calendars with external users, groups, rooms, venues or equipment, creates timed, all-day, zoned, and recurring events, and manages read-only subscription URLs. A subscriber adds a URL to Apple Calendar on iOS, Google Calendar, or Microsoft Outlook. A URL may publish one calendar or combine several. Changes appear on a later client refresh; revoking one URL stops future server access through that URL without disabling other URLs.

The first release includes authenticated calendar/event/task CRUD, durable storage, bounded queries and availability search across lists of people/resources, supported iCalendar import/export, feed management, external subject integration, and free/busy queries showing available or booked intervals for users and resources. The first release also includes availability-rule management/calculation (RFC 7953), iTIP event/free-busy scheduling (RFC 5546) and inbound/outbound email using the restricted iMIP-compatible profile under [ADR 0015](adr/0015-restricted-imip-profile.md), with component hint support and S/MIME signatures/encryption deferred. Complete RFC 6047 conformance is not selected; host-verified scheduling authority is still required, otherwise ingress rejects/quarantines without mutation or automatic reply. Calendar/feed descriptions use a defined RFC 7986 metadata profile. Include alarm definitions, durable due-occurrence execution and a connected-client notification example using Serverpod server events/streaming. Provider-specific iOS/Android delivery remains outside repository implementation scope. Proposed ownership keeps calendar timing/state in this module, generic delivery/device/provider concerns in a reusable notification service, and platform presentation in Flutter. Review exact RFC 9074 action/privacy semantics and advanced features separately; see ADR 0009. Host adapters supply verified calendar addresses, email ingress/delivery and scheduling authorization. Native task management and a defined standalone VTODO interchange profile are first-release scope. All VTODO iTIP methods and inbound/outbound iMIP task scheduling mail are deferred under [ADR 0011](adr/0011-defer-vtodo-scheduling.md); reject/quarantine unsupported scheduling without mutation or automatic replies and reject outbound task scheduling before queueing. Native task assignments and task alarms/notifications remain in scope. CalDAV, general upstream synchronization, proximity/advanced notification actions and a standalone reusable UI package remain separate scope; host Flutter GUI integration is required. The module does not store user/group profiles, credentials, or membership lists.

Only the Gregorian calendar system is supported across native services and supported interchange. Accept CALSCALE:GREGORIAN or omitted CALSCALE (Gregorian default); reject other systems and non-Gregorian recurrence extensions explicitly before mutation, without automatic conversion. Host extensions cannot bypass this restriction. Time zones and supported language/display metadata remain separate; see [ADR 0013](adr/0013-gregorian-only.md).

The example host/Flutter app is also the automated integration-test application, using the actual module, generated client and migrations. The module must support more than one concurrently active Serverpod instance against shared logical storage. [ADR 0018](adr/0018-automated-example-and-multiple-instances.md) records required evidence and proposed coordination boundaries; implementation remains pending.

## Native ISO week convention

The maintainer requires ISO 8601 week numbering and Monday as the first day for native calendars. Week 1 is the week containing January 4, equivalently the first Thursday; weekday numbers run Monday 1 through Sunday 7. Display the ISO week-year, which can differ from the Gregorian year at New Year. Device locale must not change this convention. The current recurrence default is Monday; explicit WKST values, including non-Monday starts, must be honored for recurrence and its week-number calculations without changing native presentation. The core now exposes `IsoWeekDate.fromDate` under [ADR 0034](adr/0034-native-iso-week-fields.md); Flutter calendar layout remains pending. See [the behavior and examples](week-conventions.md) and [ADR 0032](adr/0032-iso-week-convention.md).

## Native calendar precision and supported dates

The maintainer selected **whole seconds** and ordinary dates in **[1970-01-01, 2100-01-01)** under [ADR 0041](adr/0041-whole-second-1970-2100-profile.md). This supersedes earlier microsecond and broad date ranges. No rounding/truncation is permitted. Supported non-ICS input formats may use all-zero fractional spellings; future ICS adapters must enforce RFC 5545 lexical grammar separately. Audit/processing timestamps are independent of calendar precision.

The explicit 2100-01-01 midnight boundary exists only for exclusive event/query ends, allowing all of 2099-12-31. It is not a start, RDATE/EXDATE or task date. Necessary UTC conversion spillover in 1969/2100 is calculation padding, not broader canonical storage. The initial generated profile keeps timezone 0.11.2 / IANA 2026e and calculates future transitions through the horizon. Unknown offsets fail; future rule changes require a data update and dependent-state recalculation. See [timezone data maintenance](timezone-data.md).

Unit-preserving durations retain calendar-first application and existing event/task positivity/cardinality rules. UTC/zoned/DATE recurrence, spans and timing edits retain their selected semantics. Alarm policy, durable upgrades, generated storage, service integration, parsing/serialization and client interoperability remain separate implementation/review work. Unpublished API changes may break earlier callers/tests; no production data migration is required.

## Shared RFC 7953 profile

Apply the selected RFC 5545 metadata, host disclosure/validation, no-fetch URI, import-only CONTACT, allowlist, bounded recurrence and atomic/no-loss principles to legal RFC 7953 contexts under [ADR 0012](adr/0012-calendar-availability-policy.md). Availability starts/ends use UTC or zoned DATE-TIME; date-only/floating forms and event/task-only properties or nested alarms are not enabled. The maintainer subsequently selected a per-calendar no-applicable-rule setting defaulting to unbooked time free, separate calendar results and authenticated-only raw rule APIs/import/export under [ADR 0012](adr/0012-calendar-availability-policy.md). An unavailable fallback is the proposed alternative setting; no setting overrides applicable rules/bookings or makes unknown coverage free. Raw definitions are excluded from bearer feeds. Optional person/resource summaries use host-selected contributing calendars and combine their blocking bookings without merging calendar results. Admin-only associations do not imply contribution, and summary access does not imply calendar-detail access. Summary free time requires every contributor to be free after independently applying its rules, fallback and bookings with complete coverage; no cross-calendar union or priority override. Common-free search intersects resulting subject availability; native rule management/interchange and calculated free/busy/search stay required.

## Subscription HTTP review

The maintainer selected an ETag-only initial HTTP feed contract, deferring Last-Modified/If-Modified-Since/If-Unmodified-Since and byte-range/partial responses. Subscription URLs serve fixed text/calendar output rather than negotiated JSON/XML. Preserve normal GET/HEAD/If-None-Match/304 and current publication authority checks; ICS LAST-MODIFIED metadata remains independent. See [ADR 0016](adr/0016-subscription-http-profile.md). The next batch selected If-Match handling in the feed adapter (strong comparison, RFC precedence and 412 on failure after authority checks), optional host-declared intended-audience Content-Language and deferred subscription redirects. Native revisions/per-property LANGUAGE remain distinct; no language negotiation, login redirect or replacement-credential exposure. The final batch selected explicit privacy-safe 400/405/429/503/500 errors, retaining opaque credential 404 and If-Match 412. Every error/denial uses Cache-Control: no-store with no negative-response caching. Successful responses use Cache-Control: private, no-cache, max-age=0, must-revalidate; omit proxy-revalidate and Expires initially. Failures never appear as empty successful feeds or 304; cache policy does not erase downloaded data or control polling.
