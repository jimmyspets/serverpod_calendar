# Single-instance source application after range restoration

Accepted [ADR 0167](adr/0167-single-instance-applications-after-source-range-restoration.md) extends explicit single REQUEST/CANCEL application after [source restoration](source-range-restoration.md) and [master lifecycle](restoration-master-lifecycle.md). Receiving/reviewing a message still changes no calendar and sends no reply.

A new single command requires an active accepted master, no native cutoff, a clean complete accepted series and exact original/profile/membership. Other single/future components, individual cancellations and source versions remain intact. Existing bounded source profiles apply; same-anchor single/range collisions reject explicitly. A whole-cancelled master must reopen before a pending instance can be applied; current intake already rejects new instance notices for that inactive basis.

Freshness uses the effective canonical component: exact single, then applicable range, then master. Historical restoration did not rewrite those versions, so its SEQUENCE is not a global single-message floor. A new single may have a lower sequence than the historical restoration while still being fresh for its component. Whole-series CANCEL retains its separate conservative floor over current master/components and both historical cancellation/restoration versions. Source clocks and omissions remain exact.

The first new single supersedes the restoration retry receipt, as explicitly selected by the maintainer. Evidence stays frozen privately, but retrying that older command rejects without mutation. Further occurrence commands follow the same latest-only rule. Master changes preserve the current latest occurrence receipt; the latest master receipt remains separate. Retained current retries reauthorize and never reapply over newer local drafts/notices.

Existing checkpoint JSON v10 stores the current target ledger, latest request/receipt and current kind/composition bindings beside one unchanged frozen v7 acceptance/baseline/nullable-master descriptor. It does not nest v8/v9/v10 or copy another complete historical event snapshot. Historical replay shares the same strict validation as v8/v9; current target/source/component and composition validation shares the existing legacy validator with a separate v10 receipt namespace. Minimal CANCEL retains current canonical timing/content rather than claiming that its source proves past values. Missing/contradictory/tampered proof fails unavailable without fallback or read-time upgrades.

Every persisted byte, including historical/current duplication, counts against existing 4 MiB/link, 16 MiB/recipient, 64 MiB/scope ceilings and configurable lower limits. Current targets plus one range-history slot cannot exceed 128. Existing work/source limits and deletion scrubbing apply. No SQL, generated model/endpoint signature, dependency or cap expansion is added.

Source/link/raw-read, occurrence action, native import/replacement/update/lifecycle and accepted-occurrence/cancellation/restoration composition authority remain independent. Previews check applicable rights; writes and retries recheck preliminary/final immutable context. Historical and current source bodies are authorized by actual IDs even after queue pruning. Private evidence grants no authority.

Native component/baseline/checkpoint changes, revision/time, selected notice dismissal and scope/feed/alarm invalidation commit atomically. Parent metadata time, personal actions and accepted-firing deduplication remain independent. Master updates preserve the current ledger and historical restoration original; orphan/profile changes reject. Master cancellation/reopening keeps the cutoff clear and individual cancellations intact. Existing export/feed representability guards remain, including no stale 304 for unsupported state.

The example's fixed single fixture now selects its PERIOD original on January 5, independently of the January 3 range anchor. Endpoint signatures are unchanged; module tests retain same-anchor collision coverage. Existing Flutter controls expose explicit single application and explain latest-only retries versus retained history. New range transitions, other scheduling methods and real mail remain separate. See [actual validation](scaffold-validation.md).
