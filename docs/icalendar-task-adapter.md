# Standalone VTODO adapter

The pure `serverpod_calendar_icalendar` package now parses, validates and reserializes a bounded standalone VTODO master profile under [ADR 0088](adr/0088-vtodo-wire-master-implementation.md), extended with progress-only occurrence components under [ADR 0090](adr/0090-vtodo-occurrence-component-implementation.md) and the confirmed [ADR 0089 contract](adr/0089-vtodo-occurrence-component-contract.md), plus text/link metadata under [ADR 0091](adr/0091-vtodo-text-and-link-metadata.md) and inert source participants under [ADR 0092](adr/0092-vtodo-source-participants.md), plus unresolved references under [ADR 0093](adr/0093-vtodo-source-references.md) and unarmed DISPLAY alarm definitions under [ADR 0094](adr/0094-vtodo-display-alarm-source-profile.md), following the confirmed source-progress choice in [ADR 0087](adr/0087-vtodo-wire-master-contract.md). It does not import into module storage, change native task progress, assign users, publish HTTP feeds, send scheduling messages or activate alarms. Native [recurring task progress/history](recurring-tasks.md) is a separate service.

## Supported profile

Require one strict VCALENDAR with VERSION 2.0, nonempty PRODID, optional Gregorian CALSCALE and at least one VTODO. UID and UTC DTSTAMP are required once per component. Duplicate masters for one exact UID reject; occurrence components share their master's UID and require a distinct exact original RECURRENCE-ID. Source UID is text, independent of native UUID/authority. Multiple bounded masters and necessary VTIMEZONE components are supported; mixed component calendars reject in this adapter.

| Properties | Supported meaning |
| --- | --- |
| DTSTART, DUE, DURATION | Undated, start-only or due-only tasks; DATE, UTC or named-zone milestones. Positive duration requires start and excludes DUE. Preserve explicit due versus duration units; no inferred deadline or occupied interval. |
| SUMMARY, DESCRIPTION, LOCATION | Optional decoded text with scoped LANGUAGE/ALTREP; preserve absence, spelling and annotations. Links are never fetched. Limits are 4,096/16,384/4,096 code points respectively. |
| PRIORITY | Optional source integer 0–9; preserve explicit zero versus absence. |
| STATUS | Optional NEEDS-ACTION, IN-PROCESS, COMPLETED or CANCELLED. |
| PERCENT-COMPLETE | Optional source integer 0–100, independent of status/completion-property presence. |
| COMPLETED | Optional explicit whole-second UTC completion value, independent of status/percentage-property presence. |
| CREATED, LAST-MODIFIED, SEQUENCE | Optional source checkpoints/omissions; no freshness or authority inference and no invented timestamps. |
| RRULE, RDATE, EXDATE | Bounded recurring masters requiring an explicit start, using the existing typed recurrence profile and start-only inclusion/exclusion values. |
| CLASS, URL | Optional source classification and absolute HTTP/HTTPS representation link; no access grants or fetching. |
| CATEGORIES, COMMENT, CONTACT | Repeated source groups with scoped annotations; no contact directory or inferred host associations. |
| ORGANIZER, ATTENDEE | Source calendar addresses/claims, independent of host identities, native assignments and task progress; no messages/actions. |
| RELATED-TO, ATTACH | Unresolved basic source UID relationships and inert URI-only file references with optional declared media type. |
| VALARM | Unarmed DISPLAY-only source definitions with relative/absolute trigger, bounded paired repeats and optional UID/ACKNOWLEDGED. No recipients, actions or delivery. |
| VTIMEZONE | Exact case-sensitive names/aliases and full supported-horizon agreement with the pinned IANA data, reusing existing zone validation. |

STATUS, PERCENT-COMPLETE and COMPLETED stay **independently optional**. The adapter does not fill in 100 percent, a current completion time or NEEDS-ACTION, and does not apply native completion/reopen constraints to source fields. It validates the fields individually without reconciling them into native progress or claiming a conflicting source combination is consistent. No historical transition is synthesized from COMPLETED. The database import mapping remains a separate design. See [RFC 5545 §3.6.2](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.6.2), [§3.8.1.8](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.1.8) and [§3.8.2.1](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.2.1).

Ordinary milestone/checkpoint values use whole seconds in [1970-01-01,2100-01-01). **DUE and effective due cannot use the exclusive event-end exception at 2100.** Floating times, mixed DATE/timed or differing named-zone profiles, invalid chronology, nonpositive durations and out-of-profile effective due reject. This bounded profile rejects some legal RFC combinations; these are application limits, not new RFC prohibitions. Nonzero/zero lexical fractions in iCalendar DATE-TIME are rejected by its strict whole-second grammar; native DateTime values with zero fractional fields are a separate input form.

Recurrence preserves explicit WKST and its rule-specific week grouping/numbers; native ISO presentation remains separate. Canonical core sets sort/deduplicate selections while source spelling/grouping remains in the retained syntax. Earlier RDATE additions are retained without changing rule COUNT; EXDATE wins. Generated nonexistent named-zone times follow the existing skip policy, with explicit values using the selected RFC gap/fold handling. Due projection uses task milestones, preserving nominal duration versus elapsed explicit due. Undated source tasks have no invented daily recurrence anchor.

## Progress-only occurrence components

Each override requires its exact matching master in the same file, even if it appears before that master. RECURRENCE-ID identifies an original member of the master's recurrence set, never a completion timestamp. Excluded, absent, duplicate or differently profiled originals reject the whole file. Exact named-zone identity matters even when another representation has the same instant. Generated gap times are absent unless separately included by the supported explicit-date rules. See [RFC 5545 §3.8.4.4](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.4.4).

Omitted timing, text and priority inherit only in the linked projection. Raw properties retain their absence for reserialization. Explicit repetitions must match the projected start/deadline and text annotations; explicit priority 0 may match an absent master priority's undefined meaning. Equivalent supported DUE/DURATION forms retain their source form when the actual projected deadline agrees. A DURATION still requires DTSTART in that source component. Compare timed deadlines as instants, including DST folds; a repeated clock label that selects the wrong fold rejects.

STATUS, PERCENT-COMPLETE and COMPLETED may differ independently and remain independently optional on each component. Checkpoints are independent too. No effective native progress, 100-percent default, retrospective history or assignment is inferred. A consumer reads raw source progress from `linked.component`; the adapter intentionally supplies no reconciled progress getter. Explicit timing/content changes, recurrence generators on overrides and all RANGE parameters remain unsupported.

Validate retained original targets with one aggregate generation per master and the shared file-wide recurrence work budget. No per-override fresh full budget or partial success is allowed. Serialization retains original component order and source presence; `tasks` contains masters only and `series` links the occurrence components.

## Text and link metadata

Preserve CATEGORIES groups separately, including exact text spelling, duplicate values, property order and per-group LANGUAGE. Each value follows the existing nonblank/single-line 256-code-point profile, with at most 64 values across a component's groups. COMMENT and CONTACT retain separate decoded text properties and legal LANGUAGE/ALTREP annotations; each supports at most 32 properties and 4,096 code points per text. CONTACT is source-preserved data, with no native create/edit or contact lookup feature. Category text never implies ownership, permissions or native search implementation.

URL uses the existing bounded absolute HTTP/HTTPS profile without user information, at most 4,096 characters. It is a representation link, never a secret feed credential, and is not fetched. COMMENT/CONTACT ALTREP uses the existing absolute URI annotation validator, not the narrower URL scheme profile; those URIs also remain inert. CLASS accepts PUBLIC/PRIVATE/CONFIDENTIAL with canonical token projection and original source spelling retained. Preserve omitted CLASS; its RFC default PUBLIC may match explicit PUBLIC on an override without inserting it on the master. Unknown classification tokens reject in this bounded profile; the RFC also permits extensions. Host policy, rather than CLASS alone, enforces disclosure. See [RFC 5545 classification](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.1.3).

Omitted occurrence metadata inherits in `linked.metadata`; explicit URL/classification and complete repeated lists must match the master. Preserve group boundaries/order and annotations when matching. Partial lists, regrouping and changed values reject until content exceptions are supported. Raw `linked.component.metadata` retains its own omissions and explicit repetitions. All decoded values and annotations charge the file-wide task metadata budget. No unprofiled parameter is silently removed.

## Inert source participants

ORGANIZER and ATTENDEE are source calendar-address claims, **not native assignments or trusted identities**. Importing or reading them grants no access, proves no membership/delegation/SENT-BY authority, expands no groups and sends no messages. A later mapping to host identities requires a separate authorized action. METHOD still rejects; this does not implement VTODO iTIP/iMIP, native participant editing or scheduling. Source participants may describe a group-scheduled entity without executing its scheduling workflow.

`task.participants` retains an optional organizer and source-ordered attendees, including duplicates and exact address spelling. Organizer accepts CN/LANGUAGE/DIR/SENT-BY. Attendees additionally accept CUTYPE/ROLE/PARTSTAT/RSVP and ordered MEMBER/DELEGATED-TO/DELEGATED-FROM address lists. Each parameter may appear once; only those three list parameters may have multiple values. A master with attendees requires an organizer. An occurrence may inherit the same-file master's organizer, while all explicit participant state must match the master. Matching includes complete ordered attendee lists, exact addresses and decoded parameter presence/values; token case is insignificant. Even a redundant explicit default parameter rejects when absent on the master under this initial matching profile. Participant-state differences, including attendee PARTSTAT, remain content exceptions rather than the three supported task-progress fields.

Preserve absent optional parameter values separately from named `effectiveCalendarUserType`, `effectiveRole`, `effectiveParticipationStatus` and `effectiveRsvp` getters. Their defaults are INDIVIDUAL, REQ-PARTICIPANT, NEEDS-ACTION and false. Unknown well-formed CUTYPE/ROLE/PARTSTAT tokens retain source text and use UNKNOWN/REQ-PARTICIPANT/NEEDS-ACTION fallbacks. All seven task PARTSTAT values are supported, including COMPLETED and IN-PROCESS, without changing the task's independent STATUS/PERCENT-COMPLETE/COMPLETED or creating completion history. See [RFC 5545 participant parameters](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.2.12).

Use the existing absolute ASCII URI/no-userinfo validator, with at most 1,024 characters per calendar address. These are syntactic addresses, not verified deliverable mailboxes; opaque URI schemes can remain source data. CN supports 4,096 code points; LANGUAGE requires CN and an existing well-formed tag. DIR uses the existing 4,096-character absolute URI profile, with no lookup. Token values support at most 64 ASCII alphanumeric/hyphen characters. RSVP accepts TRUE/FALSE only. Cap each component at 64 attendees and each list parameter at 16 addresses; charge all decoded participant values/annotations against the shared task metadata budget. Reject malformed/duplicate/unknown parameters and limit exhaustion for the whole file. Host storage and native identity mapping remain separate.

## Unresolved relationships and inert attachments

RELATED-TO preserves a nonempty decoded text UID target and optional PARENT/CHILD/SIBLING RELTYPE; absence stays absent with `effectiveRelationType` PARENT. Keep exact UID spelling, duplicate entries and source order. Do not look up targets, create native graph edges, propagate permissions, reschedule dependencies or cascade deletes. Forward, missing, self and cyclic source references may be retained as data. Native graph validation, independent target access, scope checks and source/publication UID mapping remain separate. Extended RFC 9253 relations/parameters and unknown types reject until profiled.

ATTACH preserves an inert absolute ASCII URI and optional FMTTYPE. Optional explicit VALUE=URI remains in source. Use the existing no-userinfo URI validator (up to 4,096 characters); opaque storage/CID/URN references remain data, not permission to read a file or include its bytes in mail. Reject VALUE=BINARY, ENCODING and data-scheme payloads. The declared media type is a bounded type/subtype token (127 characters, no parameters or wildcard ranges), preserved without checking remote contents. No fetching, opening or automatic copying follows. The host owns files, retrieval and file access independently from calendar access.

Cap each list at 64 entries per component, UID targets at 4,096 code points and all decoded values under the shared task metadata budget. Linked occurrence omissions inherit; explicitly supplied complete ordered lists must match target/effective type or URI/media-type meaning. Equivalent explicit PARENT/default URI forms and media-type case may match while raw source presence remains distinct. Other content differences reject. See [RFC 5545 RELATED-TO](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.4.5) and [ATTACH](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.1.1).

## Unarmed DISPLAY alarm definitions

Task VALARM parsing supports ACTION:DISPLAY, required DESCRIPTION/TRIGGER, optional UID/ACKNOWLEDGED and paired REPEAT/DURATION. This is a **source model only**: parsing never arms an alarm, chooses a recipient, consents on their behalf, acknowledges a native reminder, creates history or delivers a notification. Source UID is optional and preserved without generating an identity; nonempty duplicate alarm UIDs within one task component reject. ACKNOWLEDGED is optional whole-second UTC source state, not proof of an authorized host action. DESCRIPTION uses the existing decoded text/LANGUAGE/ALTREP profile, without URI retrieval.

Relative TRIGGER preserves signed or zero duration units, optional explicit VALUE=DURATION and optional RELATED START/END (effective START when omitted). Require task DTSTART for START, or DUE/effective start-duration deadline for END. DATE, UTC and named-zone anchors remain typed. Absolute TRIGGER requires explicit VALUE=DATE-TIME and whole-second UTC; RELATED/TZID reject. Absolute alarms on recurring tasks represent one source absolute trigger plus repeats, not a new absolute trigger per recurrence. Undated tasks can retain absolute alarms. This adapter validates anchor presence without generating firing instants; runtime date-only timezone selection, DST application, supported result bounds and missed/expiry policy remain separate. It never chooses the server/device local zone or invents a native fallback.

REPEAT and alarm DURATION must occur together. Preserve optional versus explicit zero count; repeat count is additional firings after the initial trigger, while interval must be positive/nonzero. Trusted defaults cap 16 alarm components per task, 256 across the file (including raw overrides), 100 repeats and 366 nominal days for relative magnitude, interval and aggregate repeat span. Exact BigInt magnitude checks preserve units and do not treat nominal days as a DST execution rule. UID/description/annotations charge the shared task metadata budget; all failure is atomic. Runtime planners must separately enforce valid actual calculated instants.

Progress-only occurrence components inherit omitted alarm lists only in their linked projection. Supplied complete lists must match source meaning/order, including raw duration units, effective anchor, absolute trigger, description/annotations, optional UID/ACKNOWLEDGED and repeat presence/state. Different alarm state is not one of the three allowed task-progress differences. Preserve source property presence and ordering when serializing. Snooze/RELATED-TO, PROXIMITY, nested alarm components, AUDIO/EMAIL/custom actions, alarm recipients/attachments and unprofiled properties/parameters reject. Event alarms, native personal state, activation authorization, durable execution and reusable notification integration remain separate. See [RFC 5545 alarms](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.6.6) and [RFC 9074](https://www.rfc-editor.org/rfc/rfc9074.html).

## Rejection and boundaries

Reject detached occurrence components, occurrence timing/content differences, RANGE, PERIOD-valued additions, unsupported alarm actions/snooze/proximity, METHOD, scheduling methods, extended relationships, binary attachments, private extensions and other unprofiled properties/parameters. Those requirements remain tracked for subsequent increments. Unsupported input rejects the entire file; no successful partial task list, silent property removal, recurrence flattening, network retrieval or delivery follows. VTODO scheduling remains deferred under [ADR 0011](adr/0011-defer-vtodo-scheduling.md).

Reuse strict UTF-8/CRLF/BOM handling and existing syntax/component/temporal diagnostics. Diagnostics omit source values. Validate manually constructed syntax trees through the same profile boundary as parsed bytes. Definitions must match the full supported IANA horizon even if a narrower zone would be correct for a task's immediate dates; pre-1970 observance seeds only establish in-horizon rules. See [zone validation](icalendar-event-adapter.md) and [timezone maintenance](timezone-data.md).

| `IcalendarDisplayAlarm` | Unarmed source component, decoded annotated description, trigger, optional source UID/UTC acknowledgement/repeat count and interval. |

| `IcalendarTaskText` | Decoded value plus optional language and alternative URI. |

| `serializeIcalendarTaskCalendar` | Deterministic reserialization of validated source syntax, including FREQ-first RRULE output, quoting and UTF-8 folding. |

Typed core sets/timing are semantic projections; retained source trees preserve optional VALUE annotations, numeric spelling, repeated date-property grouping, text parameters and envelope/zone details. Serialization is source-preserving semantics, not original-byte storage or an authorized current-state module export. It does not regenerate a native calendar or serialize private transition history. No Serverpod generated models, tables or migrations change in this increment.

Defaults include `maxTasks=128` (all VTODO components), `maxOverridesPerTask=64` and `maxTaskMetadataCodePoints=65536` to the existing trusted component limits. Charge decoded UID/text/annotations across all tasks before returning results. Existing syntax, zone, observance/onset, per-rule/list and shared calendar recurrence-work/explicit-date limits remain active across the file. Invalid trusted limits reject; no budget exhaustion becomes a truncated successful file.
