# Inert event source participants

Status: scoped implementation of the confirmed source-first choice under [ADR 0108](adr/0108-inert-event-source-participants.md); concrete mechanics remain under draft review. Actual focused and broader results belong in [the validation record](scaffold-validation.md).

VEVENT ORGANIZER and ATTENDEE are preserved as unverified source calendar-address claims. They never resolve host users, establish ownership, prove membership/delegation or acting-sender authority, assign native work, change event status/transparency, reserve resources or send invitations. A source ROOM/RESOURCE kind is metadata, not a booking. Native participant editors and scheduling remain separate; METHOD still rejects. Source data is not a trusted scheduling request.

## Bounded wire profile

Immutable `IcalendarEventParticipants`, organizer/attendee values and nested parameter lists retain decoded spelling, presence, source order and duplicate attendees. Organizer permits CN, LANGUAGE, DIR and SENT-BY. Attendee additionally permits CUTYPE, MEMBER, ROLE, PARTSTAT, RSVP, DELEGATED-TO and DELEGATED-FROM. LANGUAGE requires CN; each parameter occurs once, and only MEMBER/delegation parameters accept multiple values. Unknown parameters reject. Addresses and directory/delegation links undergo syntax checks only, without lookup or retrieval. RFC 7986 EMAIL and other unprofiled participant extensions remain separate.

Optional raw token values remain absent when omitted. Separately named effective projections apply RFC defaults/fallbacks: absent CUTYPE means INDIVIDUAL, unknown CUTYPE means UNKNOWN; ROLE defaults/falls back to REQ-PARTICIPANT, PARTSTAT to NEEDS-ACTION, RSVP to false. The supported event states are NEEDS-ACTION, ACCEPTED, DECLINED, TENTATIVE and DELEGATED. Task-only COMPLETED/IN-PROCESS explicitly reject in this event profile; other well-formed unknown tokens remain source data with fallback projections. These values never change event STATUS or host authority.

A master containing attendees requires an organizer. Omitted occurrence claims inherit only in the linked projection (`participantsFor(component)`); raw omissions remain absent for export. Explicit occurrence claims must match the master exactly in addresses, ordered attendee/list values and decoded parameter presence, with token case insignificant. Adding an explicit default parameter is still a source difference and rejects. Different occurrence participants/PARTSTAT remain unsupported, including at future-timing anchors. Foreign components cannot be projected through another series. `decodeIcalendarEventParticipant` validates a single syntax property under the same profile, without cross-component authority or identity resolution.

Limits match the task profile: 64 attendees per component, 16 addresses per list parameter, 1,024 ASCII characters per address, 4,096 code points per CN and 64 ASCII alphanumeric/hyphen characters per token. Existing absolute ASCII URI/no-userinfo and language checks apply. All decoded participant values share the 65,536-code-point event metadata budget across a file or stored series. These are bounded application limits, not RFC maxima. Invalid or excessive input rejects atomically.

## Storage, authorization and example

Nullable organizer and attendee-list fields extend the existing server-only source metadata JSON, using immutable server-only `CalendarEventSourceParticipant` DTOs (address plus deeply frozen decoded parameter map). No table columns or migration are added. Empty attendee lists normalize to absence, keeping older metadata-only event-source-v2 baselines compatible; no source identities or prior claims are invented. Own source claims remain on their original component, including metadata-only originals after timing is cleared. Ordinary details/previews/protocol responses hide claims and hidden-only node presence. Native edits preserve them; export still rejects unrepresentable inherited timing. Current source snapshots participate in baseline/no-op/local-conflict checks and deletion scrubs active data/private snapshots.

Existing independent `readEventSource` authority gates export and replacement, including final checks and identical retries. Host adapters receive complete immutable current/proposed source intents, never historical baselines. Reading a claim does not approve it. Unlike native availability organizer editing, merely preserving an imported event organizer is not a host-approved address action.

The synthetic example imports/exports organizer and attendee claims and explains their inert/read-only status. Tests cover raw and effective values, matching/inheritance, malformed/unknown parameters, limits, frozen lists, server-only persistence, native retention, source replacement, atomic rejection and two-host/browser export. No production directory, invitation, email or resource action is connected. Native participant editors, relationships/attachments, alarms, scheduling, feeds and external calendar-client evidence remain separate.

See [RFC 5545 participation status](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.2.12), [attendee](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.4.1), [organizer](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.4.3), [source metadata](event-source-metadata.md) and [task participant policy](adr/0092-vtodo-source-participants.md).

[ADR 0109 source references](event-source-references.md) now extend this private source boundary with unresolved basic relationships and inert URI attachments. This supersedes references-pending wording only for that bounded profile; native graph/file editors and RFC 9253 extensions remain separate.
