# Authenticated free/busy exchanges

Accepted [ADR 0180](adr/0180-authenticated-bounded-freebusy-exchanges.md) implements optional, private VFREEBUSY PUBLISH/REQUEST/REPLY exchange in the calendar module. Enable `CalendarFreeBusyExchangeRuntime` on the example-hosted module; it is independent of HTTP subscriptions, authenticated file export and received event invitations. The example records synthetic MIME under ignored `.local/freebusy-mail/` and sends no real mail.

A mailbox represents one actual calendar. The host must verify its scope, owner, calendar, address and stable binding; it must not claim that a partial calendar represents someone's complete availability. Native operations use explicit whole-second UTC windows of at most 31 days within [1970,2100). The complete existing free/busy pipeline applies recurrence, exceptions, date-only zones, DST, tentative status, working-hours composition and fallback. Unknown, denied or over-budget coverage rejects publication atomically. Tasks do not book time.

## Explicit actions and source meaning

Publish and Request create new protocol UIDs, separate from native IDs. Share and Refuse answer the selected incoming request using its exact UID, window and roles. Share requires complete authorized native calculation; Refuse emits status 3.8 without FREEBUSY and requires no booking-read permission. Another reply to the same request requires a strictly later actual database second. Nothing manufactures a future stamp; clients retry after the clock advances. VFREEBUSY has no SEQUENCE.

Receipt, review and dismissal never calculate availability, reserve time, alter native data or send a response. Incoming publications and replies preserve the supported pure source groups, overlaps, annotations, omissions and status codes as informational data. Empty source data does not prove free time or completeness. Multi-component PUBLISH is retained atomically (up to 32 components); REQUEST supports up to 64 attendees. A reply must match a retained outgoing request's UID, verified respondent route, local requester and exact window. This exact-window restriction is an application profile, not a universal RFC requirement.

Raw ingress is server-only through `CalendarModule.receiveFreeBusy`; generated clients cannot supply sender proof. Private generated endpoints expose inbox/header/raw read, dismissal, outgoing/activity pages and explicit publish/request/share/refuse/withdraw operations. Headers contain roles and windows, not busy periods, event IDs/titles/counts or the internal calendar-binding ID. Raw source is a separate authorized inert-text view. Source UIDs, addresses and codes confer no ownership or authority. Links are never fetched.

REQUEST heads correlate exact verified requester/local-recipient/UID identities. Separate verified recipients are admitted independently. A higher DTSTAMP selects a new source, lower is stale, and equal stamp with different content makes selection conflicted until a later source arrives. Binding/calendar/window changes reject. Exact retained ingress receipts and command UUID/criteria retries reauthorize before quotas and return historical results without reactivation. A new delivery-key alias cannot pin an already expired source.

## Host authorization and consistency

`CalendarFreeBusyExchangeHost` resolves the trusted private owner and actual mailbox, verifies every incoming source role/origin, approves immutable complete messages/routes and checks each independent operation. Foreground reports also require ordinary free/busy query/export and every event/rule source projection. Refusal and data-free requests do not gain booking access. Header, raw-source, outgoing and activity permissions are separate.

Background `authorizeSources` receives actual immutable parent/event/rule requests with no fabricated actor. Dispatch rechecks current owner/mailbox authority, routes, source selection and complete-message disclosure. Hosts must make `CalendarHostContext.policyRevision` cover exchange/read policies as well as ordinary calendar policies, so a changed policy invalidates continuations. Coordinated and external fresh-check guarantees remain explicit; a final external check still leaves an after-check revocation race. A lease cannot recall an accepted external message.

Opaque pages contain no totals, charge raw work before authorization and prove authorized exhaustion. Cursor state binds family, criteria, private owner, principal/scope, policy/native revisions, metadata vector and exact timezone identity; activity also binds its command. Legacy cursor handlers reject this family. Cursors contain no message bodies, event text or saved permission decisions.

## Immutable work, storage and deletion

Seven server-only tables hold request heads, source documents, ingress receipts, outgoing commands, indexed source references, deliveries and attempts. `CalendarCursorRecord.freeBusyExchangeState` adds one nullable private JSON value. The generated module/example migrations add those boundaries without rewriting existing rows. Head latest pointers avoid cyclic FK ownership. Incoming replies pin their outgoing request; outgoing replies pin their incoming source. Retention releases receipts, commands and sources in dependency order.

A report records exact calendar settings, timezone-data/calculation profile and the complete event/rule source set, revisions and fingerprints. Before submission/retry, changes withdraw that command instead of rebuilding different bytes under its stable delivery UUID. Unrelated calendars' writes do not invalidate the work globally. An unsupported recorded timezone/profile is operationally unavailable, not proof that user data changed. Deploy compatible calculation code, deletion hooks and pinned timezone data to every active host before enabling workers; mixed-profile operation is not a supported upgrade strategy.

Deletion of a source calendar, contributing event or availability rule atomically fences pending report work, removes indexed references and scrubs queued and retained terminal report payloads/source vectors. Accepted delivery remains accepted with content-free audit; it cannot be recalled. Private reports do not block shared deletion. Exact command retries may return the same minimal receipt after scrubbing, but cannot reconstruct bodies or resend. Calendar deletion also retires its private mailbox/request-head binding. Foreign informational reports retain their independent private lifecycle.

Defaults/maximums are 128 heads/512 sources/1,024 ingress receipts/128 commands per owner, with scope ceilings 4,096/8,192/32,768/4,096; 64 versions per head, 64 routes per command, 256 pending deliveries per owner/10,000 per scope, and 16,384 source references per owner/262,144 per scope. Message bodies cap at 262,144 bytes; headers at 32 KiB. Incoming (body plus header) and outgoing families each cap at 8 MiB per owner/64 MiB per scope. Hosts may lower admission limits; maintenance still handles already admitted rows under approved ceilings. Exhaustion rejects atomically without evicting proof.

Source/ingress and terminal history default to 30 days; outgoing requests accept new correlation for 30 days. Existing dependencies may pin records longer. Content-free markers have a further 30-day retention once references permit retirement. Delivery expires after 15 minutes for reports, 24 hours for data-free requests. Workers use database leases (120 seconds), a 15-second transport timeout, at most eight attempts, 30-second exponential backoff capped at one hour, and batches of 32. Audit/lease timestamps may retain database fractions; wire calendar timestamps remain whole seconds. Stable delivery IDs and fenced outcomes survive process loss, but provider acceptance means neither recipient receipt nor display.
