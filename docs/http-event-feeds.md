# Optional event subscription feeds

Status: scoped implementation under [ADR 0116](adr/0116-optional-event-subscription-contract.md), with approved storage/defaults and full local batch validation passed. This is not external Apple, Google or Outlook compatibility evidence.

`serverpod_calendar_feed_server` and its generated `serverpod_calendar_feed_client` are the optional working package pair. On 2026-10-25, pub.dev's package API returned 404 for all eleven workspace package names, including [the feed server name](https://pub.dev/api/packages/serverpod_calendar_feed_server) and [feed client name](https://pub.dev/api/packages/serverpod_calendar_feed_client). This is a current lookup, not a name reservation; recheck before publication. Calendar storage, native APIs, authenticated import/export and iCalendar codecs remain independent. The calendar package does not depend on the feed package. The example installs both; its generated host/client schema now includes this module.

## Publication profile

A feed explicitly selects one to sixteen calendars in one trusted host scope and publishes their complete supported VEVENT series. It has its own management label, protocol UID and optional RFC 7986 text/color/link/image/refresh presentation. These values never inherit calendar metadata automatically. The Flutter editor offers an explicit label-to-NAME copy action. An empty selection is invalid; selected calendars without events produce an empty VCALENDAR.

Event publication UIDs are `urn:uuid:<native-event-uuid>`, stable across feeds and URLs. Masters and occurrence components use the same publication identity. Copies in separate calendars stay distinct even when their source UIDs match. Authenticated exports retain source UIDs and source alarms. Subscription output excludes every VALARM, all private reminder state, tasks, raw availability definitions, SOURCE and scheduling messages. No bearer URL is inserted into another publication property.

The bounded event writer validates faithful current-state export before applying that declared projection. It rejects unsupported source relationship mappings, follow-series cancellations and content-only exceptions that cannot yet be represented faithfully. It never pins inherited timing, flattens recurrence or silently drops an unsupported series. Missing, unauthorized, incomplete, over-budget or unrepresentable sources prevent the whole response. Event details are not a free/busy projection.

Zones are regenerated from the pinned IANA data. Calendar timing stays whole-second and within **[1970-01-01, 2100-01-01)**, with only the approved exclusive endpoints. Unbounded recurrence is not silently clipped with an invented UNTIL; no calculation or external-client accuracy beyond the supported horizon is promised. See [timezone handling and updates](timezone-data.md).

There is no cached timezone representation: a pinned-data or serializer update changes the generated bytes and their ETag on the next authorized request. Stored feed protocol LAST-MODIFIED currently tracks source/settings writes, not deployment versions. Coordinated timezone upgrades still need the versioned recalculation/publication-invalidation workflow in the update guide; this increment does not implement that deployment workflow or make mixed-version hosts safe.

## Host installation and authorization

Install `CalendarModule` with a `CalendarPublicationPolicy` and one `CalendarFeedDependencies` instance in its dependency-provider list. Pass that same instance to `CalendarFeedModule.install`, together with a `CalendarFeedHostPolicy` and `CalendarFeedOptions`. Installation checks the registration and declared authorization guarantee. Register `CalendarFeedRoute(pod)` at `/calendar-feed`. The example's [startup](../example/calendar_example/calendar_example_server/lib/server.dart) and [entry point](../example/calendar_example/calendar_example_server/bin/main.dart) show actual wiring.

Management endpoints require login. The host resolves actor, scope, policy epoch and an opaque publication-authority reference from trusted state. Operations distinguish list/read/create/update/delete and credential listing/creation/revocation. Policy callbacks receive actual current and validated proposed feed state, selected IDs and applicable credential context without a token/digest. The first management view is complete: allowing its operation includes the returned management fields/receipt. Lists filter authorized feeds, return bounded results and expose no totals. The example picker additionally uses ordinary authorized calendar listing; hosts can provide their own GUI.

Bearer requests use a token-free internal session. They do not fabricate a user's JWT and do not reuse the authenticated export endpoint. `CalendarPublicationPolicy` receives actual calendar/event snapshots and the stored authority reference, independently approving the complete required publication projection. That reference and source participant addresses grant no authority themselves. The example resolves it to a currently active, unblocked private-scope user; production adapters can resolve organizations, groups or other host rules.

The calendar-owned publication transaction acquires the same scope lock as native writes and supplies a server-only source projection/transaction port. The feed module queries only its own tables. Selection changes, deletion dependencies, current credentials, event reads and final policy checks use this boundary. Active selections block calendar deletion. A final external fresh check retains the documented after-check revocation race; coordinated guarantees require actual host coordination through commit. See [authorization consistency](authorization-consistency.md).

The registered dependency provider also observes actual selected-calendar event changes in that transaction, including deletion. It advances feed protocol modification time using nondecreasing whole-second database time. Unrelated calendars and native event no-ops do not change it. Management-label changes and credential creation/revocation change management revisions without changing publication bytes; accepted feed settings writes advance the feed API revision. Identical source replacements remain true no-ops. Revisions remain authoritative within one second.

## Models and limits

All four persistence classes are server-only. [ADR 0116](adr/0116-optional-event-subscription-contract.md) is the approved physical-boundary record; generated migrations come from `.spy.yaml` sources.

| Model | Retained state |
| --- | --- |
| `CalendarFeedIdentityRecord` | Server UUID, scope, API revision, optional deletion time |
| `CalendarFeedDataRecord` | Unique identity reference, management label, separate protocol UID/presentation, publication modification time, private authority reference, supported profile version and audit times |
| `CalendarFeedSelectionRecord` | Feed reference and native calendar UUID, unique per pair |
| `CalendarFeedCredentialRecord` | Management UUID, feed reference, versioned unique SHA-256 digest, optional label, revision, creation/revocation times |

Management DTOs are `CalendarFeedSettings`, `CalendarFeedView`, `CalendarFeedCredentialView` and the one-time `CalendarFeedCreatedCredential`. They are generated transport classes, not additional tables. Ordinary views omit the authority reference and digest; only the creation response contains a full URL. Treat that response as secret and exclude it from custom response-body logging/tracing.

The initial fixed bounds are 64 active feeds per scope, 16 selected calendars/feed, 16 active URLs/feed and 64 retained credential rows/feed. Native management labels are trimmed, nonblank, single-line and at most 256 Unicode code points; credential labels are optional with the same length/line rules. Presentation uses the existing bounded text and supplemental-metadata editing profile. Empty presentation objects normalize to absence. No linked content is fetched, images loaded or polling job started.

Creation uses 32 CSPRNG bytes per URL and stores only a versioned digest. Configure a trusted HTTPS `publicBaseUri` ending in `/`; an incoming Host header never determines the issued URL. An explicit loopback-only HTTP option serves local tests/development. URL creation requires the expected feed revision; revocation additionally requires the credential revision and actual feed membership. Use a token-free management UUID to revoke. A forwarded URL grants read access until withdrawn/revoked; logout does not automatically revoke the example's subscription URLs.

Deleting a feed atomically removes presentation, authority reference, selections and every credential, leaving only its minimal identity marker. It never deletes calendars/events. Revoked credentials and deleted markers default to 30-day retention, configurable from 1 to 3,650 days. `CalendarFeedModule.runMaintenance` performs bounded pruning under scope transactions; the example's existing recurring maintenance call invokes it. Reaching a retained-row bound fails without evicting active credentials.

## HTTP behavior and logging

GET and HEAD revalidate current feed/token/publication authority before conditional handling. Successful responses use exact-byte strong ETags and `private, no-cache, max-age=0, must-revalidate, no-transform`. There is no representation/allow-decision cache. If-Match uses strong comparison and takes precedence; If-None-Match uses weak comparison, lists and wildcard for 304. The [RFC 9110 conditional rules](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.2.2) are implemented independently of source protocol timestamps.

HEAD has GET's metadata/length and an empty stream. A 304 has no body or declared length. The initial profile ignores HTTP date validators and ranges, emits no HTTP Last-Modified or Content-Range, and offers no redirect/JSON/language negotiation. Optional Content-Language is declared by the host. Keep compression/transformation middleware off this identity-encoding route; encoding variants need their own reviewed validator contract.

Invalid/revoked credentials and withdrawn publication return generic bodyless 404s without ETag. All errors/denials use no-store; malformed authorized conditional fields return 400, failed If-Match returns 412 and generation/policy failures return 503 without partial content. Headers are bounded to 8 KiB, 64 tags/field lines and 32 ignored empty list elements; serialized output is at most 1 MiB and also subject to existing event/component work limits. Query-bearing/non-profile paths reject. Hosts must provide appropriate request admission/rate limits without assuming each polling subscriber has a distinct IP.

**Wrap whole-host startup in `runWithCalendarFeedLogRedaction`.** The pinned Relic adapter can print the raw URI after the route has returned when writing a response fails. The route requires the configured redaction zone, avoids a URL-derived web session and contains its own errors; the startup guard suppresses complete console messages containing configured feed paths, including encoded aliases. Configure custom mount paths in both the route and guard. Proxies, custom logging sinks, analytics and traces require equivalent redaction. This guard is not a substitute for those host/infrastructure settings.

The example's transport fault route is registered only in test mode with explicit `CALENDAR_EXAMPLE_FEED_TRANSPORT_PROBE=true`. It accesses no calendar data and deliberately exercises post-handler errors. It is absent from ordinary development. All test calendars, users and credentials are synthetic.

## Validation

Use `dart run tool/host_smoke.dart --feeds` for focused two-host HTTP/management checks, or add `--flutter` for the focused browser journey after building the host and configuring WebDriver. The full root check also exercises the feed flow. Focused tests cover publication identity/alarm separation, conditional grammar, logging, management authorization, rollback, scope/revision/cap/dependency boundaries and retention. Current exact results and deferred gates belong in [the validation record](scaffold-validation.md); full local batch validation passed. Live mobile push, iTIP/iMIP and external subscription-client UI behavior are separate requirements.

## Event descriptive fields

Accepted [ADR 0134](adr/0134-native-event-descriptive-fields.md) adds the [bounded priority/GEO/RESOURCES projection](native-event-descriptive-fields.md). Continuing complete publication authority must include location, priority and resources; `CalendarPublicationRequest.requiredEventGroups` makes that set explicit to host policy. Exact coordinate spelling and resource groups/annotations remain deterministic. Actual metadata edits change bytes/ETags; normalized no-ops keep protocol/feed generation stable. Revocation is still checked before 200/304, and labels create no bookings. Alarms stay excluded.
