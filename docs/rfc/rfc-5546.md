# RFC 5546 — iTIP scheduling

Source: [RFC 5546](https://www.rfc-editor.org/rfc/rfc5546.html), sections 2–3 and 5–6. **Scoped pure message validation:** All eight selected VEVENT methods have bounded pure source validation under ADRs 0117–0120, including bounded recurring masters and detached instances with explicit property limits. Durable transitions, authority and delivery remain unimplemented. [Status legend](README.md). Rows inventory first-release operations and supporting fields; the pure subset does not complete an operation row.

[ADR 0117](../adr/0117-first-itip-message-profile.md) records the approved first bounded pure-message increment. [The profile](../itip-message-profile.md) lists method constraints, nullable source timing/version fields and rejected properties/delegation flows. Focused tests passed; selected broader batch checks passed. No scheduling transitions, mail, stored membership or sender authority are established by this adapter.

[ADR 0119](../adr/0119-recurring-itip-message-boundary.md) records the approved detached-component boundary and its scoped pure recurrence implementation. Selected broader checks passed; concrete mechanics remain under review. Stored membership, authority and state changes still require later authenticated reconciliation.

[ADR 0121](../adr/0121-pure-freebusy-scheduling-messages.md) adds a separate [pure VFREEBUSY message adapter](../itip-freebusy-profile.md). Source windows/periods/results grant no availability authority and trigger no automatic query or reply.

VTODO scheduling is explicitly deferred under [ADR 0011](../adr/0011-defer-vtodo-scheduling.md); reject/quarantine inbound task scheduling without mutation or automatic replies and reject outbound task scheduling before queueing. Native tasks and standalone VTODO interchange remain planned. Listed method baselines are planned; detailed participation constraints still require validation. Server/protocol tests and native Flutter scheduling are independent of feed client limitations. The application inbox/outbox and mail retries are project implementation choices, not new iTIP properties. See [ADR 0007](../adr/0007-scheduling-and-email.md), FR-20/FR-21 and [scheduling work](../roadmap.md#scheduling).


Scope update on 2026-10-19: the maintainer approved every previously Proposed row as Yes — planned; see [RFC scope](README.md). Detailed constraints and validation remain implementation work; other status categories retain their existing scope. No runtime implementation is claimed.

The maintainer selected explicit atomic Save and notify and native-created organizer meetings first in [ADR 0122](../adr/0122-explicit-native-organizer-publication.md). The approved [first REQUEST runtime/storage](../native-organizer-scheduling.md) is implemented for bounded non-recurring native publication through a synthetic transport. Other runtime methods, recurring publication and real mail remain incomplete; all selected methods above remain first-release requirements. Imported organizer adoption and authenticated inbound reconciliation are separate.


Accepted [ADR 0123](../adr/0123-explicit-native-organizer-cancellation.md) implements whole-event CANCEL for existing non-recurring native organizer meetings through a separate explicit action and the last published snapshot. Local drafts remain private; explicit newer REQUEST publication can reopen. This supersedes CANCEL-runtime-pending wording only for this scoped synthetic-transport increment; recurring/instance cancellation, inbound reconciliation and email remain separate.


Accepted [ADR 0124](../adr/0124-recurring-organizer-masters.md) implements recurring-master REQUEST and whole-series CANCEL over the existing pure pattern profile. It preserves native drafts/exceptions and emits one master rather than flattened occurrences. This supersedes recurring-master-runtime-pending wording only for that slice. Occurrence-component publication, instance/range methods, inbound reconciliation and email remain separate required runtime work.


[ADR 0125](../adr/0125-scheduling-occurrence-field-projection.md) proposes a scheduling-only representation for required fields on future occurrence REQUEST components, with references checked against RFC 5546 on 2026-10-26. It is a pending native-to-wire policy question, not new parser/runtime support or approval of version/reset/bundle/storage mechanics.
