# RFC 9636 — Time Zone Information Format (TZif)

Source: [RFC 9636](https://www.rfc-editor.org/rfc/rfc9636.html), especially sections 3 and 6.1; it obsoletes RFC 8536. Added as an explicit project reference by maintainer instruction on 2026-10-22. **Current use: scoped build-time processing of pinned IANA compiler output, not full RFC conformance.** See the [status legend](README.md) and [timezone generation/update procedure](../timezone-data.md).

RFC 9636 defines a binary interchange format. IANA tzdb supplies the timezone rules; its release number is separate from the format specification. The current project pins tzcode/tzdata 2026e and `timezone` 0.11.2. Runtime data is the package's own TZF representation embedded in generated Dart source, not TZif files read on calendar requests.

| Feature | Purpose | First-release plan | Current scoped use and boundary |
| --- | --- | --- | --- |
| TZif headers/counts and binary data blocks | Locate transition/type data | Yes — planned | Existing build reader checks magic and uses counts to locate pinned compiler output; it is not a comprehensive validator for arbitrary files |
| Legacy 32-bit data block | Backward-compatible block preceding version 2+ data | Yes — planned | Build reader skips this block; runtime coverage is not limited by its 2038 boundary |
| 64-bit transition times | Represent later transition instants | Yes — planned | Existing build extracts signed 64-bit transitions, type indices, offsets, DST flags and designations for the bounded profile |
| Footer TZ strings and future rules | Describe continuation beyond explicit transitions | Host/library | Pinned IANA `zic` calculates transitions through the requested horizon; the project's reader does not independently interpret the footer |
| Bounded/truncated output | Limit generated data to a declared horizon | Yes — planned | Existing `zic -r` generation supplies explicit calculation bounds; boundary checks do not establish complete RFC 9636 truncation conformance |
| Leap-second records and version 4 expiration features | Leap-aware data and validity | No — outside contract | No leap-aware TZif reader/profile is claimed; calendar leap-second values remain explicitly rejected |
| General version 1–4 file import | Accept arbitrary external TZif files | No — outside contract | No public TZif import endpoint or general-purpose version validator is provided |
| TZif media types / TZDIST exchange | Transport timezone binary data | No — outside contract | No `application/tzif`, `application/tzif-leap` or TZDIST endpoint is added; iCalendar VTIMEZONE remains a separate RFC 5545 profile |

The plan column follows the existing inventory convention: selected bounded features can already have implementation evidence without implying complete standard support. This reference records the existing pipeline; it does not expand calendar dates, leap-second support or public import/transport scope.

## Implementation evidence

[The Python generator](../../tool/build_timezone_source.py) verifies archive checksums, builds pinned `zic`, requests fat bounded output, extracts the second header's 64-bit tables and requires explicit calculation-boundary transitions. Python `zoneinfo` supplies an independent reader for the generated reference fixture. [The Dart encoder](../../packages/serverpod_calendar_core/tool/encode_timezone_data.dart) constructs package locations and round-trips the package-specific serialized format. [The pins](../../toolchain.json) record source versions, archive/runtime checksums and coverage. Existing generation/test evidence is linked from [the timezone guide](../timezone-data.md); adding this reference does not claim a new generation or test run.

Ordinary dates remain [1970-01-01, 2100-01-01), with approved exclusive endpoints and calculation-only UTC padding. Future calculations assume pinned IANA rules continue to apply. Unknown offsets fail explicitly. Neither this horizon nor future legislative accuracy is guaranteed by the TZif format itself.
