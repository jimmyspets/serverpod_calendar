# RFC 9074 — VALARM extensions

Source: [RFC 9074](https://www.rfc-editor.org/rfc/rfc9074.html), sections 3–8. **Implemented today: No, for every row.** [Status legend](README.md). First-release alarm execution and reusable notification integration are required; [ADR 0020](../adr/0020-notification-delivery-scope.md) uses a connected streaming example and excludes direct platform push implementations. The selected personal alarm/interchange baseline below is planned under [ADR 0009](../adr/0009-alarms-and-notification-boundaries.md); this is not blanket RFC support.

| Property or feature | Purpose | First-release plan | Notes |
| --- | --- | --- | --- |
| Extended VALARM syntax | Extensible alarms | Yes — planned | Scoped time-based profile; reject unsupported combinations explicitly |
| UID in VALARM | Alarm identity | Yes — planned | Stable personal identity; never leak another recipient's state |
| RELATED-TO in VALARM | Alarm relationship | Yes — planned | Selected snooze mapping; exact private interchange policy pending |
| ACKNOWLEDGED | Acknowledgement instant | Yes — planned | Recipient-level multi-device action state |
| RELTYPE=SNOOZE | Snooze relationship | Yes — planned | Native snooze baseline; wire constraints need approval |
| PROXIMITY | Location/device trigger | No — deferred | No first-release geofencing/proximity execution |
| Nested VLOCATION for triggers | Trigger location | No — deferred | Proximity path deferred; general structured locations remain planned under RFC 9073 |
| Base ACTION | Notification action | Yes — planned | DISPLAY baseline; push is a channel, not a new RFC ACTION |
| Base TRIGGER | Trigger point | Yes — planned | Approved relative start/end/due and absolute-time forms |
| Base REPEAT/DURATION | Repeated alarm timing | Yes — planned | Confirmed capped automatic repeats with configurable limits under ADR 0010; separate from snooze/event recurrence |
| Imported third-party alarms | Untrusted notifications | Yes — planned | Do not arm automatically; explicit authorized activation/profile |
| Alarm execution | Deliver reminders | Yes — planned | Calendar due state/outbox and shared delivery adapter |
| Geofencing/device monitoring | Detect proximity | No — deferred | Requires explicit host/client runtime scope |
| Arbitrary audio/email alarm actions | Extra channels/actions | No — deferred | iMIP scheduling mail remains separate and required |

Native Flutter reminder actions and connected streaming notifications are independent of external feed alarm rendering. Keep personal acknowledgement/snooze state private, calendar timing/state in the calendar module, generic notification delivery outside it and platform providers in external adapters, and OS presentation in Flutter. Trigger/date-only/expiry/retry policies must be approved and tested. See FR-28–FR-31 and [alarm work](../roadmap.md#alarms-and-push), [push delivery work](../roadmap.md#alarms-and-push), [connected-client integration work](../roadmap.md#alarms-and-push).
