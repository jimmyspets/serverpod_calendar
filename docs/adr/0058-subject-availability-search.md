# ADR 0058: Host-resolved subject availability and common-free search

Status: **Accepted scope/access choices; adapter/API mechanics under review**. Date: 2026-10-21.

## Decisions and context

After native working-hours composition, the maintainer selected person/resource availability followed by common-free search. They confirmed an initial **single trusted host scope** and **summary authority independent of direct calendar query access**. An out-of-scope contributor produces unknown; cross-scope aggregation needs separate coordination. Existing [ADRs 0006](0006-resource-availability.md), [0008](0008-module-clients-tasks-and-search.md) and [0012](0012-calendar-availability-policy.md) require complete host-selected contributors, independent per-calendar calculation, intersection of known free time and no falsely free incomplete results.

## Host contract

Add `CalendarHostPolicy.resolveAvailabilitySubject(session, context, target, transaction)`. It returns a frozen `CalendarSubjectResolution`: explicit completeness, private revision and complete contributing calendar UUIDs. This is an authoritative host mapping, never a detail-filtered candidate plan. Hosts retain people/groups/resource identity and membership ownership. Module association flags can supply the mapping, as in the demo, or hosts can resolve their own authoritative mapping. Administrative relationships must not accidentally contribute. External sources or out-of-scope contributors that cannot be evaluated require incomplete resolution, never silent omission. Empty sets do not establish free time.

Check `readSubjectAvailability` on the exact requested namespaced target, then `projectCalendarAvailability` on every actual contributor. Direct `readFreeBusy`, calendar/event detail and rule-management grants are independent. Existing `projectEventBusy` and `projectAvailability` remain required per source. Requests carry frozen `availabilitySearchQuery` and `availabilityTarget` plus actual calendar/event/rule context where applicable. Projection rights can depend on which summary is requested. No query permission or association text creates ownership, membership or scheduling authority.

The module resolves and evaluates under its durable scope-row transaction. Recheck each successful target's summary permission and host revision/normalized contributor set after the full calculation. Changed mappings or denied/unavailable required sources invalidate that target to unknown. Trusted context/epoch changes fail the query. Hosts should coordinate their mapping and policy state through the supplied transaction; the module lock alone does not coordinate external directories or ACL writes. External fresh checks retain an after-check race; the recheck is not a lease or stronger revocation guarantee. No process-local cache provides correctness.

## Native query and response

`calendarAvailabilitySearch.search` takes bounded whole-second UTC bounds, exact opaque target triples, `perTarget`/`commonFree` mode and optional positive `minimumSeconds` defaulting to 1. Deduplicate exact targets in first-seen order. Different namespaces/kinds/case remain different references. No client-supplied contributor list is accepted.

Each target returns complete/unknown coverage, its merged native classified partition and qualifying maximal free slots. A complete partition covers the entire query even if the minimum excludes every free slot. Unknown returns neither periods nor slots. Subject free time intersects every independently evaluated contributor after its own rules, fallback and bookings; calendar priorities never override other calendars. Blocking classifications retain native unavailable/busy/tentative/free precedence. Common-free mode intersects complete results for **every** target, then applies the minimum; any unknown produces unknown common coverage and no common slots. Per-target mode has no common coverage/slots. Independently complete target results remain usable when another target is unknown.

Minimum duration means exact elapsed whole seconds, not nominal civil days. A value longer than the query can yield a complete result with no qualifying slots. Timezone/recurrence/status/exception semantics remain in the existing per-calendar evaluator. UTC/date/zone guards are unchanged. This is structured native output, not VFREEBUSY serialization or a reservation.

The response echoes requested target references/bounds/mode/minimum and adds a random `snapshotId` and whole-second `calculatedAtUtc`. These correlate one response only; they are not a revision token, validity duration or reservation. Do not disclose contributor calendar UUIDs, source object IDs/content/counts, private scope generation, resolver revision, directory labels or raw rules. Unknown does not distinguish nonexistent, denied, empty, unsupported or over-limit targets.

## Bounded profile and example

Caps: 31-day window; 32 raw target entries/8 distinct targets; 8 raw contributor IDs per resolution before deduplication; 16 calendar evaluations per search. The entire search shares expansion budgets of 256 active events, 64 definitions, 64 opening sources, 5000 projected bookings and 5000 projected openings. Repeated source reads for different targets consume the aggregate budget again, preserving target-specific policy checks. Existing per-event/opening expansion caps remain. Aggregate charges precede full query expansion; bounded identity lookahead and metadata validation for overflow detection can inspect additional records and are not a global 256-SQL-row guarantee. Each combined target/common partition accepts at most 8000 source periods and returns at most 1000 periods. Hitting a budget never truncates a successful partition; the affected target/common result is unknown. Earlier independent complete targets can remain complete, so target order can affect which targets fit a budget. No global 200000-candidate claim is made; candidate limits remain per source under the aggregate source caps.

The private demo resolves only the authenticated `demo/user` reference, from stored availability-contributing links on active calendars in that user's scope. Its bounded scan considers up to 256 active scope calendars; a larger scope is incomplete. Its private resolver revision incorporates module scope generation and policy epoch. It does not expand groups or copy a resource directory. Production hosts replace both identity resolution and policy, and may use indexed authoritative mappings. The Flutter example edits targets/window/minimum/mode, clears stale results, and distinguishes complete/no-qualifying-slot from unknown without private source details.

No new table or migration is needed: requests/views and host behavior reuse existing associations/storage. Verify generation and migration tooling. Cross-scope coordination, group-member expansion policy, indexed large-calendar candidates, resource quantity/capacity, exclusive reservations and wire export remain separate work.

## Validation

Test complete partition intersection/oracles/limits, independent calendar priorities, exact minimum boundaries, duplicate targets, administrative-only links, hidden direct access with allowed summary projection, denied sources, empty/unresolved/foreign/deleted contributors, changing revisions/sets/rights, frozen callbacks, input bounds and aggregate work exhaustion. Compare independent hosts after rule/association changes and drive both Flutter modes through generated APIs. Keep focused feature checks separate from the broader batch check and record actual outcomes in [validation](../scaffold-validation.md).
