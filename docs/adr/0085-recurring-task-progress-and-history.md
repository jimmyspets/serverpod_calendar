# ADR 0085: Recurring task progress and history

Status: **maintainer-confirmed independent occurrence progress and history preservation; concrete schema/API/query and resolution mechanics proposed**. Date: 2026-10-23.

After the non-recurring task increment, extend durable tasks with recurrence, bounded occurrence previews and original-occurrence progress. Completing or cancelling one occurrence changes only that occurrence, leaving the series and other occurrences unchanged. Preserve progress and completion history when changing a rule. Reject a rule edit that would orphan recorded occurrences until those records are explicitly resolved. These two choices were explicitly confirmed by the maintainer; they do not authorize silent removal/reassignment of records. The maintainer also confirmed explicit DTSTART for recurring tasks, rejecting conversion of a task with recorded progress until a transition policy exists, and retaining occurrence history with the active task until deletion without automatic expiry in this first increment. Configurable pruning/retention remains separate.

Propose reusing the selected typed task recurrence core and exact original DATE/UTC/zoned identity, with DTSTART mismatch rejection, canonical filters, bounded generation, ISO display fields and explicit recurrence WKST behavior. Keep task milestones distinct from event intervals: start-only/due-only tasks are valid, an undated task cannot supply a recurrence anchor, and no task books time. Do not manufacture an occurrence identity from its completion time or current display position.

Propose independent per-occurrence current progress plus append-only transition evidence while active, protected by the existing progress operation and an independent history disclosure boundary. Actual parent/task/original occurrence, current records and final validated proposal must reach the host adapter. Define ordering, retry/no-op semantics, concurrency, retention/deletion scrubbing and explicit resolution of historical orphaning before schema implementation. Neither all-series lifecycle commands, timing/content exceptions, VTODO wire mapping nor alarms are implicitly implemented by this record.

Acceptance requires focused recurrence/state/authorization tests, rule-edit orphan protection, bounded query and cursor behavior, fresh/populated migrations, two-host competing progress checks and generated-client Flutter journeys. Keep source completion timestamps, native recorded transition time and current completion state distinct; never infer old completion history from a legacy task's audit time. This is a contract record, not an implemented recurring-task service.
