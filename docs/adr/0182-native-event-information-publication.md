# ADR 0182: Explicit native event information publication

Status: **Proposed; explicit maintainer agreement required before implementation.** Group native VEVENT PUBLISH and whole-publication lifecycle using the existing durable scheduling outbox. This is information delivery, separate from invitations and HTTP subscriptions. ADR 0181 is implemented in draft PR #194; its pending hosted checks are not treated as successful.

## Evidence and scope

The selected RFC 5546 matrix still marks durable VEVENT PUBLISH planned. ADRs 0117–0120 implement its pure codec; ADRs 0122–0130 implement native invitation publication/lifecycle with four private tables, verified organizer/routes, immutable bytes, stable retry identities and fenced workers. The current meeting row has one unique event binding but no purpose discriminator. Existing workers/checkpoints and example MIME explicitly handle invitation REQUEST/CANCEL. Adding a method string alone would not safely separate informational recipients from attendees.

[RFC 5546 section 3.2.1](https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.1) requires an organizer and forbids attendees in PUBLISH. Its SUMMARY property is required but may be empty. Publication may be updated and cancelled; the existing pure profile supports explicit STATUS:CANCELLED without attendees in CANCEL. Those source facts grant no sender authority or automatic native action. The example remains synthetic-only.

Group initial/update Save and publish, whole Cancel and publish, published-value Reopen and publish, repeated lifecycle, model migration, worker/MIME adaptation, generated APIs and Flutter with two-host/process-loss tests. Support native-created DATE/UTC/named-zone non-recurring events and recurring masters with the existing RRULE/RDATE/EXDATE/PERIOD profile. New active PUBLISH rejects stored single/future occurrence components or cancellation cutoffs rather than dropping them. Component publication, information-recipient changes, imported adoption and incoming PUBLISH review/application follow separately and remain required work.

## Explicit operations and disclosure

Expose separate `saveAndPublishInformation(CalendarSchedulingSaveRequest)`, `cancelPublishedInformation(CalendarSchedulingCancelRequest)`, `reopenPublishedInformation(CalendarSchedulingReopenRequest)` and `informationPublicationStatus(eventId)`. Reuse the immutable request shapes: trusted actor/scope is resolved on the server; the save contains event ID/revision, validated native content, recipient proposals and command UUID. No input can choose the binding purpose or assert organizer authority. Ordinary saves send nothing.

A first binding requires proven native origin and an active supported event; imported/unknown origin rejects without inferring provenance from a null baseline. Its organizer is host-verified. Native API UUID, stable event protocol UID, outgoing version and delivery UUID remain distinct. Fix exact normalized recipients, organizer and authority binding at first publication. Mail recipients are private routing targets, not ATTENDEE properties, host assignments, directory identities or RSVP grants. Invitation/publication purpose conversion and recipient changes reject.

Save and publish validates the same native editing/lifecycle rules as ordinary event writes, then atomically saves the accepted final event and durable PUBLISH intent. The outgoing message preserves every supported representable property and timing distinction, uses the verified organizer, has no ATTENDEE and contains no VALARM. Reject canonical attendee claims, conflicting organizer claims, unsupported source alarms or unrepresentable data rather than stripping them. Personal alarms remain separate private runtime state. When native SUMMARY is absent, emit an explicit empty scheduling-only SUMMARY; never store or invent a display placeholder.

The first binding fixes recurring/non-recurring mode. New active publications require the supported master-only shape. Exact retained historical retries and whole lifecycle use their retained supported published basis while preserving newer drafts; they never serialize private occurrence edits opportunistically. No detached/component publication or range semantics is inferred.

Use separate `publishEventInformation`, `cancelEventInformation`, `reopenEventInformation` and `readEventInformationPublication` host permissions. Writes also require applicable actual native edit/lifecycle rights and complete event detail/source disclosure. The protected status response needs its new read gate and ordinary event read; it exposes only the existing bounded identity/local-change/outcome profile, not bodies/routes. Host adapters receive trusted purpose, action, current/final native snapshots, the canonical publication checkpoint, exact immutable outgoing message/digest and recipient. `resolve` remains method-neutral organizer/route verification; it is not publication authority. Complete-message checks distinguish informational recipients from an invitation roster at both command phases and actor-free dispatch.

## Version, lifecycle and retries

Reuse the invitation workflow's published-versus-native version rules and true no-op semantics. Initial outgoing master SEQUENCE starts at the existing native baseline; actual changed publication must advance past its previous published version, reusing an already-newer saved native version where valid. Whole cancellation/reopening uses the existing conservative lifecycle floor. Whole-second protocol stamps remain nondecreasing; raw database creation/lease/expiry time stays separate. Overflow rejects the complete transaction.

An identical normalized current/last-published state is a true authorized no-op with no native revision, protocol, scope generation or intent changes. It is not a manual resend. A changed publication advances the API revision even for an already-saved local edit. Exact retained command retries reauthorize and return their stable historical receipt before new admission; changed criteria or reuse across purpose/action rejects. Retrying an old cancellation cannot cancel a later reopened state.

Whole cancellation sends METHOD:CANCEL with explicit STATUS:CANCELLED and no attendees, based on the last published information snapshot and fixed routing recipients. It preserves newer native draft text/timing/metadata and requires independent cancellation plus native lifecycle authority. Repeat synchronized cancellation is a true no-op, never an implicit resend.

Reopening sends a newer active PUBLISH using the retained last active published values, while preserving unrelated newer draft values and making only the approved native lifecycle change. It is a separate explicit action and permission. Later new publications may explicitly publish current validated local edits. Published status, current native status and local-dirty indication remain distinct. Prior exact receipts remain historical and never reactivate work. Existing generation supersession/fencing and terminal-history rules apply; no new parallel-partial coordination is introduced.

## Proposed storage and API boundaries

Add `CalendarSchedulingBindingPurpose` with `invitation` and `informationPublication`, one nonnullable purpose field on `CalendarSchedulingMeetingRecord`, and a nullable read-only purpose in `CalendarSchedulingView` (null when unbound). The generated migration initializes every existing binding as invitation because all were created by the existing invitation workflow; all prior values/receipts/leases/checkpoints remain unchanged. Do not infer native event origin or convert any old binding. No new SQL table or quota expansion is proposed.

Add explicit information publish/cancel/reopen values to `CalendarSchedulingPublicationKind`, and trusted actual purpose to the immutable policy/intent context. New endpoints derive purpose server-side. Old invitation send/read/reply/instance/range paths must reject an information binding before legacy parsing or correlation fallback, and information paths reject invitation bindings. Incoming participant replies never create attendee response state for PUBLISH recipients. Deploy the generated migration and compatible purpose-aware code to all active hosts/workers before enabling information publication; mixed old-worker operation is not claimed safe. Existing invitation behavior and legacy checkpoint decoding remain intact.

Use a separate bounded flat information-publication checkpoint version in existing snapshot/projection columns: purpose/action/event/parent/UID bindings, canonical/outgoing correspondence, last active supported master, lifecycle/version floor and command receipt. Retain no recursive predecessor chain. Every read/dispatch revalidates purpose, method/kind, organizer, no-attendee shape, supported profile, digest and version/body correspondence. Corrupt or cross-purpose state fails unavailable. Reuse existing payload/snapshot ceilings, pooled scope/recipient work and retention limits; purpose separation may not bypass quotas.

The latest required private checkpoint remains while its binding is active; superseded terminal history retains the existing default 30-day policy. Existing dependency restrictions continue to block event/calendar deletion while a binding remains active. Binding retirement/removal is still separate work; nothing is silently detached or archived. No new body retention or automatic history eviction is introduced.

## Workers, MIME and validation

Reuse the existing four-table command/delivery/attempt machinery and shared database locks, generation fences, leases, expiry, retry/backoff and stable delivery UUIDs. Resolve current actor-free organizer/route/detail/source and method/purpose-specific authority immediately before submit/retry. Never regenerate old bytes from native drafts or fabricate a login. Coordinated guarantees cannot silently downgrade; external after-check and provider-acceptance races remain explicit. Acceptance is not recipient receipt/display.

Extend only the existing example-host enough_mail composition allowlist to PUBLISH, retaining current payload bounds, deterministic sender/recipient/message headers and exact authorized calendar-byte preservation. All addresses remain host-verified synthetic example.invalid routes; no SMTP/provider authentication, production transport or real email is authorized. Other MIME/parser/protection limits remain unchanged.

The Flutter example gets explicit information-publication controls and purpose-aware status. It explains fixed routing recipients, no attendance request, ordinary local saves versus published values, unsupported master/component states, and cancellation/reopening without publishing private drafts. Invitation controls must not operate on information bindings.

Validate native origin, no attendee/authority inference, empty SUMMARY projection, DATE/UTC/zones/recurring masters, unsupported exception/alarm rejection, purpose isolation before fallback, independent permissions/disclosure, stale revisions/no-ops/retries, overflow/quotas, final rollback, private-draft lifecycle preservation, pooled capacity and fresh/upgrade migrations preserving populated invitation state. Exercise two real hosts, competing commands/workers, process loss before/after commit and synthetic acceptance, exact UUID/calendar/MIME retries, route/access withdrawal, generation supersession and ordered retention. Include generated JWT clients and connected Flutter for initial/update/cancel/reopen and old invitation regressions. Run focused development checks, broader group checks once, and full exact-head hosted checks before readiness; commit the complete group once.

## Alternatives and remaining work

Treating route recipients as attendees would manufacture participation. Reusing the invitation binding without a discriminator would expose wrong worker/reply paths. Stripping participants/alarms or flattening recurrence would silently change supported source meaning. Automatic sends on every edit and live regeneration of retries are rejected. Separate tables would isolate purposes but duplicate the existing proven outbox; a trusted discriminator with strict dispatch/API isolation is the bounded proposed alternative.

This is scoped outgoing PUBLISH and whole lifecycle, not incoming publication adoption, all occurrence publication, arbitrary recipient/organizer changes, remaining selected methods, provider trust or full scheduling interoperability. Those existing first-release requirements remain on the roadmap. HTTP bearer feeds, standalone import/export and private alarms stay independent; no deployment or package publication is proposed.
