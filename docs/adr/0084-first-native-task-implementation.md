# ADR 0084: First native task implementation

Status: **scoped implementation of confirmed ADR 0083 choices; concrete schema/API/query mechanics under draft review**. Date: 2026-10-23.

Implement a dedicated non-recurring task family using the pure DateTaskTiming/TimedTaskTiming core. Transport timing is explicitly undated, DATE, UTC or named-zone, with optional start/due and positive duration only with start. Preserve explicit due versus duration; no implicit due or busy interval. Task DUE/effective due is an ordinary value before 2100, not an exclusive endpoint exception. Nonzero fractions, floating/mixed zones, invalid chronology, DUE plus DURATION and recurrence input reject. Native summary is optional; UI-only Untitled task is never stored. Reuse bounded text values and optional native priority 0 through 9.

Separate task identity (UUID, actual calendar, revision, deletion time) from active payload. Payload stores typed content, progress, canonical opaque assignees, independent generated protocol UID/digest/version and audit times. Exact protocol UID candidates are calendar-scoped and non-unique digests; native creation assigns UIDs. New task rows have known native checkpoint times/SEQUENCE 0, without invented source history. Delete scrubs the active row, leaving only a minimal marker. Active tasks block parent deletion under the shared scope lock; dates/assignees never contribute booking intervals.

Expose distinct create/content/progress/assignment/delete commands with optimistic revisions. Native creation starts NEEDS-ACTION/0 and no completion time; nonempty initial assignees require independent assignment permission. Progress actions explicitly set 0–99 percent, complete, reopen or cancel. Complete sets 100 and whole-second server UTC time; repeating complete retains it. Reopen resets NEEDS-ACTION/0 and clears time. Cancel preserves percentage and clears time. Percentage editing/completing a cancelled task requires reopening; percentage editing a completed task also requires reopening. This is the initial native application profile, not an RFC constraint or completion history. Accepted normalized no-op writes keep protocol checkpoints but retain existing native API-revision/audit/generation behavior.

Use separate list/read/create/update/progress/assignment/delete host operations and actual parent/current/final proposed task context. No built-in owner/assignee role. Assignees are namespaced opaque references approved by the host, not user profiles, membership, ATTENDEE or scheduling authority. Raw assignments are bounded at 128 and the host maxAssociations budget (default 64), sorted/deduplicated exactly; namespace/kind are bounded ASCII tokens and external IDs retain up to 256 code points. Collection/object scope is resolved from stored identity rather than claimed parentage.

Add predefined summary, description, location, timing, priority, progress, assignment and protocol-identity disclosure groups. Pages contain only authorized views, an opaque continuation and no totals; host candidate constraints cannot bypass actual read decisions. Bind task cursors to task query kind/calendar/groups, actor/scope/policy/data generation, page size and expiry. Existing calendar/event cursors must reject task continuations. Initial list APIs select a calendar without task-specific filters; richer filtered queries follow with their own disclosure-safe contracts.

Generate separate identity/payload tables and nullable task cursor bindings using the pinned toolchain. Verify fresh and populated upgrades without inventing tasks/history or changing existing calendar/event state; do not hand-edit generated metadata. Exercise protected progress/assignment transitions, immutable proposals, stale/final-denied rollback, marker scrubbing, parent dependencies, cursor isolation, multiple hosts and Flutter. Native task recurrence/history, VTODO interchange, advanced metadata, scheduling and alarm execution remain separate increments. Reusable semantics remain outside Serverpod/Flutter.
