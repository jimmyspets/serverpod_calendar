# ADR 0094: VTODO DISPLAY alarm source profile

Status: **scoped implementation of confirmed DISPLAY timing/source-state slice; concrete representation/limits remain under draft review**. Date: 2026-10-23.

The maintainer selected pure DISPLAY alarms with relative start/due or absolute UTC triggers, paired bounded REPEAT/DURATION and preserved optional UID/ACKNOWLEDGED. Snooze relationships follow separately. No imported alarm is activated or delivered; source state establishes no recipient, consent, acknowledgement by a host user or permission. This extends task wire parsing only, not event alarms, native storage/actions, workers or notification delivery.

Propose immutable `IcalendarDisplayAlarm` and `IcalendarAlarmTrigger` values with raw syntax and decoded source state. Require ACTION:DISPLAY, DESCRIPTION (existing scoped text annotations) and TRIGGER. Relative triggers preserve signed/zero duration units, optional VALUE=DURATION and optional RELATED START/END with effective START. Absolute triggers require explicit VALUE=DATE-TIME and whole-second UTC; RELATED/TZID reject. UID is optional source text, not generated/authority; duplicate nonempty UIDs within one task component reject. ACKNOWLEDGED preserves optional UTC source value, without manufacturing native user actions/history.

Require existing task DTSTART for relative START and DUE or DTSTART/DURATION for END. DATE, UTC and named-zone tasks retain their typed anchors. A linked progress occurrence may inherit omitted task timing and alarms, but supplied complete alarm lists must match the master semantically and in order, including optional UID/acknowledgement state. No per-occurrence alarm edits in this first slice. Compare raw relative duration units, effective anchor, absolute value, text annotations, repeat presence/count/interval and optional source state; keep source presence/spelling separately. Absolute alarm data on recurring tasks denotes one absolute trigger plus repeats, not a separate trigger for each recurrence. No actual firing instants are generated by this adapter.

Use trusted defaults maxAlarmsPerTask=16, maxCalendarAlarms=256, maxAlarmRepeat=100 and maxAlarmDurationDays=366. Charge raw components across masters/overrides against the calendar count and description/UID/annotations against the shared task metadata budget. Bound relative magnitude and positive repeat interval using exact nominal unit magnitudes, and total repeat span to the same bound; this is a resource/profile check, not DST calculation. Preserve explicit REPEAT 0 with its required positive interval; missing pair members, negative count, nonpositive interval, fractions and limit exhaustion reject atomically.

Runtime date-only zone choice, DST trigger application, missed/expiry/cancellation rules, private recipient state, activation authorization and durable delivery require later decisions/tests; source preservation does not choose implicit server/device timezone or UTC fallback. Future planners must enforce supported calculated instants. Reject snooze/RELATED-TO, PROXIMITY, nested components, AUDIO/EMAIL/custom actions, attendees/attachments and unprofiled properties/parameters. No silent stripping or auto-arming of an alarm-bearing file. Concrete model/limits remain under draft review.

Validate sparse/annotated source state, DTSTART/DUE anchors (including due-only and inherited timing), absolute triggers on undated tasks, repeat/default forms, exact boundaries/BigInt arithmetic on VM/Chrome, component/aggregate caps, duplicate UIDs, semantic round trips, occurrence matching and explicit unsupported-action/extension rejection. See [RFC 5545 alarms](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.6.6), [TRIGGER](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.6.3) and [RFC 9074](https://www.rfc-editor.org/rfc/rfc9074.html).
