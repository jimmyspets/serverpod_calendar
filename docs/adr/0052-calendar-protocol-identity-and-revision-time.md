# ADR 0052: Calendar protocol identity and revision time

Status: **Accepted separate generated UID and automatic calendar timestamp; implementation mechanics under review**. Date: 2026-10-21.

## Confirmed decision

The maintainer selected a separate stable, server-generated protocol UID for each native calendar, distinct from its API UUID, future imported-source identities and aggregate-feed identities. Maintain a whole-second UTC LAST-MODIFIED automatically when the calendar's own metadata, settings or associations change. Event/task changes and future publication have separate change-tracking requirements; this native timestamp alone is not a full exported-calendar validator.

[RFC 7986 sections 5.3–5.4](https://www.rfc-editor.org/rfc/rfc7986.html#section-5.3) define persistent calendar UID and calendar LAST-MODIFIED. Generate random UUID text without user, host or domain information. Native generation does not approve UID reassignment, import deduplication or replacement of imported source identity. Native API UUIDs are not iCalendar UIDs or access credentials.

## Implementation choices

Add a non-null random UUID column with a unique index to active calendar data, generated by the pinned Serverpod model/database defaults. Existing active rows receive independent random UIDs on upgrade; preserve identities, content and revisions. There is no UID update command. Deletion removes the active UID with other payload; do not add it to the minimal deletion marker or expose deleted calendars.

Expose immutable `CalendarProtocolIdentity(uid, lastModified)` only through a separate `protocolIdentity` disclosure group; null means unrequested/denied. Trusted host snapshots include both values. Existing commands cannot assign either value, and UID disclosure alone grants no authority. The example shows these fields read-only.

Use the existing precise active `updatedAt` as the persisted source of native revision time. Project it to UTC with fractional seconds removed for LAST-MODIFIED; preserve the original precision for existing native diagnostics. Use the shared PostgreSQL clock after authorization/locking for creation and successful changes, clamped to the previous value so clock correction cannot make a calendar timestamp go backwards. Do not add artificial future seconds: multiple revisions in one second may share LAST-MODIFIED. Expected revisions remain authoritative; timestamps are not concurrency tokens, ETags or proof of completeness. Accepted no-op writes still advance the revision and touch time according to existing command behavior.

Reads, denied/stale/invalid commands, failed dependencies and rolled-back writes do not touch identity/time. Association attach/detach/contribution, name-only edits, native presentation, protocol text/color, supplemental metadata and availability settings share the same timestamp path. Deletion retains only the separately approved marker time; no new deleted protocol view is added.

These are administrative revision timestamps, not scheduled civil times; they do not expand the ordinary calendar date profile. Future imported LAST-MODIFIED values need separate preservation. Event/task additions, edits and removals, projections, selection and serializer changes must participate in eventual publication change tracking; do not emit this native timestamp unchanged as proof that a full VCALENDAR is current.

## Validation and limits

Verify fresh/upgrade schemas, stable distinct UIDs across hosts, independent disclosure/snapshots, automatic timestamps on all mutation families, nondecreasing time, same-second revisions, denied/stale rollback and payload deletion. Extend generated-client and Flutter journeys without creating a wire exporter or feed route. Record actual results in the validation guide. Production coordinated host policies, retention and full publication lifecycle remain separate work.
