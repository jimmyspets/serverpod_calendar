# ADR 0097: Create-only task import contract

Status: **maintainer-confirmed create-only/permission/version/baseline choices; concrete service and storage mechanics proposed**. Date: 2026-10-23.

The maintainer selected create-only task series import, exact active protocol UID conflict within the destination calendar, copies into another calendar, preservation of each master/occurrence's source protocol versions/omissions, and one private normalized source baseline in active storage for future conflict detection. Native API UUID/revision and database audit time remain separate. Source participants never assign anyone or establish host authority. Alarms/snoozes remain unarmed definitions. No source progress or acknowledgement invents native history.

Require a separate task-import permission, task-create permission for every proposed series, and change-task-progress permission whenever STATUS/PERCENT-COMPLETE/COMPLETED occurs on a master or occurrence, including explicitly neutral values. A supplied COMPLETED or participant/acknowledgement claim cannot bypass authority through its source spelling. Use trusted actor/scope and actual destination parent, immutable complete validated proposals, declared policy guarantee and final authorization before atomic persistence. Receipts are minimal and independently authorized, not a grant to read imported fields.

Parse strict supported VTODO input as one bounded batch. Require matching in-file masters and supported named zones/full-horizon evidence. Reject unsupported data, duplicate source identities, exact active destination conflicts or any unavailable/denied member without partial creation. Digest candidates remain bounded and exact text comparisons authoritative. Never fetch URLs/attachments/directories, resolve relationships/participants to host identities, arm alarms, send mail or execute scheduling methods. Existing source progress semantics follow ADR 0096: independently optional fields and complete master defaults only when an original has no own progress component.

Extend storage to retain the full currently supported decoded task profile before adding the endpoint: annotations/groups, participants, unresolved relationships, inert attachments and unarmed DISPLAY/snooze definitions, source component presence/timing forms and independent versions. Preserve approved source distinctions rather than flattening overrides or replacing missing fields. Use the existing event/availability semantic preservation boundary: source components are retained as decoded meaning, with future envelope/timezone presentation regenerated from pinned data; original file bytes and unused/decorative zones are not an archive. Exact representation, disclosure groups, native edit retention/versioning and bounded local initialization require a concrete storage ADR and tests.

The private baseline may retain source values removed by a subsequent native edit. Never expose it through ordinary task views, host policy snapshots, receipts, cursors or current-state exports; deletion scrubs it with active content. It is not an authorization/freshness proof. Native/legacy tasks without a prior import do not receive a fabricated import baseline. Imported non-recurring tasks retain an unknown prior-progress checkpoint, even when current progress looks neutral: a file cannot prove that a task has never had progress. Converting such a task to recurrence requires a future explicit adoption/reconciliation operation; import must not infer a clean history. Replacement/adoption, upstream synchronization, task scheduling, native alarm activation/runtime and extended metadata remain separate.

Validate authorization/final revocation and rollback, source shape/progress/version preservation, no history/assignment/activation side effects, exact UID copies/conflicts/races and parent deletion across hosts, limits and strict input rejection, disclosure-safe receipts, baseline privacy/scrubbing and generated-client/Flutter import journeys. These are planned endpoint acceptance conditions, not implemented import evidence.
