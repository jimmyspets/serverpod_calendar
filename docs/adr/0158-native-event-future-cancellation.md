# ADR 0158: Native event future cancellation and cutoff restoration

Status: **Proposed. The maintainer confirmed cancel-all/preserve-exceptions and clear-entire-cutoff/preserve-individual-cancellations policies. Concrete storage, API and integration mechanics await explicit approval.**

## Context and evidence

Accepted ADR 0157 implements pure DATE/UTC/named-zone `cancelledFrom` cutoffs. Its implementation PR #145 passed grouped local checks and full hosted inspect/runtime CI. No native adapter supplies that cutoff yet. The maintainer confirmed that native restoration should clear the entire saved cutoff using current retained timing/content, while keeping individually cancelled occurrences. Historical snapshots and partial suffix restoration are not selected for this increment.

Inspected native override validation/actions, protocol lifecycle/source baselines, occurrence preview/pages, busy and alarm candidates, worker timing digests/action checks, event export and existing publication boundaries. Existing state already separates override JSON from replaceable master content, validates every retained original, and uses the shared scope transaction/revision fence. This batch should integrate native behavior across these consumers together rather than expose storage that availability or workers ignore.

[RFC 5546 CANCEL](https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.5) and [RFC 5545 original identity/RANGE](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.4.4) supply protocol context. The cutoff, commands, native protocol bookkeeping and restoration rules below are application policy; no incoming/outgoing scheduling reconciliation or interoperable range-cancellation encoding follows.

## Proposed model and actions

Add nullable `cancelledFrom: CalendarEventTiming?` to `CalendarEventTimingOverrides` in its existing nullable event active-data JSON column. It is a start-only original identity in the exact event kind/zone, not a replacement span. Retain single/future timing and content/source metadata unchanged. Expose it only with the existing timing disclosure group and include it in immutable current/proposed host snapshots. Null/absence means no cutoff. Do not rewrite legacy rows merely on read; preserve legacy source-baseline bytes and omissions. No new table, SQL column/index, migration, retention expansion or cancellation-history store is proposed. Upgrade writers/clients together; old writers cannot safely preserve an unknown JSON field.

Add `cancelFuture` and `restoreFuture` to the by-name `CalendarEventOccurrenceAction` enum. Reuse `changeOccurrence`, `CalendarEventOccurrenceChange`, existing event receipts and expected revision; neither action accepts replacement timing. Require an explicitly recurring event profile (RRULE or explicit additions/PERIODs), an exact ordinary original and the existing bounded membership checks. Charge a non-null cutoff as one of the combined 128 override slots, even when co-located with a single/future timing anchor. Keep existing collision rules between timing components.

`cancelFuture` sets the cutoff to the earlier of the current cutoff and requested original. A later cancellation cannot silently restore an already cancelled portion. Repeating the same/later cancellation is an accepted revision-checked unchanged save under existing native write semantics. `restoreFuture` requires the exact currently saved cutoff original, rejects missing/different targets, and clears only that cutoff. It retains all current timing/content, source annotations and single cancellation flags. It does not reopen a cancelled master. The event UUID, protocol UID, recurrence pattern and parent calendar metadata stay unchanged.

Both actions require existing `changeEventStatus` authority; the exact typed action and current/final proposed overrides let hosts distinguish single/future cancellation and restoration. Do not substitute `updateEvent` or trust client parentage. Preserve preliminary authorization before target-specific errors, final checks, declared coordinated/external guarantees, trusted scope and separately authorized receipt disclosure. No idempotency-key table or historical command receipt is added: uncertain native writes require refresh and expected-revision reconciliation, as with existing single actions.

Ordinary master/timing/content edits preserve and revalidate the cutoff, rejecting orphaning recurrence/profile changes. Clearing timing does not clear cancellation. Existing single lifecycle actions continue to edit their own flag; clearing a single flag under the cutoff does not restore its effective occurrence. The example must distinguish individual flags from effective future cancellation. No bulk replacement/import helper may accidentally omit the new field.

## Protocol state, sources and transactions

An actual cutoff change advances the native master protocol SEQUENCE/timestamps using the existing nondecreasing whole-second rule; unchanged cutoff saves keep protocol state unchanged while native API revision/audit/scope semantics remain. Unchanged retained occurrence components keep their independent versions. The cutoff is not a fabricated VEVENT occurrence component and allocates no invented source version. Sequence overflow must roll back completely.

Include the cutoff in current normalized native-state comparison so an imported/adopted series with a local cutoff is dirty against its accepted source baseline. Keep accepted source baselines source-only and mask-free; do not overwrite them or insert a cutoff into accepted invitation checkpoints. Native cancellation/restoration does not accept/dismiss a notice, change attendee responses or send mail. Existing source replacement/application paths retain their clean-series protection. Restoring a cutoff does not undo the separate protocol changes made by a local write or automatically establish a clean source baseline.

Write cutoff/revision/audit/protocol state, scope/feed generation and alarm invalidation under the existing scope transaction. Include current cutoff state in durable alarm timing digests and invalidate outstanding plan/lease generations on actual timing-state changes. Preserve rollback, stale-revision and database fencing behavior across independent hosts. Parent/event deletion already scrubs active overrides; retain minimal identity-marker rules.

## Queries, availability and reminders

Pass the cutoff into both pure active-expansion adapters. Ordinary previews omit masked occurrences; their saved cutoff remains visible to authorized timing readers for restoration. Calendar occurrence pages respect `includeCancelled`: false returns active originals, true materializes retained timing with effective cancellation marked. Preserve moved-in/original identities, sort/cursor/disclosure rules, complete spans and existing candidate/materialization caps. Retained geometry that cannot be represented or exceeds limits fails the query without partial coverage; do not invent clipped timing.

Complete busy projections omit masked originals, including later singles/ranges; calendar, subject and common-free results must use that complete projection rather than filtered detail pages. Maintain tentative/status/transparency and complete-or-unknown rules.

Relative alarm candidates omit masked originals. Fresh planner/dispatch/retry/snooze/reconnect checks must also reject an original covered by the cutoff, so already queued reminders cannot escape through stale plans or live-delivery recovery. Retain personal definitions and occurrence acknowledgement/dismiss/reset history; no automatic acknowledgement or source-alarm arming follows. Restoration uses current retained timing and the existing grace, expiry, deduplication and action rules, without resetting private actions or resurrecting terminal deliveries. Absolute alarms retain their established `item` identity and whole-item behavior; a suffix cutoff does not turn them into occurrence alarms. Whole-item CANCELLED status continues to suppress them.

## Export, publication and example

Until a faithful wire mapping is reviewed, reject a selected masked series in authenticated VEVENT export, subscription projection and new REQUEST publication. Do not truncate recurrence, drop later exceptions, publish a false whole-master cancellation or silently omit the series. Feed generation must change on saved cutoff changes, and an old validator must not produce 304 while the current selected projection is unsupported. Restoration may make a series representable again, subject to every existing export/policy/profile check. Historical scheduling retries/CANCEL/restore operations that use an already published snapshot continue preserving unrelated native drafts; they must never clear the cutoff to manufacture a supported REQUEST.

Flutter adds explicit cancel-future and restore-saved-cutoff controls using original identities, saved revision and current disclosure. Explain that timing/content stays retained, individual cancellations remain, and local actions send nothing. Refresh after uncertain outcomes/stale revisions. Display effective cancelled state separately from individual flags; retain ordinary timing/content editors and inherited metadata.

This batch does not implement incoming range CANCEL application/master composition, organizer range CANCEL messages, range replies, standalone future-cancellation wire import/export, tasks/opening cancellation, partial restoration or real transport. Those remain original-scope follow-up work.

## Validation and acceptance

After explicit model/ADR approval, regenerate sources using the pinned toolchain; no hand-edited generated files. Test DATE/UTC/named zones/DST, earlier/PERIOD additions, co-located/later/moved exceptions, repeated/earlier cancellation, exact full-cutoff restoration and preserved individual flags/content/versions. Cover orphan/profile/slot rejection, hidden timing/source groups, independent/final lifecycle authority, immutable host context, stale races/overflow and complete rollback. Verify legacy nullable reads/source baselines remain unchanged.

Exercise active/cancelled pages, cursor invalidation, free/busy and common-free, planner digest/generation/lease invalidation, stale automatic/repeat/snooze/live recovery suppression and restored action/dedup/expiry behavior. Check unchanged absolute item alarms explicitly. Verify export/REQUEST/feed rejection and no stale 304, then restored representability. Run generated-client/Flutter journeys and actual two-host cancellation/restoration races plus worker loss/recovery with synthetic data. Use focused tests during development, broader grouped checks at completion and full repository CI before readiness; commit only the complete agreed batch.
