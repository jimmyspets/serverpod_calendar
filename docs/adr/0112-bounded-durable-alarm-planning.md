# ADR 0112: Bounded durable alarm planning and handoff

Status: execution policies and persistent storage boundaries confirmed; implementation and validation in progress. Date: 2026-10-24; storage/retention confirmation: 2026-10-25.

The next batch should add pure trigger calculation, explicit arm/disarm and durable bounded planning/handoff. Existing definitions remain unarmed until that implementation passes. Imported alarm adoption, private source publication and mobile providers remain separate. Native actions and the reusable notification/connected-client path require their own integration before claiming the first-release runtime complete.

Confirmed: host-authorized explicit arm/disarm; rolling 30-day planning/refill; configurable late eligibility with a 15-minute example default; completion/cancellation signals suppress task delivery without rewriting source fields; acknowledge/dismiss/snooze suppress repeats for that original occurrence; snooze acknowledges the original and creates one replacement; recovery selects the latest eligible overdue firing per definition, recording other eligible firings suppressed and older ones expired.

## Confirmed persistent boundaries

Use three server-only tables plus additive definition fields. No source baseline, parent text or provider credential is copied into work rows.

| Model | Stored fields |
| --- | --- |
| Existing personal definition | Add `armed=false` and internal `generation=1`. Generation changes invalidate work; parent-driven replanning does not alter the API revision or protocol state. |
| `CalendarAlarmPlanRecord`, unique alarm ID | UUID, alarm ID, trusted scope, generation, normalized timing/lifecycle digest, exact window start/end, planning status/reason, `dirty`, next scan, last completed time, lease owner/until/fence. Complete ready window or explicit needs-attention/unavailable; no cursor/partial coverage. |
| `CalendarAlarmFiringRecord` | UUID also used as stable handoff request ID, alarm/generation/original key, normal-or-snooze kind, repeat ordinal, snooze revision, due/expiry, pending/suppressed/expired/accepted state and reason, next attempt/count, accepted time, lease owner/until/fence and audit times. Unique logical candidate identity. Durable retry/handoff state lives here, not in a duplicate outbox table. |
| `CalendarAlarmActionRecord`, unique alarm/original key | UUID, alarm ID, exact original key, API revision, acknowledgement/dismissal instants, pending snooze UTC/revision and audit times. State survives timing/settings edits and removed originals, without retargeting or granting authority. Explicit reset clears it. |

Use indexed due scans and shared database time. Proposed defaults are 30-second fenced leases, bounded scans/claims, 1,000 firings per complete definition plan (host configurable), 100 claims per sweep and a separate bounded retained-history capacity. No process-local correctness state or test clock in production. Terminal firing/delivery history has host-configurable retention, with 30 days as the example default, then bounded pruning. Action state remains separate until explicit reset or alarm deletion; pruning terminal history must never rearm an acknowledged original. Pending, leased or retryable work is not terminal history.

Parent writes record dirty/wake state in the same transaction as the existing scope generation change; private settings/arm/action writes invalidate their own generation transactionally without advancing public scope generation. Dirty plans cannot dispatch. A refreshed timing/lifecycle digest avoids replay after unrelated parent text changes. Claim leases are short transactions; computation runs outside the locks and commit rechecks the owner/fence, unexpired lease, generation, actual parent and authorization under the trusted scope lock. Parent deletion removes firing/action/plan rows before the definition, including every recipient, without consulting private-alarm permissions.

The host installs an explicit background-recipient policy with distinct plan/dispatch operation context and a delivery port with current-generation/access/expiry revalidation during downstream retries. Missing runtime configuration fails closed; no request identity is impersonated and stored recipient references never grant authority. A delivery port's acceptance is not display or acknowledgement. Logical request IDs survive retries, and consumers must deduplicate them; acceptance followed by a crash can still produce transport redelivery. The reusable notification module/connected example must demonstrate this contract before end-to-end delivery is claimed.

Database lease/fence checks must survive two independent hosts, process loss, duplicate wake-ups and stale owners. Claim briefly, calculate outside locks, then reacquire the trusted scope and revalidate current parent/configuration/recipient authorization before committing. Final delivery checks repeat after queue delays and retries. The host supplies a dedicated background recipient/access decision; do not impersonate a request session or treat a stored recipient as authority. Declare coordinated versus external fresh-check guarantees and the unavoidable after-check handoff race.

Relative calculations use the effective original timing, explicit DATE midnight zone, calendar units before elapsed clock units and existing RFC gap/fold rules. Explicit exclusive endpoints may be anchors for a negative offset, but the resulting firing must remain ordinary supported UTC time. Nonexistent generated originals are skipped. Every effective occurrence needs fresh anchor, zone-coverage, lifecycle and arithmetic validation; current-master compatibility alone is insufficient.

The maintainer selected a complete 30-day target or explicit needs-attention, with a configurable initial budget of 1,000 firings per definition. Do not expose or dispatch a partial plan. Automatic repeats count against the budget before recovery coalescing. Preserve acknowledgement/dismissal for the same alarm/original across parent timing and setting edits until an explicit reset; removed originals are never retargeted. Snooze requires a future whole-second UTC instant no more than seven days ahead of shared database time and replaces the existing pending snooze rather than creating chains. Concrete per-work limits and claim mechanics are documented in [the scoped implementation guide](../durable-alarm-planning.md), without claiming that every implementation detail is a separately approved product decision.

Persist metadata/definition changes, generation invalidation and pending-work suppression transactionally. Shared edits must not depend on private permissions. Deletion scrubs private content/work under the same parent transaction. Arming must not convert imported alarms or create notifications for other recipients. No exactly-once human delivery, recall after acceptance or acknowledgement inferred from transport is promised.

The maintainer approved the three-table storage boundaries and armed/generation fields on 2026-10-25, together with the separate terminal/action retention policy. Concrete code must enforce the documented logical identities and cancellation/retry fencing; approval is not runtime evidence. Test UTC/DATE/zoned offsets, endpoints, DST gaps/folds, repeats, moved/cancelled originals, task progress, policy revocation, late/coalesced/expired work, conflicting workers, stale fences and crash windows with controlled shared time and synthetic adapters.

Serverpod future calls are scheduling wake-ups rather than the sole durable state. The implementation verified and generated their interfaces against the pinned SDK; see [official future-call documentation](https://docs.serverpod.dev/concepts/scheduling/future-calls). Scoped worker evidence is recorded in the validation guide. It does not establish a functioning notification module or complete alarm runtime.
