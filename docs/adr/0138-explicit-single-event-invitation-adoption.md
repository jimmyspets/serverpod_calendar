# ADR 0138: Explicit single-event invitation calendar adoption

Status: **Accepted by explicit maintainer approval on 2026-10-29 for the complete adoption batch and binding storage/API/retention design. The scoped implementation and phased complete-batch validation finished on 2026-10-29; see the guide and validation record.**

## Context and selected boundary

Accepted ADR 0137 implements trusted non-recurring REQUEST intake and private review/dismissal without calendar mutation. The next batch adds one explicit Add to calendar action for a reviewed current source. It creates a local event and stable link; it does not accept participation, send REPLY/REQUEST, reserve resources exclusively or grant organizer authority. Existing-meeting source updates, moving/copying the link, recurrence, CANCEL and mail follow separately.

The confirmed one-event policy applies to the logical scope/recipient/exact UID/organizer correlation, not only the lifetime of an inbox UUID. Ordinary file imports remain independent and do not establish this link. Inbox source expiry must not make the same invitation silently create another linked event.

Primary sources checked 2026-10-29: [Serverpod model guidance](https://docs.serverpod.dev/concepts/data-and-the-database/models), against the pinned 4.0.4 generator, and [RFC 5546 REQUEST/message sequencing](https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.2). The link lifecycle and permission/retention limits below are application choices, not new RFC requirements.

## Approved request and creation

Add a native request containing invitation UUID, expected invitation revision, exact selected current source UUID, destination calendar UUID and expected calendar revision. Resolve the actual actor/recipient and actual source/parent in the same trusted host scope. Require a pending, readable, current non-recurring source for first adoption; a manually dismissed version or unavailable/expired source cannot be newly adopted. Input fields are frozen before awaits, with bounded exact revision/UUID validation.

The explicit action validates a temporary ordinary VEVENT document from the complete accepted REQUEST source, removing only the METHOD envelope field. It preserves all supported component properties/omissions/participants/version/timing and uses the existing ordinary wire/storage conversion; unsupported conversion rejects atomically. Envelope/zone regeneration and semantic preservation follow existing authenticated event-import policy. Removing METHOD here is an explicit scheduling-to-local-copy projection, not a way to turn arbitrary input into a supported invitation.

Create a server-UUID event with the source protocol UID, source version/omissions, imported origin and one private normalized import baseline. Record database audit/API revision separately. Source participants remain inert, no alarms are armed, and imported origin does not acquire native organizer publication authority. Source STATUS/TRANSP and existing native omission defaults remain as under ordinary event import. Consequently the explicitly added event can contribute occupied time under the ordinary calendar rules; adding it is still not a participation acceptance or exclusive reservation.

Reject an exact protocol UID already active in the destination calendar unless the existing approved link proves this is a retained retry. Never adopt an arbitrary preexisting event, retarget an unrelated copy or infer authority from UID/organizer text. A move or separate copy requires a later profile. Reuse/refactor internal validated event-import persistence so event, baseline, link and inbox state commit in one scope transaction; do not nest public import transactions or silently change ordinary import behavior.

On successful first adoption, mark only that selected inbox version reviewed/dismissed and advance its revision atomically with the new event/link. A concurrently newer REQUEST causes expected-source/revision rejection when it wins first; if adoption wins first, a later newer source can reopen private review under ADR 0137, but cannot automatically update or create another event. Existing native event edits remain local and retain their import baseline for future conflict detection. Generic file-based source replacements on linked events reject in this first profile, including hosts without active invitation ingress; ordinary local edits/deletion remain supported. A later explicit reconciliation policy can change the adopted baseline. Unlinked ordinary import/replacement behavior is unchanged.

## Approved host authority

Add independent invitation adopt/read-link operations. Require ordinary inbox summary/source authority and explicit host approval of the stored source for the current origin/recipient mapping; a persisted address alone is insufficient. Require destination-calendar import/create permission and the applicable event lifecycle/source gates. The first profile also requires full ordinary event disclosure plus event source-read authority for the resulting linked event, so it cannot create an invisible local copy or return a hidden event reference. Hosts may map gates to common rules; blind creation/redacted adoption can be reviewed separately.

Host contexts identify the actual inbox/source, normalized REQUEST/digest, selected current version, actual destination calendar, allocated event/link IDs, complete validated proposed event/source/version/origin, current link/event where present and final receipt. Preserve current versus proposed state and native versus source versions. Preliminary approval precedes private link/conflict lookup; final checks run after proposed writes within the transaction and roll everything back on denial/unavailability. Declare coordinated/fresh-check guarantees without downgrade; external checks retain their after-check revocation race.

Keep recipient resolution/current actor policy-epoch checks and the existing shared scope lock. All participating hosts must enforce link/correlation semantics even if their optional invitation runtime is disabled for user ingress. No process-local lock/cache/sticky routing may establish uniqueness or permission. Cross-scope adoption remains unavailable in the initial profile.

## Approved private binding table

Use **CalendarInvitationLinkRecord**, server-only, containing server link UUID; trusted scope/recipient; exact source UID/organizer plus fixed correlation digest; original inbox/source UUID references and source digest/SEQUENCE presence/DTSTAMP; destination calendar and native event identity UUIDs; original request digest; created event/inbox revisions and database adoption time. There is no copied source body/title/location, provider credential or address-to-host-user directory.

Use unique scope/recipient/correlation-digest and scope/recipient/original-inbox keys, with retained-value verification; use unique native event UUID to prevent accidental many-link association. Raw source identifiers are not index keys. Calendar/event references target identity rows so ordinary active payload deletion can still scrub event content. Inbox/source UUIDs are historical references rather than foreign keys: ADR 0137 retains its independent source/body/marker cleanup and caps. The binding survives that cleanup and still enforces one logical link.

The immutable binding is also the native creation receipt; no separate command-receipt table is proposed. Hash the complete validated original request (source/entry IDs, expected revisions and chosen calendar) in an unambiguous encoding. A matching retained request can return a flat immutable receipt (link/event/calendar/source identities, created revisions and adoption time) after fresh authority checks. Different input for an existing correlation rejects without changing the link/event, including a newly received inbox UUID for the same logical invitation. Retained requests do not reapply source content, reset local edits, re-dismiss a later version or recheck old revisions as if creating anew.

When the original inbox body has expired, retained retry context explicitly reports that historical content is unavailable and supplies the protected binding/version/reference plus actual current native event/source state. Still require all applicable permissions and explicit host approval of that descriptor; do not invent old source content or silently substitute a weaker check. A host requiring unavailable original evidence can fail unavailable. No source content is returned in the flat receipt.

Default first-profile capacity is 1,024 bindings per recipient, with lower validated host limits allowed; creation at capacity fails atomically while exact retained requests do not allocate another row. Keep active bindings and content-minimal link markers after native deletion until a separately reviewed removal/purge policy is available; this is not a selection of permanent retention for release. The bounded cap and missing purge/relink flow are explicit initial limitations. Native deletion scrubs active event data/personal alarms as before, without restoring/recreating the linked event. An inactive/deleted linked event makes adoption/read-link unavailable rather than making a new copy. Calendar identity deletion/purge dependencies must be verified against those retained minimal references; no implicit detach/cascade follows.

## Queries and example

Add independently authorized linkage lookup from a known invitation and a flat adoption receipt. Resolve any actual linked calendar/event before exposing identity; withheld/unavailable linkage is an explicit error, never a false unlinked result. The binding can resolve an original retained request even after inbox cleanup; a newly received equivalent invitation resolves through exact correlation. No global UID search or private-target discovery follows.

The private review screen adds an explicit calendar selector and Add to calendar action for a current unlinked source. Explain that a local copy may block time according to STATUS/TRANSP and sends no reply. Keep request/body identity on uncertain retries. Show a known existing link instead of offering another copy; newer incoming versions are review-only until reconciliation is implemented. Stale source/calendar revisions require reload, never silent overwrite. The event remains an imported-origin local copy, not an organizer-controlled native meeting.

## Alternatives and acceptance

Allowing independent copies conflicts with the selected one-event policy and complicates future updates. Reusing ordinary import without a binding cannot recover a lost response or distinguish a matching source UID from an unrelated calendar copy. Pinning all raw inbox bodies forever would expand ADR 0137 retention; the minimal binding and explicit historical-unavailable descriptor keep the original queue lifecycle separate. A second command ledger is unnecessary for one immutable creation result but may be needed for later update workflows.

Before implementation, review the binding model, immutable receipt/context/query fields and exact event write-helper adaptation. Test source/version/annotation/DATE/UTC/named-zone preservation, native/imported origin separation and unchanged participation/outbound/alarm state; independent source/create/import/read/link permissions and final rollback; active UID conflicts, quotas/overflow and scope/recipient isolation; exact retry after source/native changes and inbox expiry; different destinations/new equivalent inbox UUIDs; deleted links and no recreation; native deletion payload scrubbing; two real hosts racing adoption, import/UID conflict, source updates and parent deletion; actual before/after-commit process loss; fresh/upgrade schema and generated-client/Flutter journeys. Run focused checks during feature work, then full batch checks before one code commit. Mail, response/adoption authority, source replacements/relink/removal and release interoperability remain required separate work.
