# ADR 0095: VTODO snooze source profile

Status: **scoped implementation of confirmed bounded sibling snooze profile; concrete mechanics remain under draft review**. Date: 2026-10-23.

The maintainer selected snoozes with their own UID, an absolute UTC trigger and exactly one SNOOZE link to an acknowledged original alarm in the same VTODO. Detached links, snooze chains and repeating snoozes reject initially. All values remain unarmed source definitions; no native acknowledgement, recipient, activation, consent or delivery is inferred. This extends ADR 0094 only for the selected wire slice.

Propose an optional decoded `snoozeTargetUid` on immutable `IcalendarDisplayAlarm`, with `isSnooze` and original RELATED-TO syntax retained in the source tree. Require explicit RELTYPE=SNOOZE, a nonempty exact text UID target, a distinct nonempty own UID, absolute whole-second UTC TRIGGER and absent REPEAT/DURATION (even explicit REPEAT 0 rejects). Require the target UID to resolve to a nonsnooze sibling with source ACKNOWLEDGED present in the very same raw VTODO component. Component order is immaterial; original alarms may precede/follow the snooze. Existing per-task unique alarm UID checks prevent ambiguity. Cross-task, master-to-override borrowing, self links and chains reject.

Progress occurrence components retain ADR 0089's content policy: absent entire alarm lists inherit in linked projections; explicit complete lists must match order/meaning, including snooze target and source acknowledgement/UID. A raw override cannot supply only a snooze and borrow its original from the master. Target text charges the existing file-wide task metadata budget; existing alarm/file/count/time limits remain active. Unknown relation types/parameters, multiple RELATED-TO properties and incomplete graphs reject the whole file.

Source ACKNOWLEDGED is preserved, never created or trusted as a verified host action. Structural validation does not reconstruct the original firing occurrence or infer chronology from acknowledgement timestamps; a later acknowledgement can legitimately postdate a source snooze trigger. Actual snooze authorization, original occurrence, timing, cancellation/expiry, recipient privacy, durable execution and notification integration remain separate. No firing instants or mutation are produced. Other alarm relation types, event alarms and native snooze remain pending. The stricter source profile is an application boundary, not a blanket RFC restriction.

Validate ordering, exact decoded UID identity, missing/cross-component targets, missing acknowledgement/own UID, relative triggers, repeats including zero, self/chained links, duplicate relations/UIDs, immutable round trips, occurrence omission/matching and shared budgets on VM/Chrome. See [RFC 9074 §7](https://www.rfc-editor.org/rfc/rfc9074.html#section-7). Concrete mechanics remain under draft review.
