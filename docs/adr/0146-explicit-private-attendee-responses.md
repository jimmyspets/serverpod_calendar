# ADR 0146: Explicit private attendee responses with durable synthetic delivery

Status: **Accepted by explicit maintainer approval on 2026-10-30 for the complete response workflow, three tables, limits and worker mechanics. Scoped implementation and complete local batch validation are complete.**

## Context and evidence

The maintainer selected explicit Accept/Tentative/Decline responses independent of Add to calendar and Apply update. Declining must not require an event. Receipt, ordinary editing, adoption, source application and dismissal send nothing implicitly. Existing invitation intake is a private, authenticated, non-recurring REQUEST/CANCEL profile; [ADR 0145](0145-host-mime-native-ingress.md) adds its host MIME bridge, not attendee response sending.

[RFC 5546 section 3.2.3](https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.3) and [section 2.1.5](https://www.rfc-editor.org/rfc/rfc5546.html#section-2.1.5) define event replies and their ordering: a reply identifies its original UID and replying attendee, echoes the relevant source sequence, and uses DTSTAMP to order otherwise matching responses. This proposal emits a deliberately minimal reply; delegation, counter-proposals and additional property changes are separate profiles. The strict command-clock rule below is project policy, not an RFC requirement that every timestamp be globally unique. Source inspection confirms that current organizer delivery requires a native event binding and an organizer sender; reusing that binding for an unadopted attendee invitation would misrepresent the role and parentage.

## Proposed native command and independent state

Add an explicit authenticated Send response command for the current host-resolved private recipient. Inputs are invitation UUID, expected invitation revision, exact current source UUID, expected response-state revision (0 when absent), client command UUID and one of ACCEPTED/TENTATIVE/DECLINED. Clients supply no attendee address, organizer route, scope or origin proof. Read-source and separate read-response/send-response permissions are required. The request must select a currently retained, non-cancelled non-recurring REQUEST, not a historical/stale source or CANCEL notice. New-source/recipient/revision changes during the transaction reject; no automatic rebasing.

Persist the personal choice and outbound intent atomically under the existing shared database scope transaction. Do not edit the invitation source/revision/dismissal state, calendar event, applied-source baseline, link, task, alarm, feed generation or organizer-owned attendee roster. No calendar adoption is required, including when declining. An old recorded response remains explicitly labelled with its source basis when a newer request arrives; it is never treated as automatic acceptance of that newer request.

Exact retained command retries compare all original criteria, reauthorize, return the original immutable command receipt and perform no writes or reactivation—even after a newer source/response exists. Receipt retries are protected historical access, not new sends: current-source eligibility applies to new commands and dispatch, while retry policy sees both actual current state and retained basis with an explicit retry marker. Different content under that command UUID rejects. A new UUID is an explicit new send, including a deliberate resend of the same choice; it advances the response-state revision and supersedes older pending work. Concurrent new commands with the same expected state revision have one winner. Returning a command receipt proves only atomic queue acceptance; current delivery status is queried separately.

## Proposed reply and clock profile

Generate one VEVENT with source UID, a server/database-clock whole-second UTC DTSTAMP, the source's exact optional SEQUENCE, the organizer address and one host-verified ATTENDEE carrying the chosen PARTSTAT. Preserve omitted versus explicit zero SEQUENCE; never increment the organizer's sequence. Use the existing pure syntax/iTIP validators and selected iMIP mailbox profile; reject older stored sources that cannot be represented without changing them. Emit no copied summary, timing, comments, participant names/links, attachments, alarms, recurrence or other optional source metadata. This is a new scheduling projection, not canonical import/export or a rewrite of source data.

Allocate DTSTAMP from actual database time. For a later new send on that private invitation, require the whole-second database time to be strictly later than its previous allocated response stamp. If it is equal or earlier, return temporarily unavailable without writes; the same command may be retried when the clock advances, with fresh checks. Do not invent a future timestamp, round user input or change SEQUENCE to break a tie. Retained retries reuse the exact stored payload/stamp. This conservative whole-second rule also makes a clock rollback visible rather than manufacturing ordering.

## Proposed host authority and dispatch

Keep the existing private recipient resolution and raw-source authorization for commands. Add a dedicated response host adapter which resolves a verified attendee identity and approved organizer route and authorizes the complete immutable outgoing message/digest. Enforce exact agreement with the current recipient and source participant/organizer addresses; source claims alone cannot establish either role. The policy context contains trusted actor/recipient/scope, actual invitation and source/version descriptors, current response state, validated proposed state, exact outgoing message/digest and approved route/authority references. There is no fabricated native calendar parent for an unadopted invitation.

The background context has no fabricated login/actor. On each claim/submission/retry, revalidate current recipient access, verified attendee identity, source-read/send rights, source body and current REQUEST/version, generation, expiry and approved organizer route. Apply declared coordinated/fresh-check guarantees without downgrade; external checks retain their documented after-check race. A newer source/CANCEL or superseding response withdraws stale pending work. Denied access withdraws; unavailable policy/evidence remains bounded retryable work. Actual in-flight acceptance cannot be recalled and transport ordering is not guaranteed; do not claim exactly-once external delivery.

Use a dedicated attendee-response transport/submission contract with attendee sender and organizer destination; do not call an organizer sender field an attendee. Stable delivery UUID survives retries. Reuse existing generic transport outcome meanings, not event-binding storage. Database-time leases, owner/generation fencing and bounded attempts support competing instances and loss before/after synthetic acceptance. Provider acceptance remains distinct from remote receipt/application or user display.

## Proposed three private tables and retention

| Proposed server-only table | Responsibility and retained data |
| --- | --- |
| CalendarInvitationResponseStateRecord | One UUID row per scope/recipient/invitation entry; choice revision/generation, latest response UUID, last allocated protocol stamp, last choice/source descriptor and bounded terminal outcome/audit metadata. No canonical source rewrite. |
| CalendarInvitationResponseRecord | Immutable command criteria/hash/receipt, source reference/version/digest, exact minimal reply/payload digest, verified authority/route references and choice; mutable delivery/lease/retry/expiry/outcome fields. Exactly one organizer delivery per response. |
| CalendarInvitationResponseAttemptRecord | Bounded per-response attempt identity, owner/fence, times and outcome/receipt codes; no provider credentials or arbitrary diagnostics. |

Existing invitations acquire no choice, state row or outgoing intent on upgrade; missing state is an authorized revision-zero projection. Response state retains its revision/stamp and last personal choice while the invitation entry exists, independently of terminal delivery-history pruning. A latest outcome can remain as a small historical marker, never proof that the organizer received it. Retired response IDs cannot be recreated with stale expected revisions. State is removed only with entry pruning after no retained response/attempt remains; no permanent raw-mail identity or restore feature is added.

Retained response records pin their actual invitation entry/source body through delivery and retry-history retention. Extend invitation cleanup under the same scope lock to honor these references; never silently discard a source needed for reauthorization. Existing invitation source/count/byte caps still apply. Pin pressure may reject admission until eligible records expire; it does not raise the existing hard profile or evict private history. No alternate source snapshot is invented when a reference is missing/corrupt.

Proposed defaults: at most 128 response-state rows per recipient and 4,096 per scope; 32 retained response records per state, 512 per recipient and 4,096 per scope; at most 16 pending per recipient; minimal reply at most 32 KiB, retained reply payloads at most 8 MiB per recipient/64 MiB per scope. Reject overflow atomically. Reuse bounded worker defaults: 8 attempts, 120-second lease, transport timeout at most 30 seconds, 30-second initial backoff capped at one hour, 7-day work expiry and configurable 30-day terminal record/attempt retention. Options may lower admission caps; upper bounds remain explicit. Current active personal state is distinct from terminal history. Maintenance scans/cleanup are bounded and use the database clock.

## Proposed example and validation group

Add protected response-state/activity reads (bounded at 32 retained commands per invitation, no totals), generated command/receipt/view models and separate explicit Flutter Send response controls. Keep Add/Apply/dismiss controls independent. Show queued, retrying, accepted, withdrawn, expired and failed distinctly; never label transport acceptance as organizer receipt. The development/test host verifies its current synthetic recipient and only example.invalid organizer routes.

Compose synthetic outbound REPLY MIME through the already selected enough_mail library, with actual verified attendee From, approved organizer To, deterministic response-UUID Message-ID/date, bounded UTF-8/base64 and exact retained calendar bytes. Do not reuse the ingress fixture's deliberately unrelated headers or constant Message-ID. Preserve protection rejection and no-echo diagnostics. Record only synthetic ignored fixtures; no SMTP/IMAP/POP service, provider credential or real sending is authorized.

Test new/changed-source/revision/recipient denial, independent permissions, final rollback, no calendar/adoption/application effects, source sequence omissions, current clock/equal-second/rollback rules, exact retries, deliberate resend, conflicting criteria and racing choices. Verify source pins/retention/capacity, inactive/pruned sources, generation withdrawal, access revocation, expiry, corruption, competing leases and loss before/after acceptance. Route a synthetic response through the implemented organizer reply handler with separately trusted proof to verify current/stale semantics, without treating MIME headers as proof. Exercise two independent hosts, generated clients and the Flutter response controls. Verify generated fresh/populated upgrades; run focused work then full repository checks before one complete-batch commit.
