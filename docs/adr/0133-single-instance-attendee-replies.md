# ADR 0133: Single-instance attendee replies

Status: **Proposed. The maintainer confirmed accepting any validated published original and using the effective single/range/master component version. The storage, publication-version upgrade and concrete mechanics below require explicit review before implementation.**

## Confirmed direction and source evidence

Accepted [ADR 0131](0131-first-authenticated-attendee-replies.md) and [ADR 0132](0132-recurring-master-attendee-replies.md) implement trusted organizer-side master replies, separate private source/receipt/response storage, ordering, protected review and complete published context. The maintainer selected replies to any original in the published series, including originals without their own component. A single component wins, otherwise the latest applicable THISANDFUTURE component, otherwise the master. The reply itself targets exactly one original; RANGE replies remain separate.

RFC 5546 sections [2.1.5](https://www.rfc-editor.org/rfc/rfc5546.html#section-2.1.5), [3.2.3](https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.3) and [3.7.1](https://www.rfc-editor.org/rfc/rfc5546.html#section-3.7.1) separate component identity, response ordering and original recurrence identity. Primary source checked 2026-10-28. The component precedence and bounded ingress mechanics here are an application profile, not a claim that the RFC prescribes our independent outgoing-version representation.

## Proposed target and authority

Admit one supported nondelegated REPLY component with exact UID and one RECURRENCE-ID, without RANGE, RRULE/RDATE/EXDATE or a second target. Require exact DATE/UTC/named-zone original profile and bounded membership against the validated published series, not the latest native draft. Include explicit additions/PERIOD originals, exclusions, independent replacements and published cancellation state. A moved start never becomes the original identity. Core candidate budgets are shared across membership and projection; exhaustion fails without guessing absence or partial writes.

Resolve effective timing/content from the complete published message and self-contained checkpoint. Host contexts distinguish the requested original, selected source component/anchor, effective occurrence, complete message, canonical published series and current native drafts. Supplied ordinary values must match that effective occurrence; omissions remain absent. A master response does not create instance acceptance, and an instance response never changes master/other-instance state. Individual/whole cancellation admits no active update. New intake requires current published membership or explicit retained published cancellation identity; removed/unproven originals reject without guessing historical membership. Previously stored historical targets remain reviewable and prior, never retargeted. An explicit original query may return no current target version when only retained historical state exists.

Use the same preliminary origin approval before private-history lookup, final transactional approval, native provenance, actual scope/parent/UID/roster and independent response/raw-source rights. Sender/RECURRENCE-ID claims establish no authority. No native content or outbound intent changes follow from intake.

## Proposed outgoing version safety

Independent component counters can collide when an original switches from master/range inheritance to a newly published component. Merely recording a different basis key would prevent carrying an existing response, but could still misclassify an old minimal wire reply with the same numeric SEQUENCE as a new response. Do not silently treat such ambiguity as acceptance.

Introduce a versioned checkpoint profile in the existing snapshot columns. For newly introduced outgoing components, allocate above the maximum prior retained outgoing component version; retain unchanged existing component versions. Include the applicable master recurrence/exclusion profile in range-component version comparisons, so removing and later reintroducing membership cannot silently resurrect an old instance acceptance. Changes to that applicability profile advance the affected outgoing range versions even when their own property lines are identical; this explicitly extends ADR 0126's own-wire-field comparison. Retained original/range identities keep their counters through reset. Preserve the existing cancellation/reopening floors. This prevents a newly selected component from reusing an older effective target version. Overflow rejects atomically. A separate source version and native inheritance remain unchanged.

Legacy checkpoints remain readable for existing flows and master replies. Instance intake requires the new publication profile. A deliberate full Save and notify upgrades legacy bindings by allocating a common floor above all retained versions for the master and components, then resumes independent unchanged-version behavior. It sends an actual newer invitation and reauthorizes the complete outgoing message; no background rewrite or silent adoption is permitted. Legacy partial commands cannot manufacture the upgrade. Existing individual-cancellation and terminal-delivery guards still apply; upgrading does not introduce parallel partial commands or bypass restoration requirements. The upgraded invitation is a changed publication, not an identical no-op; ordinary accepted-write revision/generation rules apply while native content/source versions stay separate. Fresh databases remain allowed, but populated upgrade tests must preserve existing reply/source state as prior.

## Proposed storage, APIs and bounds

Reuse the three reply tables. Add server-derived targetKey (default master) to source and response rows, nullable typed originalStart to source rows, and targetBasisKey (default master) on source rows. No receipt column changes are proposed. For instances, targetKey is a fixed-size SHA-256 key over canonical original kind/value and exact zone; originalStart retains the exact typed point for equality/collision checks. Compare exact originals after every key lookup and reject a digest collision rather than merging or retargeting. targetBasisKey similarly distinguishes master, single and future anchors and is never client-supplied. Derived keys grant no authority. Change the response uniqueness index to meetingId/attendeeAddress/targetKey. Existing rows become explicit master targets; receipt delivery-key and source-digest uniqueness remain unchanged. This is an additive source-model/generated migration and one reviewed index replacement, with no new tables. Validate redundant target fields against normalized source before disclosure/order updates.

Existing master response queries select only the master key. Add an explicit single-original response query returning the fixed bounded roster with current/prior/unknown state, exact original and effective target version/active state. Querying unknown participation allocates nothing. Source descriptors expose their optional original under existing independent raw-read permission; bounded source lists remain all-or-nothing. No totals, cross-occurrence list or new cursor.

Keep existing 256 sources/1,024 receipts per binding, scope caps, 512 KiB source and 30-day defaults; targets/response rows cannot exceed retained source references. Scan up to the existing hard source cap for publisher inactivity hooks, sharing work budgets. Protect current ordering per active target, prune inactive targets only under the existing source/reference rules, and never evict history to admit input. All master-changing and single/range/restore/cancel publisher paths re-evaluate tracked instance currentness in the same shared-scope transaction, including hosts without inbound adapters. Unrelated target versions retain currentness.

The synthetic example adds an explicit original selector and single-occurrence label while keeping master review separate. Stable retries include exact original and body-defining values. No mail, delegation, attendee-side invitation intake, RANGE response, manual overwrite or response-to-invitation correlation beyond this reviewed profile follows.

## Alternatives and consequences

Limiting replies to separately published exceptions would omit the confirmed any-original policy. Expanding every recurrence into stored response targets would create unnecessary unbounded work; explicit original queries and source-backed rows avoid that expansion. Storing a different basis key alone does not distinguish old/new minimal wire replies when independently allocated numbers collide. The proposed outgoing floor/profile upgrade addresses that boundary but requires all participating hosts to upgrade together and an explicit new invitation for legacy bindings. Native inheritance is preserved; RANGE replies and broader transport correlation still need separate profiles.

Generate migrations normally and verify fresh/populated upgrades. Exercise actual two-host publication/reply races and process loss, generated clients and labelled Flutter selection. Use focused tests during development and full batch checks before one code commit. External client/mail conformance remains separate.
