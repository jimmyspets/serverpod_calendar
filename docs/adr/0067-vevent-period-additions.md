# ADR 0067: VEVENT PERIOD additions

Status: **Accepted PERIOD batch; adapter mechanics remain under review**. Date: 2026-10-22.

## Context and authorized scope

The maintainer selected PERIOD-valued RDATE additions after [recurring masters](0066-recurring-vevent-master-adapter.md), followed by separate occurrence components. The pure core already preserves positive PERIOD spans and rejects conflicting forms at an original identity under [ADR 0040](0040-bounded-temporal-core-completion.md); the current whole-second/date/zone profile remains authoritative under [ADR 0041](0041-whole-second-1970-2100-profile.md). This batch adapts wire values to that behavior without changing native service storage or endpoints.

Sources: RFC 5545 [PERIOD](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.3.9), [RDATE](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.5.2) and [recurrence duration](https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.5.3). RFC syntax/requirements are distinct from our bounded native conflict/profile policy.

## Implemented adapter mechanics

Accept explicit VALUE=PERIOD only on RDATE for UTC/named DATE-TIME masters. A comma-separated list may mix start/end and start/positive-duration forms; separate RDATE properties may use start-only values. Parse each pair into TimedEventSpan and expose it through IcalendarEvent.recurrence.timedSet.periods. Require one solidus, nonempty halves, strict DATE-TIME/DURATION grammar and a positive resolved interval. Negative and zero durations reject; an explicit positive sign is valid. Do not turn DATE-only events into timed events, allow PERIOD EXDATE or infer PERIOD from an untyped value.

Both start and explicit end use the property's independently validated TZID. Every period start must match the master's exact UTC/named/alias profile. Missing TZID remains floating and rejects; UTC suffix plus TZID, missing/unmatched zone definitions and mixed aliases reject. Supplied definitions retain full-horizon pinned-IANA matching. Explicit gap/fold rules remain unchanged, and interval positivity is evaluated on resolved instants. Duration units remain nominal: P1D can differ from PT24H across DST.

Period starts are ordinary 1970–2099 dates. An explicit exclusive end, or validated duration result, may reach only the approved 2100-01-01 midnight boundary in its temporal profile. No start, fraction, leap second or later endpoint may bypass existing guards. UTC padding stays calculation-only.

Reuse the core set: earlier additions do not rebase DTSTART or rule COUNT; a PERIOD supplies the complete span at the matching original identity, including one also generated by DTSTART/RRULE/start-only RDATE. EXDATE removes that identity without replenishing COUNT. Identical canonical spans coalesce, retaining every accepted source representation. Conflicting spans/forms at one identity reject even when excluded. Equal instants do not equate end and duration forms, or P1D and PT24H; this is explicit native policy, not a claim that RFC 5545 mandates that conflict rule.

Charge each raw pair once to the existing combined per-event/calendar explicit-date caps before normalization, alongside start-only additions and exclusions. Duplicates still count; endpoints do not count as separate occurrences. Syntax byte/line limits and shared rule/zone candidate work remain active. A late bad pair rejects the entire semantic calendar with sanitized diagnostics. Retain source parameters, raw pair spelling/order, units and forms; deterministic output remains source serialization with the existing FREQ-first normalization, not authorized export.

## Alternatives, consequences and acceptance

Flattening periods into starts loses their exceptional lengths. Converting all spans to elapsed duration loses nominal units and end/duration identity. Last-value-wins conflicts silently discard data; keep the existing core rejection instead. Expanding native persistence/import now would combine independent authorization, reconciliation and schema work with this pure adapter batch.

Focused VM tests cover RFC examples, round trips/source retention, union/COUNT/exclusion precedence, overlaps with starts before the window, duplicates/conflicts, exact zones/aliases, gap/fold and nominal DST durations, profile endpoints, malformed/context/parameter rejection, combined raw limits and atomic sanitized failure. Run the complete VM/Chrome and repository checks at batch completion. No schema, migration, generated protocol/client or dependency changes are expected. Separate occurrence components, database import/export, scheduling/alarms and HTTP publication remain pending.

## Subsequent scoped extension

[ADR 0068](0068-vevent-occurrence-components.md) adds separate occurrence timing/single-cancellation components and timing-only ranges. It supersedes occurrence-component rejection only for that profile; per-occurrence content/future cancellation and authenticated import/export remain pending.
