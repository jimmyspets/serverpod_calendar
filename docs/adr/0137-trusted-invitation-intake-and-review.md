# ADR 0137: Trusted non-recurring invitation intake and private review

Status: **Accepted by explicit maintainer approval on 2026-10-28 for the complete intake/review batch and three-table storage design. The scoped implementation and complete feature-batch validation finished on 2026-10-29; see the implementation guide and validation record.**

## Context and boundary

ADRs 0117–0120 provide pure iTIP validation; ADRs 0131–0133 implement organizer-side REPLY intake. Receiving an organizer REQUEST is a separate attendee-side workflow. The maintainer selected a private review queue: receipt does not create an event, book time, record acceptance or send a reply.

This calendar-owned scheduling queue is independent of the reusable notification module and does not add a persistent notification inbox. This first batch implements trusted intake and protected review/dismissal of one non-recurring REQUEST. Explicit Add to calendar, existing-meeting updates, participant responses, recurrence and CANCEL correlation follow separately reviewed batches. In particular, this batch provides no Add button that silently calls ordinary import. Ordinary imports, feed bearer URLs and organizer bindings do not authorize inbound scheduling.

Primary sources checked 2026-10-28: [RFC 5546 REQUEST](https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.2) and [message sequencing](https://www.rfc-editor.org/rfc/rfc5546.html#section-2.1.5). Queue presentation, storage limits and review policy are application choices rather than RFC requirements. Keep supported source distinctions and the existing strict whole-second, 1970–2099, matching-zone and payload profiles.

## Trusted ingress and authorization

Add a server-only receiveSchedulingInvitation entry point and replaceable host adapter. There is no reusable public endpoint accepting verified sender/recipient flags. Trusted ingress supplies bounded source bytes, a namespaced delivery key and origin reference; the host resolves the actual scope, an opaque recipient key and exact source calendar address, and verifies that origin may send for the exact source ORGANIZER. Headers, display text, UID and ATTENDEE claims provide no authority. A source ATTENDEE must match the host-verified target address. Native review resolves the current recipient from trusted session context, never a client-supplied recipient ID.

Use the declared coordinated/fresh-check guarantee without silent downgrade. Preliminary origin/target authorization precedes private history lookup; proposal/final checks include actual immutable source, digest, scope/recipient, existing entry/version and proposed classification, server IDs and retry status. Final denial/unavailability rolls back every proposed row. External fresh checks retain their after-check revocation race. The shared database scope transaction, uniqueness constraints and expected revisions coordinate independent hosts; process-local locks/caches establish no correctness.

Require independent receive/list/read-summary/read-source/dismiss operations. Hosts can map them to common rules. Summary access does not imply source access. Views and requests expose actual inbox/source identity and trusted recipient context; source addresses never grant host identity, assignment or organizer publication authority.

## Accepted message and ordering profile

Require exactly one supported non-recurring VEVENT REQUEST with required DTSTART/SUMMARY, DTSTAMP, UID, ORGANIZER and a target attendee. Reject recurrence properties/RECURRENCE-ID, detached/range components, delegation/SENT-BY and unsupported data explicitly. Reuse the pure parser and exact full-horizon known-zone validation, without dropping components or applying native defaults. No imported alarm is armed and no URI is fetched.

Correlate within scope/recipient by exact source UID plus organizer address; different organizer claims are not automatically merged or treated as a verified organizer replacement. Preserve sequence omission as source omission while comparing it as zero. Order by SEQUENCE first, then DTSTAMP: higher sequence wins even with an earlier stamp; at equal sequence a later stamp becomes current, an earlier stamp is stale, and equal version/stamp with different normalized source is a conflict. Retain unapplied stale/conflict records for protected review. Source clocks prove neither trust nor local freshness; the host may impose an explicit clock policy.

Deterministic source serialization preserves supported property groups/order/omissions; equality is not universal semantic equivalence. Compare normalized text as well as its digest. Exact duplicates never replace current state or advance the inbox revision. Retained same-key/same-source retries reauthorize and return the original receipt; the same key with different source/target/origin evidence rejects. Different keys can share one source row and retain independent receipts. No duplicate or stale message creates an event or sends anything.

## Three proposed private tables

1. **Invitation entry — CalendarInvitationRecord**: server UUID, trusted scope/recipient, exact UID/organizer correlation, revision, current source UUID, database audit times and optional dismissal time. It is independent of calendars and has no event/booking/participation link. Use a unique scope/recipient/correlation-digest key over length-prefixed exact UID/organizer values; verify the retained values after lookup and reject a digest collision. Do not index unbounded raw UID/address strings. Scope/recipient opaque keys are bounded to 512 UTF-8 bytes. The current-source reference may be transiently absent while constructing a new entry inside its transaction; a committed pending entry must have a validated current source.
2. **Source record — CalendarInvitationSourceRecord**: server UUID/entry, normalized bounded REQUEST, its UTF-8 byte count and digest, source SEQUENCE presence/DTSTAMP, classification and database receipt/retention times. Retain the latest pending source independently from terminal history. Private full source may contain participant/contact information; ordinary summaries and exports do not expose it.
3. **Ingress receipt — CalendarInvitationReceiptRecord**: trusted scope/recipient and digest of namespaced delivery key, source UUID, origin evidence digest, outcome and database time/expiry. Uniqueness spans entries within that recipient so a conflicting key cannot create a second UID. No provider credentials, mail transport payload/header archive or device tokens are stored.

Proposed default bounds: 64 pending entries per recipient, 16 retained sources per entry, 256 retained sources/16 MiB normalized source bytes and 1,024 receipts per recipient, with a 256 KiB input/normalized-message cap. These are initial profile caps; hosts may lower them through validated options. Increasing them needs explicit profile review. Reaching a count/byte limit fails atomically without evicting live evidence. Existing stricter syntax/component/work limits still apply. Dismissed retained markers/receipts have their own bounded counts (64 entry markers per recipient in addition to pending entries); cleanup precedes admission and never deletes protected references. No SQL/index source is added before maintainer model review; fresh/upgrade and real process tests are required after generation.

Superseded/stale/conflict source and receipt retention defaults to 30 days. The current pending source survives until a newer source or explicit dismissal. Unexpired receipts retain their source; record inactivity when a current source becomes terminal, then prune expired references before eligible sources/markers. Dismissal retains a minimal correlation/version/digest marker for the same configurable 30-day window, without an event or restore/archive promise. Retained bodies are available only through source-read authority until eligible cleanup; dismissal is not an immediate erasure feature. Bound cleanup work and report capacity failure rather than silently deleting protected rows. Duplicate guarantees end after the documented marker/receipt retention; an old delivery may then reappear for review but can never automatically recreate a calendar event.

## Review and dismissal APIs/example

Return the current recipient’s pending queue as a complete bounded list without totals, using per-entry summary authority; deny omits a row and unavailable policy fails the whole request. The first personal queue is capped at 64 pending entries, so it uses a complete bounded list rather than a silently truncated page. A summary contains the opaque entry/revision, organizer address whose sender authority the host verified, source UID, summary/timing, source version/receipt time and pending/dismissed state; it omits other attendees, private CONTACT and raw source. Source/history review independently authorizes each entry/source and shows inert text, classifications and preserved omissions.

Dismiss requires the expected entry revision and a separate operation. It hides the selected current version without accepting/declining or sending anything. Exact duplicate receipt preserves dismissal; a strictly newer current source reopens review, while stale/equal-conflict sources never do. Retained retry/dismiss no-ops reauthorize. Inbox revisions change only when visible current/dismissal state changes; native calendar scope generations/protocol state remain unchanged because no calendar content changes. The same scope transaction still serializes inbox writes.

Add a protected example invitation-review screen and synthetic-only trusted ingress fixtures. Clearly label receipt as unprocessed and do not label it accepted/added. Source links/addresses remain inert. Calendar adoption and response actions will follow with separate concurrency, baseline, local-edit, deletion and scheduling-correlation contracts.

## Alternatives and acceptance

Automatic creation conflicts with the confirmed review-first policy. Reusing ordinary event import would conflate trusted scheduling correlation with duplicate-conflict file import. Copying full bodies into every receipt increases private retention; three tables separate source identity, delivery idempotency and current inbox state. Holding everything forever violates bounded retention; deleting all ordering evidence on dismissal allows immediate duplicate resurfacing.

Test verified/spoofed/unknown origins and recipient isolation; DATE/UTC/named zones and unsupported recurrence/delegation; sequence omission/order/ties, normalized/cross-key duplicates and key conflicts; immutable final host context, rollback/overflow and unavailable policy; summary/source separation, dismissal/newer-source behavior, retention/reference/capacity boundaries and no event/feed/alarm/outbound mutations. Exercise two actual hosts racing duplicate/conflicting ingress and dismissal, actual loss before/after commit with stable retries, generated clients, synthetic-only Flutter review and fresh/upgrade schema. Run focused tests during development, then full batch checks before one implementation commit. MIME/real mail, calendar adoption, updates, recurrence and remaining iTIP methods stay required separate work.

Implementation mapping: the approved dismissal marker stores current SEQUENCE presence, DTSTAMP and digest directly on the entry so eligible terminal bodies can be pruned without losing retained ordering. currentSourceId may become absent only for a dismissed marker after pruning, never for a committed pending entry. Receipts retain the original entry revision for stable retries. These fields implement the approved minimal version marker and retained-result mechanics; no event link or adoption state is added.
