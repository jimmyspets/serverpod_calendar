# ADR 0175: Bundled invitation whole-series cancellation and reopening

Status: **Proposed — requires explicit maintainer agreement before implementation.**

## Context and inspected evidence

[ADR 0174](0174-complete-bundled-invitation-updates.md) implements complete linked REQUEST updates. Implementation [PR #180](https://github.com/jimmyspets/serverpod_calendar/pull/180), commit `6c61092690ab458a5ed83a9f6afb26a985f99ece`, passed its recorded local group; hosted inspection passed and runtime remains in progress in [run 42036382773](https://github.com/jimmyspets/serverpod_calendar/actions/runs/42036382773). That observation is not a full hosted conclusion.

The permanent `bundledRequest` link flag currently fences every CANCEL, scalar application and participation path. The full event import baseline already retains every accepted component, and the application row binds its digest and latest immutable result. Ordinary whole-CANCEL projection preserves the accepted content/overrides while replacing master status/version; reusing that projection alone would not validate the bundle's independent component floors or missing review evidence.

[RFC 5546 section 3.2.5](https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.5) identifies whole recurring cancellation by UID without RECURRENCE-ID, requires a higher SEQUENCE and distinguishes whole cancellation from attendee removal. The RFC does not require the conservative maximum-of-all-components floor proposed below. Existing pure validation and trusted host ingress remain separate boundaries; participant addresses establish no authority.

## Proposed complete group

Implement trusted whole-series CANCEL review, explicit clean-series Apply cancellation, complete REQUEST reopening, repeated whole-lifecycle cycles, protected views, generated clients, synthetic MIME/Flutter and two-host/process-loss checks together. Restrict this to an active imported event linked by `bundledRequest=true`. Receipt/dismissal never changes the calendar or participation. Keep pre-adoption cancellation, mode conversion, instance/range cancellation, roster changes, partial merges/removal, replies, VALARM and real transport guarded.

Accept one supported CANCEL component with matching UID/organizer, no RECURRENCE-ID/RANGE or recurrence properties, explicit STATUS:CANCELLED and SEQUENCE, and attendee addresses drawn only from the fixed accepted roster including the actual trusted recipient. The CANCEL may name a subset of that roster, as the RFC permits. Do not interpret a status-free attendee-removal notice as whole cancellation. Reject cancellation text/timing/metadata outside the minimal UID/organizer/attendees/status/sequence/stamp profile; legal participant parameters already supported by the pure profile remain inert source data. This deliberately bounded native profile does not claim the RFC forbids other properties.

Require CANCEL SEQUENCE strictly greater than the master and every explicit accepted component's effective-zero sequence, and every component of a different retained pending REQUEST. A newer pending CANCEL is another strict floor. Do not use DTSTAMP alone to cross a cancellation floor. Exact retained ingress retries run first and reauthorize without reactivation. An identical normalized cancellation body is a duplicate; a different normalized body tied at the same cancellation version rejects, rather than treating different cancellation claims as interchangeable. A lower or incomparable packet rejects as a whole.

Retain ADR 0174's complete-set REQUEST rules for reopening: preserve every accepted original/range identity and independent component version, reject regressions/removal/orphans and require the new master SEQUENCE strictly above the accepted or selected pending cancellation. Unchanged children keep their original versions. A child-only REQUEST cannot reopen a cancelled series. A complete newer REQUEST can supersede pending cancellation review without changing the still-active event; an already accepted cancellation requires the separate explicit reopening command. Reopening may carry supported changed content/timing under the existing complete-set rules; it does not clear individually cancelled components.

## Proposed state and storage

Reuse the existing one-per-link `CalendarInvitationApplicationRecord` and event import baseline; no SQL table/column or retention-cap change is proposed. Add `bundleCancellation` to the source-kind enum, appended after existing values. Only trusted correlation to the permanent bundle link may classify the otherwise single-component CANCEL this way. Never classify unrelated whole CANCEL messages as bundles from their syntax alone.

Applying cancellation creates a full cancelled baseline: retain all accepted timing, recurrence, text, metadata, overrides, child source versions and individual cancellations; replace only master status/presence and master protocol version with the actual cancellation SEQUENCE/DTSTAMP, with absent optional CREATED/LAST-MODIFIED left absent. No component version or content is invented from a minimal CANCEL. The native event stays present and its entire series stops contributing busy time or reminder delivery. Receipt alone suppresses nothing.

The application row's `kind=bundleCancellation` binds the actual cancellation source/digest and the full cancelled-baseline digest. Its scalar version remains the master version. The bundle reader must allow cancelled baseline content only when it matches that accepted kind; an ordinary REQUEST checkpoint with cancelled master state remains corrupt. Reopening installs a validated full REQUEST baseline and `kind=requestBundle`. Preserve the original creation receipt, native UUID, associations and personal alarm/action records. Feed/alarm/scope generation fencing follows the existing transactional path; reopening does not replay accepted firings or reset acknowledgements.

Do not copy source bodies or embed predecessor checkpoints. Keep current accepted state and one latest update/lifecycle result. Cancellation/reopening supersedes the prior update/lifecycle retry under the same latest-only rule; exact current retries reauthorize and return their immutable result without saving, even after local edits, source pruning or a newer review. Old creation retries remain separate. Missing/corrupt baseline or mismatched kind/version/result bindings fails unavailable. Parent deletion scrubs active data and cannot be undone by retry.

## Proposed APIs and authorization

Keep `bundleApplication` as the protected full view. Add read-only `acceptedKind`, optional `incomingKind`, `canApplyCancellation` and `canReopen` fields; `canApply` continues to mean ordinary active-series REQUEST update. Incoming cancellation version evidence has one actual master entry; it must not be presented as a newly received full component vector. Its proposed native projection separately retains all accepted children. Distinguish unavailable source bodies from known baseline projections.

Add `applyBundleCancellation` and `applyBundleReopening`, reusing the existing immutable Apply request/revision tuple and receipt. Require `expectedOccurrenceRevision=0`; bind separate command-digest prefixes and actual source kind. The ordinary `applyBundleUpdate` rejects cancelled accepted state rather than silently reopening it.

Add independent host operations `receiveBundleCancellation`, `applyBundleCancellation` and `reopenBundle`. CANCEL ingress still requires receive/receiveCancellation plus bundle authority. Reopening requires applyBundleUpdate and reopenBundle authority. Every read/write retains actual scope/recipient/link correlation, summary/source/link/full-bundle disclosure, native import/replacement/edit and lifecycle permissions. Expose complete actual current/proposed native and review snapshots, accepted component evidence, actual incoming message, accepted/incoming kinds and result. Preliminary and final checks remain mandatory; declared coordinated/external guarantees and the after-check race are unchanged.

All new applications require matching calendar/event/invitation/application revisions and a clean entire series. In one transaction update the complete native state/baseline, checkpoint/result, selected review and generation fences. A final denial rolls everything back. Never apply cancellation over local content changes or let imported source claims authorize lifecycle edits.

## Retention, reconstruction and limits

Use unchanged source/receipt/link/active-baseline byte/count/retention limits and one shared work budget across full baseline validation, pending/accepted comparisons, source parsing and candidate construction. Capacity/work exhaustion rejects atomically. Do not infer missing pending versions. If a surviving marker's different selected body expired, new admission is unavailable; after normal unaccepted-marker pruning the surviving accepted baseline/kind may reconstruct review without inventing expired history. Preserve the permanent bundle flag and recurring mode through CANCEL and pruning. Historical duplicate REQUEST/CANCEL source rows must validate against the permanent profile, not only today's entry kind.

An accepted cancellation body may expire while its validated kind, source descriptor, master version and full cancelled baseline survive. Views/retries then report unavailable bytes without fabricating a REQUEST or MIME body. A new strict-version CANCEL/REQUEST may use that accepted proof. A tied different CANCEL body never gains semantic-duplicate admission merely because earlier bytes expired. Existing foreign-key/deletion/retention rules and limits do not widen.

## Complete acceptance and consequences

Test DATE/UTC/exact named zones, child SEQUENCE above master, subset/foreign/absent recipients, missing/zero/tied/lower cancellation versions, backwards source clocks with higher sequence, cancelled creation corruption, full vector reopening, retained individual cancellations, pending alternation, pruning/marker reconstruction, local conflicts, independent/final-denied authority, result corruption, no recreation and source omission preservation. Verify free/busy, previews, reminder suppression/reopening without replay, private actions and ordinary scalar/instance/range/response guards. Race intake/apply across two hosts and kill before/after every commit; exact receipts and one active state must survive. Extend generated-client and connected Flutter explicit cancel/reopen journeys and the complete CI entry point. Run focused iterations, then the complete relevant group and exact-head hosted checks; commit code once the whole approved group is complete.

This closes one coherent whole-series lifecycle gap without designing component-wise cancellation merging. A separate lifecycle/history table would add an unnecessary retention boundary; overloading the older occurrence ledger would mix incompatible link profiles. If implementation needs new persisted fields, recursive state or larger limits, return for review. The maintainer's earlier whole-series clean-baseline policy remains; explicit agreement on this ADR is still required for these new bundle mechanics.
