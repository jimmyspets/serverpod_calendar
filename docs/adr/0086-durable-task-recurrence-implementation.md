# ADR 0086: Durable task recurrence implementation

Status: **scoped implementation of maintainer-confirmed ADR 0085 choices; concrete mechanics under draft review**. Date: 2026-10-23.

Extend the task content timing disclosure with canonical recurrence rules/inclusions/exclusions. Require explicit start and reject PERIOD additions and floating/fractional/profile-mismatched inputs. Reuse core start-based expansion, nominal duration versus elapsed explicit due semantics and bounded original identities; do not use task dates as bookings. Preview queries are revision-bound, bounded to 366 days/500 results and charged against existing candidate/rule budgets. ISO week presentation stays separate from explicit rule WKST.

Persist a bounded set of per-original-occurrence current progress rows and append-only transition rows in the active task family. Only actual progress changes append evidence, with server-recorded time and before/after state; an accepted identical write advances native API concurrency state but does not invent a transition. Keep original typed start/profile, trusted task/parent, actual prior state and final validated proposal in authorization. Separate history reading from ordinary progress disclosure, requiring both current progress read access and dedicated history authority. No actor identity is published by the first history projection.

Recurring masters keep the initial neutral current progress; ordinary whole-task progress commands reject for a series. Each original occurrence independently follows the confirmed completion/cancel/reopen rules. Bound recorded originals to 1,000 per active task; exceeding work/storage budgets fails without partial state or pruning. Histories have bounded authorized pages with opaque continuations, no totals, bound to original identity, task revision/scope generation, actor/policy and query kind. Retain history until task deletion; deletion scrubs current/history rows with the active payload. Configurable pruning is separate.

Track whether native non-recurring progress has ever changed so reopening cannot erase the evidence needed to reject ambiguous conversion. New tasks explicitly start with false. Legacy rows without this checkpoint remain unknown, not fabricated false; reject conversion without a trusted clean checkpoint. No retrospective transition history is inferred. Native conversion also requires neutral current progress. Recurrence/timing pattern edits preserve every recorded original; reject removed/profile-changed originals and removal of recurrence while records exist. A later explicit reconciliation API will resolve such cases; this batch never silently discards or retargets them.

Implement generated DTOs and separate server-only current/history tables, additive cursor bindings/checkpoint migration and fresh/populated upgrade checks. Validate immutable host context, disclosure/permission separation, stale/final-denied rollback, membership/exclusion/DST, no-op transition behavior, deletion scrubbing, two-host competing progress and Flutter preview/history actions. VTODO interchange, task timing/content exceptions, all-series lifecycle operations, scheduling and alarms remain separate.
