# ADR 0111: Native personal alarm definitions

Status: confirmed personal-recipient, explicit DATE zone, shared-edit/deletion, trigger scope and bounded single-table choices; concrete mechanics under draft review. Date: 2026-10-24.

Implement private native event/task definitions and example timing editors before planning/delivery. A trusted host resolver supplies the current recipient from authenticated context; requests never select recipients. No source-alarm adoption or activation occurs. Definitions remain unarmed and produce no notification intent or action state. Native definitions never enter ordinary item responses or source exports.

Use one private table with server UUID, scope, actual calendar and exactly one event/task parent, trusted recipient namespace/key, revision, immutable trigger/repeat configuration and database audit times. Full deletion removes the row; no new permanent marker/retention is chosen. Hard-cap 16 definitions per recipient/item and return a bounded parent-scoped list without totals. Existing item/calendar deletion rules remain except that hidden personal definitions do not block parent deletion: delete their content transactionally with the item.

Relative START/END triggers apply independently to original recurring occurrences, while absolute UTC applies once per definition/item. Per-occurrence personal overrides follow separately. DATE-relative anchors use midnight in an explicit named IANA zone, never server/device inference. Relative units retain existing calendar-first duration/DST semantics; whole-second/range rules remain. Reuse bounded 366-day offsets/repeat spans and 100 additional repeats as the initial limits. Repeat requires a positive interval and nonnegative bounded count. Timed END requires an explicit end/due or duration; relative START requires a start. Absolute reminders support undated tasks.

Creating or replacing a definition validates available anchors. Later shared item edits must not be rejected because of private definitions: retain invalidated definitions as needing attention. Future planning must validate every effective original/current timing and skip invalid configurations rather than infer missing anchors/zones. Cancellation/progress does not delete definitions; execution suppression is a later lifecycle decision. No firing-ready or delivery claim follows from anchor compatibility.

Host checks are independent personal-alarm operations with actual current calendar/event/task, trusted recipient, alarm identity/current settings and validated proposed settings. Scope locks serialize limits, revisions and parent-deletion races across instances. Re-resolve current recipient/context for final checks; declare the existing coordinated/external guarantee and residual external race. A caller can never query another recipient through an alarm UUID. Private writes do not change event/task protocol versions, source baselines or content revisions. Private writes leave public scope generation unchanged; the complete bounded personal list has no continuation. Mutation receipt disclosure is host-controlled independently of list access.

Expose timing/repeat/DATE-zone editors only. Notification text will derive later from freshly authorized parent data; custom text, native acknowledgement/snooze, arming/adoption, planning/outbox and generic notification streams remain separate batches. Test boundary validation, same-scope multi-recipient isolation, cross-scope/parent spoofing, stale/final-denied writes, 16-limit races, invalidation and deletion atomicity, no item protocol mutation, actual generated clients and Flutter editors.
