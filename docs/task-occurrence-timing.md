# Single task occurrence timing

Status: scoped native/wire/example implementation under [ADR 0101](adr/0101-single-task-occurrence-timing.md); concrete mechanics remain under draft review. The maintainer confirmed single-occurrence scope, complete timing replacements, completed-history preservation, progress capture and complete explicit wire timing. [This-and-future timing](task-future-timing.md) now extends this slice under ADR 0102; per-occurrence text remains separate.

## Native action and identity

`calendarTask.changeOccurrenceTiming(CalendarTaskOccurrenceTimingRequest)` accepts actual task UUID, expected API revision, exact original typed start and nullable complete `replacement`. A replacement requires a start in the master's DATE, UTC or exact named-zone profile. It may have no deadline, explicit DUE or positive DURATION; add/remove/switch forms explicitly. Null follows the series timing again without deleting progress, metadata or history. Whole seconds and ordinary [1970,2100) dates remain mandatory for starts and due values; due values do not use event-exclusive endpoints.

Timing edits use `updateTask` authority, independently of progress and assignment permissions. The host receives trusted scope/actor, actual parent/task/original, current and validated proposed occurrence timing/progress, every recorded original and independent proposed component version. Every operation uses the durable scope transaction, rejects stale revisions and rechecks final declared-guarantee authority. A final external check retains its documented revocation race. No client-claimed parent or process-local lock is trusted.

A completed occurrence can move without reopening. Preserve its exact original identity, percentage/completion time and history. If timing first creates an own component, capture the original's current effective progress without adding a progress-history transition. That captured value is independent of later source-master progress changes. Existing sparse own progress stays unchanged, including independently absent fields. Clearing timing retains that own progress/component and all history; resolving/removing recorded originals remains separate work.

Changed timing advances only the occurrence component version, creating SEQUENCE 0 and known local timestamps for a new component. Legacy records lacking versions use the existing documented local baseline without inventing CREATED. Identical timing saves retain protocol versions; accepted native writes still advance API revision/audit time/scope generation. Master protocol version, assignments and parent metadata time are unchanged. Deletion scrubs active timing/progress/history with existing payload deletion. Pattern/profile changes preserve replacements and reject orphaned originals.

## Effective-start queries

Previews retain `originalStart` and add typed `actualStart` plus optional stored `replacementTiming`. `startUtc` and `dueUtc` retain resolved instants independently of civil display, including later-fold due identities. DATE deadlines use `dueDate`. Windows filter effective starts: include moved-in originals, omit moved-out ones, preserve distinct originals at colliding actual starts, and sort by actual start then original. A due date is not a reservation or an overlap-query interval.

Pure core expansion validates all replacement anchors collectively and charges membership and query generation to one shared candidate-work budget. Native records remain bounded to 1,000; previews retain 366-day/500-result and existing rule/work limits. No partial query or mutation escapes a limit failure. Conservative bounded scans can reject requests whose visible result would be small. DATE/UTC/named-zone durations preserve calendar units versus elapsed explicit DUE semantics; named-zone resolution keeps the selected RFC gap/fold behavior.

## Wire presence and pre-beta transition

An occurrence component with **explicit DTSTART supplies its complete timing**. Omitted DUE/DURATION means no deadline, even when the master has one. Omitting all timing follows the master projection. Matching DUE-only repetitions from the earlier profile remain source-preserved following projections; a different DUE without DTSTART rejects. RANGE=THISANDFUTURE now follows the [future timing profile](task-future-timing.md); content differences still reject. Master/original membership and exact profile must match; original identities never become moved starts. This is the selected bounded application profile, not a claim that RFC 5545 defines these inheritance choices or that external clients handle every form identically.

Source timing writes retain metadata/annotations, raw progress and private import baselines. Full generated round trips validate current state and pinned full-horizon zones. Source alarms remain unarmed; reject a timing change that removes an inherited/retained relative END anchor instead of discarding or activating the alarm. Absolute source alarms remain inert values. Native task assignments still never become source participants.

**Breaking pre-beta source profile:** private task baselines now use `task-source-v2/<pinned-IANA-version>`, superseding v1. Existing v1 imports fail closed and must be reimported into fresh/recreated development data; no automatic adoption, timestamp correction or baseline invention is performed. Source components that explicitly repeated DTSTART can now have different deadline meaning. The nullable generated migrations preserve existing rows without guessing their interpretation or creating replacements. No development database reset is performed by this implementation. Native source-free tasks remain usable; old imported data needs explicit recreation/reimport. Root test reset affects only dedicated synthetic test storage.

## Example and verification

The Flutter occurrence screen displays original and actual starts, allows complete single timing replacement with no deadline/explicit deadline/duration forms and provides “Follow series timing.” It preserves completion status; history remains a separate read. Named-zone explicit deadlines require entered civil fields rather than guessing a fold from a UTC preview. Stale writes reject and require reload. The example exports/imports the same scoped source semantics without activating alarms.

Focused tests cover core moves/order/work limits/DST, wire presence and alarm anchors, native progress/history capture, immutable host context, independent permissions, stale/final denial, pattern orphans, late rollback and UTC/zoned persistence/export/reimport. Full `./tool/check.ps1` passed: core 474 VM + 474 Chrome, wire 310 + 310, module 149 VM + 17 Chrome, widgets 3 and database 282, plus populated upgrades, two-host timing/progress races, the complete Flutter move/clear/history journey and release Web build with successful Wasm dry run. Commands and scope are recorded in [validation](scaffold-validation.md). Native future timing, content exceptions, source reconciliation, alarm execution and external-client interoperability remain separate.
