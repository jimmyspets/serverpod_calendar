# Repository guidance

## Current state and sources

This repository now contains an initial workspace/authentication scaffold; calendar domain features remain documentation-first. Read README.md, docs/discussion-migration.md, docs/requirements.md, and the relevant proposed ADRs before changes. The per-RFC tables in docs/rfc/ are the latest feature-scope source; explicit newer maintainer instructions take precedence. Reconcile older narrative text with the table statuses and notes without treating unapproved implementation detail as accepted. Architecture documents describe proposals, not implemented behavior. Do not invent earlier chat decisions or claim complete iCalendar, CalDAV, or client compatibility.

## Current calendar profile

The maintainer selected whole-second calendar timing and ordinary dates in **[1970-01-01, 2100-01-01)** under [ADR 0041](docs/adr/0041-whole-second-1970-2100-profile.md), superseding earlier microsecond/broad-date/2037 limits. Nonzero fractions reject without rounding. Only explicit exclusive endpoints may be 2100-01-01 midnight; UTC calculation padding does not extend ordinary storage. Keep the current timezone library and reproduce the bounded generated IANA data using [the update procedure](docs/timezone-data.md); never edit its generated payload by hand. Preserve historical ADR/validation evidence with clear supersession notes. APIs remain unpublished and breaking changes are authorized.

## Change discipline

- Preserve existing contents and the Apache 2.0 LICENSE.
- Use a focused branch and pull request; keep architecture PRs draft while material design questions remain.
- Check existing issues and PRs before creating overlapping work.
- Keep source evidence, assumptions, proposed decisions, and verified behavior distinct.
- Record material boundary, storage, time, recurrence, or protocol changes in an ADR. Proposed ADRs become accepted only after explicit maintainer agreement; merging documentation alone does not approve every proposal. The maintainer authorized removing superseded uncommitted ADR drafts after preserving relevant guidance and updating references; preserve committed/accepted decision history. Keep uncommitted draft ADR numbering consecutive and update filenames, titles, indexes and references together when renumbering.
- Keep requirements, compatibility matrix, per-RFC property/feature plans under docs/rfc/, roadmap, and issue acceptance criteria consistent. Distinguish planned/proposed/undecided support from implemented behavior and preserve the module-versus-feed boundary.
- Use Mermaid diagrams in Markdown fenced code blocks labeled `mermaid` for documentation diagrams. Keep diagrams consistent with the accompanying text and clearly label proposed designs.
- Never commit credentials, private calendar exports, personal event data, or production configuration. Use synthetic fixtures.

The maintainer confirmed a separate optional Serverpod module for iCalendar HTTP feeds under [ADR 0042](docs/adr/0042-optional-http-feed-module.md). Calendar domain APIs/storage and authenticated import/export remain independent; feed credentials, selections and HTTP/ETags belong to the feed module. Names/contracts/scaffolding remain pending.

Under [ADR 0043](docs/adr/0043-host-authorization-context.md), modules enforce authorization while a replaceable host adapter decides using trusted actor/scope, specific operation, actual collection/object/parent context and relevant current/validated proposed state. Do not trust client-claimed parentage or hard-code a required owner/role scheme. See [authorization documentation](docs/host-authorization.md); APIs/query/transaction integration remain proposed, not implemented.

Query response choices under [ADR 0044](docs/adr/0044-authorized-query-projections-and-pagination.md) are confirmed: separate detail/free-busy responses, predefined disclosure groups, and authorized initial pages with opaque continuation and no totals. Filtering, field mappings, cursor/snapshot and policy consistency are still proposed; see [query design](docs/authorization-queries.md). Never derive free time from a detail list filtered by visibility.

Under [ADR 0045](docs/adr/0045-authorization-consistency-guarantees.md), support coordinated and external fresh-check host policies with explicit guarantees and no silent downgrade. A final external check does not eliminate an after-check revocation race; same-database reads alone do not prove commit coordination. Defaults/operation requirements/protocols remain proposed in [the consistency guide](docs/authorization-consistency.md). Existing current feed/worker/cursor checks remain required.

## Implementation guidance once scaffolding exists

Read the scoped [example guidance](example/calendar_example/AGENTS.md) and module AGENTS.md files before working in those folders. Use the root setup/generation/check/start scripts described in [local development](docs/development.md); they coordinate the workspace, isolated synthetic test storage, generated clients and Flutter Web journeys. Keep seeding/reset local to development/test, record auth mail locally and inspect owned test logs under ignored `.local/`.

For an interactive running example, prefer Serverpod MCP migration, log, hot-reload/restart and Flutter launch/tooling-daemon operations when those tools are actually exposed and connected. Verify availability in the current session; a generated AGENTS.md or local MCP configuration does not establish access. Use the pinned CLI workflow when MCP is unavailable. Reusable modules are not standalone servers; run them through the example host. Stop a running host bundle before rebuilding that bundle on Windows.

After approved table-source changes, generate migrations with the pinned CLI or connected MCP and verify fresh/upgrade database behavior. Never hand-edit generated protocol/client/test tools or migration metadata. A generated `migration.sql` may be edited only for a necessary data-preserving transformation; its final schema must match `definition.sql`. Domain schema changes still require the model/ADR review gates.

Target Serverpod 4.x and later. Select and pin compatible Dart, Flutter, and Serverpod SDK versions during scaffolding, and verify compatibility before claiming support for a version.

Keep reusable calendar semantics independent of Serverpod and Flutter. Put persistence, authorization, and endpoint adaptation in the Serverpod module; keep iCalendar parsing/serialization behind an explicit adapter boundary. Do not hand-edit generated files: change their sources and regenerate using the pinned toolchain.

Authorization must be checked server-side for every read, write, query, import, export, association change and feed-management operation. Users, groups and membership belong to the host; store only opaque namespaced association references and use host policy adapters. Never trust client-supplied identity or membership. Handle event changes, import batches and feed selection changes transactionally; reject stale revisions rather than silently overwriting.

First-release requirements include named time zones, recurrence/exceptions, and iCalendar subscription feeds targeting Apple Calendar on iOS, Google Calendar and Microsoft Outlook. Date-only values are not midnight UTC timestamps. Preserve UTC, date-only and zoned local meanings; reject unsupported floating times explicitly. Never silently flatten recurrence or discard unsupported calendar data.

Feeds select one or more calendars and support multiple independently revocable long random bearer URLs with ETag/If-None-Match. Tokens grant read-only subscription access without a password; management remains host-authorized. Store token digests, redact bearer URLs, check revocation and continuing publication authorization before content or 304 responses, and keep proposed security policies distinct from verified behavior. See ADRs 0004 and 0005. Calendars also represent rooms, venues and equipment; first-release free/busy queries must resolve all availability-contributing calendars, preserve recurrence/DST/status semantics, protect event details and never label incomplete/denied results free. Separate management associations from subjects whose time is booked. See ADR 0006; querying availability alone does not guarantee an exclusive reservation.

## Validation and reporting

Use focused VM tests and directly affected regressions during feature development. At the end of an agreed feature batch, run broader formatting, analysis and complete core VM/Chrome checks plus relevant integration checks; run the full repository checks before marking the PR ready. Record which checks ran and which were deferred. Commit and push code only after the whole agreed batch is complete; do not make intermediate feature check-ins.

For documentation-only changes, check relative links, requirement/ADR consistency, and the changed-file list. Do not claim runtime tests passed when there is no application. Once code exists, document and run appropriate formatting, analysis, unit, and database integration checks using the selected SDK versions. Include commands actually run and results in each implementation PR. Add tests for authorization boundaries, import rejection/atomicity, temporal semantics, concurrency, and supported interoperability cases.

First-release standards also include RFC 7953 availability rules, RFC 5546 iTIP and RFC 6047 iMIP. Keep scheduling reconciliation separate from ordinary import and feed publication; host adapters provide trusted calendar addresses and inbound/outbound email. Validate participant authority, method/version/occurrence identity and duplicate/stale messages. Persist outbound intent transactionally and test retries/crash recovery. See docs/standards.md and ADRs 0012/0007; do not claim scheduling interoperability from subscription-only tests. No real email is authorized by documentation changes alone.

Use the defined RFC 7986 profile for calendar/feed descriptions. RFCs 9073/9253 and advanced RFC 9074 features are required design considerations; a scoped time-based alarm/runtime capability is now required under ADR 0009. Do not imply blanket extension support. Record per-feature support/defer/reject decisions under ADR 0014 before finalizing parser/schema choices; keep resource/participant publication metadata distinct from host identities and permissions, alarm data distinct from reminder execution, and relationship links distinct from authorization. Metadata changes must be reflected in deterministic feed output and ETags without disclosing other bearer URLs.

The primary product is the Serverpod calendar/free-busy/scheduling/task module, with generated Dart clients for host Flutter GUIs. External iOS/Google/Outlook feeds consume only a declared subset; preserve full canonical/native capability independently. Native availability search accepts lists of people/rooms/resources and a bounded period, with explicit per-target versus common-free behavior, optional minimum duration and complete/unknown coverage. Native tasks and an approved VTODO interchange profile are in scope; task dates do not automatically book time. Validate native/protocol behavior separately from feed-client UI support, and choose scheduling-mail targets independently. See ADR 0008.

First-release alarm execution and a reusable notification module are required. Under ADR 0020, the example may use Serverpod server events/streaming to connected Flutter clients; iOS/Android delivery is illustrative and must not be implemented directly here. No FCM/APNs or OS background-delivery release gate is required. ADR 0009 proposes calendar-owned timing/occurrence/action state and durable intent, a separate reusable notification delivery/device/provider boundary, and Flutter permissions/presentation/actions. Keep provider SDKs/tokens/credentials out of calendar core/tables. Revalidate current generation, recipient access, cancellation and expiry before dispatch/retries; distinguish provider acceptance from display/acknowledgement. Private/imported alarm handling and advanced actions need explicit policy; never auto-arm untrusted ICS alarms. Logical package responsibilities/names are selected in docs/scaffolding-plan.md; detailed contracts and trigger/action constraints remain under review.

The example host/Flutter app is a required automated integration-test application. Test real module/migrations, generated-client APIs, feed routes and Flutter journeys. The module must work with multiple concurrently active Serverpod instances; CI must exercise at least two independent host processes sharing test storage, cross-instance state/revocation, competing workers and instance-loss recovery. Do not rely on process-local locks, caches or sticky routing for correctness. Use synthetic data and deterministic mail/notification test adapters; retain separate real-client and connected-stream evidence. See ADR 0018 and NFR-14/NFR-15.

The initial scaffold pins Flutter/Dart/Serverpod in toolchain.json and pubspec.lock. Use docs/development.md and the repeatable local check scripts; CI configuration is deferred, while CI release requirements remain. Do not infer calendar/protocol support from the auth/module smoke tests.
